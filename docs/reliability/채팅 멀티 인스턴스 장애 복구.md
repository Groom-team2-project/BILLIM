# 채팅 멀티 인스턴스 장애 복구 로컬 시험

> 버전: v0.1.0\
> 시험일: 2026.10.26

## 목적과 조건

- 목적: Redis Pub/Sub 신호 유실, 수신 백엔드 재시작, MySQL 중단이 저장·실시간 수신·누락 복구에 미치는 영향 확인.
- 구성: `billim-perf-multi` 격리 Compose, 백엔드 2대(`billim-perf-redis-listener-pool`), MySQL 8.4, Redis 7.4. 기존 성능 시험용 128개 방·256개 계정 중 방 1개 사용. 운영 서비스·DB 미사용.
- 전송: A 서버에 HTTP POST, 같은 회원의 WebSocket은 B 서버에 연결. 각 전송의 고유 `clientMessageId`로 수신과 DB 조회 결과 대조.
- 도구: [`tools/chat-failover.py`](tools/chat-failover.py). 테스트 전용 `websocket-client==1.9.0`, `requests==2.32.3` 사용. 라이브러리는 Git 제외 `docs/performance/tools/chat-notification/local/deps/`에 설치 가능. 서비스 의존성 변경 없음.
- 원본: Git 제외 `docs/performance/tools/chat-notification/local/failover-*-20261026.json`. 파일에는 세션 원문을 기록하지 않음.

Redis 중단 중 HTTP 전송 시간은 **187·16·31·32ms**, B WebSocket의 HTTP 완료 이후 수신 대기는 **329·343·141·1,875ms**였다. 현재 DB 재확인 간격은 2초이고 각 회차는 전체 방 조회 완료 후 다음 대기 시간을 세는 `fixedDelay` 방식이다. 따라서 2초를 엄격한 복구 시간 상한으로 보장하지 않는다.

## 해석과 남은 문제

- Redis Pub/Sub은 [공식 문서의 at-most-once 전달 방식](https://redis.io/docs/latest/develop/pubsub/)이므로 중단 중 발행된 **신호 자체는 재생되지 않는다**. 이 구조에서는 채팅 원본을 MySQL에 저장하고, 연결 중인 백엔드가 DB 재확인으로 누락 메시지를 찾아 보낸다.
- 백엔드가 내려간 동안 그 서버의 WebSocket은 끊긴다. 재연결한 WebSocket은 현재 방 순번에서 시작하므로 중단 중 메시지의 과거 재생을 맡지 않는다. 프론트의 `afterSequence` 메시지 조회가 복구 경로다. 이번 시험은 API 조회 결과를 확인했으며 **실제 브라우저 화면의 자동 복구까지 측정하지 않았다**.
- MySQL 장애에서는 성공 응답 없이 저장도 되지 않았다. 그러나 약 **58초** 뒤에야 500으로 끝났다. 사용자 요청 시간 초과와 재시도 경험을 고려해 DB 연결 실패 시간을 별도로 점검해야 한다. 클라이언트가 먼저 시간 초과할 경우 저장 여부를 재조회하거나 동일 `clientMessageId`로 안전하게 재시도하는 경로도 검증 필요.
- 이 시험은 **1개 방·소량 전송·31.95초 Redis 중단**이다. 256 VU 부하 중 장애, Redis와 백엔드의 동시 장애, 장시간 네트워크 분할, Redis 구독만 끊기는 경우, MySQL 복구 중 다량 재시도는 검증하지 않았다. 따라서 모든 장애에서 메시지 유실이 없다고 일반화할 수 없다.

## 재현

격리 Compose와 기존 테스트 시드가 준비된 상태에서 저장소 루트에서 실행한다. 컨테이너가 `billim-perf-multi` 프로젝트 소속인지 도구가 먼저 확인한다. 실행 뒤 중단시킨 컨테이너는 복원하며, 판정 실패 시 비정상 종료한다.

```powershell
$env:PERF_IMAGE = 'billim-perf-redis-listener-pool'
docker compose -f docs/performance/tools/chat-notification/compose.multi.yaml up -d mysql redis backend-a backend-b
python -m pip install --target docs/performance/tools/chat-notification/local/deps websocket-client==1.9.0 requests==2.32.3
python docs/reliability/tools/chat-failover.py redis
python docs/reliability/tools/chat-failover.py backend-restart
python docs/reliability/tools/chat-failover.py mysql
docker compose -f docs/performance/tools/chat-notification/compose.multi.yaml down
```

`fixtures.json`이 없으면 [`seed-multi.py`](../performance/tools/chat-notification/seed-multi.py)로 이 격리 DB를 먼저 시드해야 한다. 시드의 세션 원문과 결과 JSON은 Git 제외 `local/`에 보관한다.
