# 인증 방식 결정

> 버전 : v0.1.0\
> 수정일 : 2026.10.08

서버 세션(DB)과 JWT 중 **세션을 선택한 근거**와, 감수한 리스크·개선 경로의 기록. 4장의 재검토 조건에 해당하면 이 문서부터 갱신.

## 1. 요구사항 — 결정의 출발점

| 요구사항 | 출처 |
| --- | --- |
| 제재·차단·로그아웃의 **즉시 반영** | 기획서 (신뢰·안전 정책) |
| 다중 인스턴스 대응 | 팀 결정 |
| 쿠키 기반 세션 전제 | API 명세 0.2 |

## 2. 선택지 비교

| | 서버 세션(DB) — **선택** | JWT |
| --- | --- | --- |
| 인증 확인 | 매 요청 DB 조회 1회 (유니크 인덱스, ms 미만) | 서명 검증만 — DB 불필요 |
| **즉시 취소** | 행 폐기 = 즉시 무효 | **불가** — 만료까지 유효. 취소하려면 매 요청 취소 목록 조회 = DB 조회 부활 |
| 다중 인스턴스 | 같은 DB 연결로 성립 (검증 완료 — [점검 문서](인증%20검증%20및%20보안%20점검.md) §2) | 서명 키 공유로 성립 |
| 구현·운영 | 테이블 1개 + 쿠키 | 키 관리, 리프레시 토큰, 만료 정책 |

**결정 논리 한 줄**: 즉시 취소가 요구사항인 순간 JWT의 유일한 이점(DB 없는 검증)이 소멸 — 남는 건 복잡도뿐.

JWT가 정답인 영역은 따로 있음: 취소 즉시성이 덜 중요한 **서버 간 인증(MSA)·외부 API 제공**. 그런 구간이 생기면 그 구간만 JWT 혼용 가능.

## 3. 감수한 리스크와 개선 경로

리스크의 정체는 세션의 비용이 아니라 **DB 중심 서비스 구조의 비용** — JWT로 바꿔도 거의 그대로 남음.

| 리스크 | JWT였다면 | 규모가 커지면 |
| --- | --- | --- |
| 매 요청 DB 조회 | 동일 (취소 목록 조회 필요) | 세션 조회만 Redis 전환 — 교체 지점 `AuthSessionService` 1곳으로 한정해 둠 |
| 커넥션 풀 한계 — 인스턴스당 풀 10 × N대 ≤ MySQL `max_connections`(기본 151) | 동일 — 비즈니스 조회가 어차피 DB행 | 인스턴스 증설 시 풀 크기·`max_connections` 재계산 |
| DB 단일 장애점 | 동일 — 비즈니스 데이터가 같은 DB | 레플리카 + 페일오버 (인증 코드 무변경) |
| 익명 세션 레이트 리밋 부재 | 동일 — 방식과 무관 | `RATE_LIMITED` 구현 (명세 0.1) |
| 카카오 장애 시 신규 로그인 불가 | 동일 | 기존 로그인은 카카오 없이 유지됨 — 세션 방식의 부수 이점 |

지금 선제 도입하지 않는 이유: 팀 컨벤션 "측정 없는 최적화 금지". 해결을 미루되 **교체 지점을 한정**해 전환 비용을 묶어 둠.

매 요청 **쓰기**는 이미 완화됨 — 유휴 만료 갱신은 `touchInterval` 경과 세션만 UPDATE.

## 4. 재검토 조건

- 세션 조회가 DB 부하의 유의미한 비중으로 **측정**될 때 → Redis 세션 저장소 전환
- 인스턴스 증설 계획이 나올 때 → 커넥션 산수 재계산
- 서버 간 인증·외부 API 제공이 생길 때 → 해당 구간만 JWT 검토
