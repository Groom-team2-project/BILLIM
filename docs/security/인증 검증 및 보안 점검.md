# 인증 검증 및 보안 점검

> 버전 : v0.1.4\
> 수정일 : 2026.10.29

공격자 관점에서 침입 시나리오를 시도한 기록. 세션·배포 구조가 바뀌면 같은 절차로 재점검.\
세션 방식을 선택한 근거는 [인증 방식 결정](인증%20방식%20결정.md) 참고.

## 1. 공격 시나리오 점검

점검 방식 3가지 — **재현**: 실제 공격 요청 전송(curl·브라우저) · **테스트**: 자동 테스트로 상시 재검증 · **코드/설정**: 해당 경로 검토.

| # | 공격 | 방식 | 결과 | 막는 것 |
| --- | --- | --- | --- | --- |
| 1 | 세션 토큰 추측 | 코드 `SessionTokens` | 실패 | 256비트 `SecureRandom`. 전수조사 불가 |
| 2 | XSS로 쿠키 탈취 | 코드 `SessionCookies` | 실패 | `HttpOnly` — 스크립트가 쿠키 접근 불가 |
| 3 | 훔친 쿠키를 피해자 브라우저에 심기(세션 고정) | 테스트 `rotatesSessionOnLogin` | 실패 | 로그인 시 토큰 회전. 심어둔 토큰은 폐기됨 |
| 4 | 공격자 code+state를 피해자 브라우저로 콜백(로그인 CSRF) | 테스트 `rejectsCallbackFromAnotherBrowser` | 실패 | state 소비가 시작한 세션으로 제한 |
| 5 | 가로챈 콜백 URL 재사용(state 재생) | 테스트 `consumesOnceUnderConcurrency` | 실패 | 단일 UPDATE 1회 소비. 동시 8요청 중 1건만 통과 |
| 6 | 타 사이트에서 변경 요청 위조(CSRF) | 테스트 `postWithoutCsrfIsForbidden` | 실패 | 세션 결합 토큰 + `X-CSRF-TOKEN` + `SameSite=Lax` |
| 7 | 타인 프로필 조회·수정 | 코드 `MemberController` | 실패 | principal 기반. 대상 ID를 받지 않음 |
| 8 | 요청에 `role` 등 선언 외 필드 주입 | 설정 `application.yml` | 실패 | `fail-on-unknown-properties: true` → 400 |
| 9 | 비로그인 POST 반복으로 DB 증식 | 재현 — 403 POST 5회에 `auth_sessions` 5행 증가 | **발견 → 수정** | 발급을 GET으로 제한. 회귀 테스트 `rejectedPostDoesNotCreateSession` |
| 10 | 운영 Swagger로 API 구조 정찰 | 설정 `application.yml` | **발견 → 수정** | prod에서 springdoc 비활성 |
| 11 | http로 쿠키 도청(배포 실수) | 설정 `application.yml` | **발견 → 수정** | prod에 `cookie-secure: true` 고정 |
| 12 | 리다이렉트 주소 조작 | 코드 `sendRedirect` 3곳 | 실패 | 설정값·고정 URL만 사용. 요청 입력 미사용 |
| 13 | 일반 회원으로 관리자 API 호출(권한 상승) | 테스트 `userIsForbiddenFromAdminPaths` | 실패 | `/api/v1/admin/**` → `hasRole(ADMIN)` 경로 규칙. 컨트롤러 역할 검사(`SafetyRequests.adminId`)와 겹벽 |

## 2. 다중 인스턴스 검증

증명할 명제: **요청이 어느 서버로 가든 같은 세션으로 동작** — 발급·조회·사용·폐기가 각각 다른 인스턴스에서 일어나도 결과 동일. 로드밸런서가 요청을 아무 서버로나 보내는 상황과 같은 조건.

### 구성 — 서버 4대, DB 1개

```
curl / 브라우저 ──(같은 BILLIM_SESSION 쿠키)──▶ :8080 · :18080 · :28080 · :38080
                                                        └── 모두 같은 MySQL의 auth_sessions 참조
```

기동: `./gradlew bootRun --args='--server.port=<포트>'` (실행 중인 compose MySQL에 자동 연결)

### 시나리오 — 단계마다 다른 인스턴스 사용

| 단계 | 인스턴스 | 확인 내용 | 결과 |
| --- | --- | --- | --- |
| ① 발급 | :18080 | `GET /auth/csrf` → `Set-Cookie` + `auth_sessions` 1행 증가 | 통과 (19→20행) |
| ② 조회 | :28080, :8080 | 같은 쿠키 제시 → `Set-Cookie` 없이 기존 세션 인식 | 통과 (각 0건) |
| ③ 사용 | :28080 → :38080 | :28080이 발급한 CSRF 토큰을 :38080의 POST에 사용 | 통과 — `CSRF_INVALID`(403) 아닌 `UNAUTHENTICATED`(401) |
| ④ 폐기 | :38080 | `POST /auth/logout` → 204 + 만료 쿠키 | 통과 |
| ⑤ 전파 | :18080 | 폐기된 쿠키 재제시 → 재사용 거부, 새 세션 발급 | 통과 (새 `Set-Cookie`) |
| ⑥ 로그인 | :8080 → :18080 | 카카오 로그인 후 같은 브라우저로 `/members/me` | 통과 (200, 동일 회원) |

- ③이 세션 공유의 직접 증거 — 토큰 검증이 쿠키·토큰 모두 DB 대조로 이루어지며, 발급 서버와 검증 서버가 달라도 통과
- ⑤가 운영상 핵심 — **한 서버의 로그아웃이 즉시 전 서버에 반영.** 제재·차단도 같은 경로라 동일하게 즉시 적용
- ⑥만 2대 수행 (카카오 로그인은 자동화 불가, 브라우저 수동 확인)
- :8080은 직전 빌드, 나머지는 최신 빌드 — **버전 혼재 상태에서도 세션 호환** (롤링 배포 가능)

### 재현 명령

```bash
curl -c jar.txt localhost:18080/api/v1/auth/csrf                  # ① 발급
curl -b jar.txt -D - localhost:28080/api/v1/auth/csrf             # ② Set-Cookie 없으면 공유 성공
curl -b jar.txt -X POST -H "X-CSRF-TOKEN: <②의 csrfToken>" \
     localhost:38080/api/v1/auth/logout                           # ③④ 사용 + 폐기 (204)
curl -b jar.txt -D - localhost:18080/api/v1/auth/csrf             # ⑤ 새 Set-Cookie면 폐기 전파 확인
```

### 한계

- 사진 저장(`LocalMediaStorage`)은 인스턴스 로컬 디스크 — 다중 인스턴스 미대응. 공유 저장소(EFS) 전환 필요
- ~~정리 배치는 인스턴스마다 중복 실행~~ — 한 인스턴스만 실행하도록 해소, 7절 참고

## 3. 관측 지표 노출 (2026.10.19)

`/actuator/prometheus`를 열되 서비스 포트로는 나가지 않게 한 기록.\
여는 이유 — 성능 측정의 서버 지표 수집(Prometheus·Grafana)이 이 경로를 사용, [성능 측정 양식](../performance/성능%20측정%20양식.md) 참고.

| 항목 | 값 |
| --- | --- |
| 관리 포트 | `MANAGEMENT_PORT` 기본 9090 |
| 바인딩 | `MANAGEMENT_ADDRESS` 기본 `127.0.0.1` — 같은 호스트만 수집 |
| 노출 엔드포인트 | `health`, `info`, `prometheus` (`metrics` 등 제외) |

- 포트 분리만으로는 부족 — 분리된 포트에도 Spring Security가 적용되어 `prometheus`는 401. `PUBLIC_PATHS` 허용이 함께 필요.
- 허용 후 서비스 포트(8080) 확인 — `/actuator/prometheus` **404**. 액추에이터가 관리 포트에만 붙어서, 허용 목록에 넣어도 8080에서는 열리지 않음.
- 노출 범위 확인 — 9090에서도 `metrics`는 401. `exposure.include`에 적지 않은 엔드포인트는 허용 목록과 무관하게 막힘.
- 허용을 테스트로 고정 — `prometheusIsNotBlockedBySecurity`가 보안 통과(서비스 포트 404)를 상시 재검증. `PUBLIC_PATHS`에서 빠지면 401로 즉시 실패.

```bash
# 재현
curl -o /dev/null -w "%{http_code}\n" localhost:8080/actuator/prometheus   # 404
curl -o /dev/null -w "%{http_code}\n" localhost:9090/actuator/prometheus   # 200
lsof -nP -iTCP:9090 -sTCP:LISTEN                                            # 127.0.0.1:9090
```

### 남은 결정

- 원격 수집 시 `MANAGEMENT_ADDRESS=0.0.0.0` + 보안 그룹으로 소스 제한. 공개 금지 — 지표에 요청 경로·DB 상태 포함.
- 2대 운영(11.06~) 전환 시 인스턴스 간 9090만 허용.

## 6. 별도 출처 채팅 연결권 (2026.10.27)

Netlify 로그인 쿠키를 별도 WSS 도메인으로 복사하지 않고, 기존 쿠키·CSRF로 방별 일회용 연결권 발급. JWT 도입·세션 쿠키 속성 변경 없음. 기본 비활성화, 배포 설정은 [채팅 WebSocket 배포](../deploy/채팅%20WebSocket%20배포.md) 참조.

| 항목 | 로컬 자동 검증 |
| --- | --- |
| 연결권 재사용·동시 사용 | 실제 Redis GETDEL, 두 서비스의 동시 소비 중 한 건만 성공 |
| 만료·다른 방 변조·세션 폐기 | 소비 거부 |
| 허용 출처 이외 연결 | 실제 Spring 보안 필터·WebSocket 서버에서 403. 유효 연결권 미소비 |
| 쿠키 없는 정상 연결 | 허용 Origin·연결권으로 연결 성공, 재사용·연결권 없음은 401 |
| 연결권 API | 로그인 주체와 현재 세션 사용, CSRF 없는 발급 차단, 성공 응답 no-store |
| Redis 미사용 환경 | 연결권 기능 기본 비활성화. 기존 동일 출처 쿠키 연결 유지 |

CloudFront 경로 제한 함수의 404 및 EC2 원본의 401 응답 확인 완료. 실제 운영 WebSocket Upgrade·연결권 인증 검증 미완료. 공개 HTTP 원본 사용 금지, ticket 쿼리의 접근 로그·오류 추적 도구 수집 제외 필요. Redis 장애 시 연결권 발급·소비는 503으로 차단. 운영 코드 배포 후 인증된 연결 점검 및 배포 상태 갱신 필요.

## 7. 정리 배치 단일 실행 (2026.10.29)

만료 세션·OAuth 시도 정리(`ExpiredAuthCleaner`, 매일 04:00)를 여러 인스턴스 중 한 대만 실행하도록 변경. 잠금은 ShedLock + MySQL `shedlock` 테이블.

### 문제

- 2대 운영(11.06~)부터 같은 cron이 인스턴스마다 동시에 발화
- 삭제 결과는 같으나 두 인스턴스가 같은 만료 행 범위를 묶음 단위로 동시 삭제 — 행 잠금 대기와 삭제 부하가 두 배
- `auth_sessions`는 모든 인증 요청이 조회하는 테이블이라 정리 중 부하가 응답시간에 직결 (성능 측정 5절에서 묶음 분할로 줄인 비용)

성능 측정 5절은 "실제 문제는 동시 실행이 아니라 단일 실행의 크기"로 결론. 서버 1대 측정이며 크기 문제는 묶음 분할로 대응 완료. 이 절은 그다음 단계인 2대 운영의 중복 실행 대응. 동시 실행의 비용 자체는 미측정 — 결과가 같은 작업의 중복이라 측정 없이 제거해도 잃는 것이 없다고 판단.

### 선택지

| 선택지 | 장점 | 제외 이유 |
| --- | --- | --- |
| 현행 유지 | 변경 없음 | 위 경합·부하가 인스턴스 수에 비례 |
| 한 대만 스케줄 활성(환경 변수) | 코드 변경 최소 | 해당 인스턴스 종료·교체 시 정리 중단. 인스턴스별 설정 분기 |
| MySQL `GET_LOCK` | 의존성·테이블 없음 | 잠금이 커넥션 단위 — 정리 동안 풀 커넥션 1개 추가 점유. 종료 직후 재실행 방지를 직접 구현 |
| Redis 잠금 | 빠른 획득·자동 만료 | Redis 미사용 구성 존재(채팅 연결권 기본 비활성) — 정리가 Redis 가용성에 종속 |
| Quartz 클러스터 | 작업 이력·재시도 | 테이블 11개·스케줄러 교체. 작업 1건에 과함 |
| **ShedLock + MySQL** ⭐ | 테이블 1개·어노테이션 1개. 최소·최대 유지 시간 내장 | — |

### 결정

- **저장소는 MySQL** — 모든 구성에 이미 존재하는 의존성. 잠금 시각은 DB 시계 기준(`usingDbTime`)으로 서버 간 시계 차이 배제
- **최소 유지 1분** — 인스턴스 간 cron 발화 시각이 어긋나면 먼저 끝난 정리 직후 다른 인스턴스가 재실행. 정리 시간과 무관하게 1분간 잠금 유지
- **최대 유지 30분** — 최장 실행(테이블당 묶음 1,000회 상한, 묶음 사이 50ms 대기 — 수 분 수준)보다 충분히 길게. 정리 중 인스턴스가 종료되어도 다음 주기 전 잠금 해제
- **적용 범위는 만료 정리만** — 대여 요청 만료는 요청별 최신 상태 재검사, 사건 전달은 `FOR UPDATE SKIP LOCKED` 선점으로 이미 중복 처리를 막고 있음

### 검증

`ExpiredAuthCleanerLockTest` — 실제 MySQL(Testcontainers)에서 다른 인스턴스의 잠금 행으로 재현.

| 항목 | 결과 |
| --- | --- |
| 다른 인스턴스가 잠금 보유 중 | 정리 건너뜀 |
| 정리 직후 재호출 | 최소 유지 시간 내 재실행 없음 |
| 잠금 유지 시각 경과(종료된 인스턴스) | 다시 정리 |

### 재검토 조건

- 잠금이 필요한 배치가 늘어나 작업 이력·재시도가 필요해질 때 — Quartz 등 스케줄러 재검토
- 정리 실행 시간이 최대 유지 시간(30분)에 근접할 때 — 묶음 크기·최대 유지 시간 조정

| 한도 | csrf 분당 30, 로그인 시작·관리자 로그인 합산 분당 10 | 경로별 개별 한도 — 제공자를 바꿔 가며 한도 배가 |

| 클라이언트 식별 | Netlify `x-nf-client-connection-ip`, 프록시 서명(`x-nf-sign`) 검증 시에만 신뢰 | 아래 |
| 추적 상한 | 주소 5만 개. 초과 시 새 주소 차단 | 상한 없음 — 메모리 고갈 |

클라이언트 식별 선택지:

| 선택지 | 문제 |
| --- | --- |
| 접속 주소만 | 운영은 Netlify 프록시 뒤 — 모든 사용자가 Netlify IP로 묶여 한도 공유 |
| `X-Forwarded-For` | `ForwardedHeaderFilter`가 하위 필터에서 헤더 제거. 앞쪽 값은 클라이언트가 임의 지정 가능 |
| 프록시 IP 헤더 그대로 신뢰 | EC2 8080이 외부에 열려 있어 직접 호출로 헤더 위조 |
| **프록시 IP 헤더 + 서명 검증** ⭐ | — HS256 JWS, Netlify와 같은 비밀값. 서명이 없거나 틀리면 접속 주소로 계수. 비밀값 미설정 시 헤더 전부 불신 |

### 발견한 우회와 수정 (10.29)

- 증상: 서명 없는 직접 호출이 `X-Forwarded-For` 값만 바꿔 보내면 제한 무력화. 같은 주소 70회 중 차단 0회
- 원인: `ForwardedHeaderFilter`가 헤더 제거와 함께 `getRemoteAddr()`도 `X-Forwarded-For` 값으로 교체. 서명 불일치 시 쓰는 "접속 주소"가 결국 요청자가 보낸 값
- 미발견 이유: 운영 확인 절차는 `x-nf-client-connection-ip` 위조만 시험. 테스트 컨텍스트는 `forward-headers-strategy`가 prod 프로필 전용이라 해당 필터 없이 실행
- 수정: 래퍼를 벗겨 원본 요청의 접속 주소 사용 — 필터 등록 순서와 무관하게 유지
- 고정: `AuthSecurityTest`에 운영과 같은 `forward-headers-strategy=framework` 지정. 수정 전 코드에서 실패·수정 후 통과 확인

### 관리자 로그인 계정 단위 잠금 (10.29)

- 문제: IP별 제한은 주소를 바꿔 가는 대입을 막지 못함. 관리자 계정은 팀 공용 1개라 탈취 시 피해 범위가 전체. 시도마다 bcrypt(cost 12) 연산이 t3.small CPU 소모
- 결정: IP가 아닌 계정 기준 집계. 15분 안에 5회 실패 시 15분 잠금, 잠금 중에는 올바른 자격증명도 429 · bcrypt 대조 생략
- 감수: 공격자가 잠금을 반복 유발하면 정상 관리자도 대기. 대입 성공보다 작은 비용으로 판단. 카운터는 인스턴스 메모리라 서버 대수만큼 허용 실패 수 증가
- 기록: 실패·잠금 시 경고 로그 — 응답의 `requestId`로 요청 추적
- 설정: `ADMIN_LOGIN_MAX_FAILURES`·`ADMIN_LOGIN_LOCK_DURATION`

## 10. 프론트 보안 헤더 (2026.10.29)

Netlify가 내보내는 화면 응답에 보안 헤더가 없어 다른 사이트의 iframe 삽입이 가능했던 상태. 로그인 쿠키가 실린 채로 화면을 겹쳐 버튼 클릭을 유도하는 클릭재킹 경로 — 다른 기기 로그아웃·물건 삭제 등. API 응답은 Spring Security 기본 헤더 적용 확인.

### 결정

| 헤더 | 값 | 적용 |
| --- | --- | --- |
| CSP | `frame-ancestors 'none'` · `base-uri 'self'` · `object-src 'none'` · `form-action 'self'` | 강제 |
| `X-Frame-Options` | `DENY` — `frame-ancestors` 미지원 브라우저용 | 강제 |
| `X-Content-Type-Options` | `nosniff` | 강제 |
| `Referrer-Policy` | `strict-origin-when-cross-origin` — 외부로는 출처만 전달. 카카오 지도 키의 도메인 검증은 출처로 성립 | 강제 |
| `Permissions-Policy` | 위치는 자기 출처만(동네 인증), 카메라·마이크·결제·USB 차단 | 강제 |
| 출처 제한 CSP | 스크립트·이미지·연결을 자기 출처·카카오 지도·채팅 WSS로 제한 | **Report-Only** |

출처 제한을 바로 강제하지 않은 이유: 카카오 지도 SDK가 앱 키 검증 후 하위 도메인에서 스크립트·타일을 추가로 불러오며, 키 없이 그 목록을 확정할 수 없음. 잘못 강제하면 지도 화면 중단.

### 강제 전환 절차

1. 배포 후 지도·채팅·사진 업로드·로그인 화면을 사용하며 브라우저 콘솔의 `[Report Only]` 위반 확인
2. 위반 출처가 정상 기능이면 `netlify.toml` Report-Only 값에 추가
3. 위반이 없으면 Report-Only 값을 `Content-Security-Policy`로 옮겨 강제

### 확인

```bash
curl -sI https://billim.netlify.app/ | grep -iE "content-security|x-frame|nosniff|referrer|permissions"
```

## 11. API 진입점 단일화 (2026.10.29)

### 문제

- Netlify → EC2 구간이 평문 HTTP(`http://<EC2>:8080`) — 세션 쿠키·CSRF 토큰·관리자 비밀번호가 인터넷 구간을 암호화 없이 통과
- 8080이 `0.0.0.0/0`에 열려 있어 Netlify를 거치지 않는 직접 호출 가능 — 프록시 헤더 처리·요청 제한의 전제 우회

### 선택지

| 선택지 | 월 비용 | 판단 |
| --- | --- | --- |
| ALB + ACM 인증서 | ~$18 + 도메인 | 도메인 필요. 확장 시점에 재검토 |
| EC2에 인증서(Caddy 등) | 도메인 | 도메인 필요, 8080 대신 443 개방 — 직접 호출 경로 유지 |
| **CloudFront + VPC 원본** ⭐ | $0 (무료 구간) | 채팅 WSS가 같은 방식으로 운영 중. 원본 구간이 AWS 사설망이라 EC2 공개 포트 불필요 |

### 결정

- Netlify → CloudFront(HTTPS) → VPC 원본(사설망) → EC2. API 전용 배포를 새로 생성, 채팅 배포(D 도메인)는 변경 없음
- 8080 `0.0.0.0/0` 규칙 삭제 — EC2는 CloudFront VPC 원본 보안 그룹에서만 접근
- 남는 공개 경로(CloudFront 주소 직접 호출)는 백엔드가 차단 — `/api/**`에 Netlify 서명(`x-nf-sign`) 필수, 없으면 403. `/ws/chat`은 일회용 연결권 인증이라 대상 밖
- 서명 강제는 옵트인(`REQUIRE_PROXY_SIGNATURE`, 기본 꺼짐) — 배포가 재시작만 하고 상태 확인·롤백이 없어, 머지만으로 전 요청 거부가 일어나지 않게 함. 켰는데 비밀값이 없으면 기동 거부

### 적용 순서

1. 백엔드 배포(서명 강제 꺼진 상태) — 동작 변화 없음
2. API용 CloudFront 생성 — 원본: 기존 VPC 원본(EC2 8080, 콘솔에서 선택 불가 시 같은 인스턴스로 VPC 원본 추가 생성) · 뷰어 HTTPS 전용 · 허용 메서드 전체 · 캐시 정책 `CachingDisabled` · 원본 요청 정책 `AllViewerExceptHostHeader`(쿠키·헤더·쿼리 전달)
3. `netlify.toml` 프록시 대상을 `https://<API용 CloudFront 주소>/api/:splat`로 변경 후 배포 — 로그인·사진 업로드·채팅 연결권 발급 확인
4. EC2 `.env.prod`에 `REQUIRE_PROXY_SIGNATURE=true` 추가 후 재시작 — CloudFront 주소 직접 호출 403, Netlify 경유 정상 확인
5. 보안 그룹에서 8080 `0.0.0.0/0` 규칙 삭제

되돌리기: 4는 환경 변수 제거 후 재시작, 3은 `netlify.toml` 이전 값으로 재배포. 5를 되돌리기 전에는 3 이전으로 복귀 불가.

### 영향

- 운영 서버 직접 측정(성능 2차)은 서명 헤더 필요 — `docs/performance/tools/auth/nf_sign.py`로 생성해 k6 `NF_SIGN`에 전달
- 비밀값 미설정 시 요청 제한이 접속 주소(CloudFront 원본 측 주소)로 계수 — 4단계 전 `PROXY_SIGNATURE_SECRET` 설정 확인

### 검증

`ProxySignatureFilterTest` — 서명 통과·누락·위조·만료, API 밖 경로 제외, 기본 꺼짐, 비밀값 누락 시 기동 거부, 요청 제한보다 먼저 실행
