AWS 배포 계획과 비용·일정.

- **다중 인스턴스로 확장 가능한 구조** — 세션을 DB에 둬 인스턴스를 늘려도 로그인이 유지됨. 로컬 4대 교차 테스트로 검증 완료([보안 점검](../security/인증%20검증%20및%20보안%20점검.md) §2). 2차 배포 후 실제 2대로 전환
- **관측 가능한 운영** — SLO(가용성 99.5%, 500ms 이내 응답 95%)를 정하고 운영 기간 동안 준수 여부를 지표로 확인 (§6)

## 2. 구성

**현재 (1대)**

```
브라우저 → billim.netlify.app (프론트 + /api 프록시) → CloudFront(API) → EC2 1대 → RDS
브라우저 → CloudFront(채팅 WSS) ─────────────────────────────────────┘
```

**2대 전환 후 (11.12~)**

```
브라우저 → billim.netlify.app → CloudFront(API·채팅) → 내부 ALB → EC2 #1·#2 → RDS + EFS(사진)
                                                                 └ 모니터링 EC2가 지표 수집
```

| 구성 | 선택 | 역할 | 상태 |
| --- | --- | --- | --- |
| 앱 | EC2 (t3.small) | 애플리케이션 | 1대 운영 → **11.11 2대** |
| DB | RDS (MySQL) | 관리형 · 자동 백업 | 운영 |
| HTTPS·프록시 | Netlify | 공개 HTTPS 종단, `/api/*` 프록시 | 운영 |
| 진입점 | CloudFront + VPC 원본 | EC2 직접 접근 차단, 사설망으로 전달 | 운영 |
| 로드밸런서 | 내부 ALB | 헬스체크 · 인스턴스 분산 | **11.12 전환** |
| 미디어 | EFS | 사진을 인스턴스 수명과 분리 · 다중 인스턴스 공유 | **운영** (11.05 전환, §5) |
| 모니터링 | EC2 (t3.medium) | Prometheus · Grafana · 알림 | **운영** (11.05~, §6) |

**2대 전환 방식**

- 2차 배포는 1대로 진행, 이후 2대로 전환 — 코드 확인과 인프라 변경을 분리해 문제 발생 시 원인 구분
- 전환은 CloudFront 원본을 EC2에서 ALB로 바꾸는 한 번 — 세션이 DB에 있어 로그인 유지. 문제 시 원본을 1번 서버로 되돌려 즉시 1대 구성 복귀
- CD는 2대에 한 대씩 순차 배포 — 배포 중에도 한 대가 요청 처리
- 커넥션 풀은 서버당 25 — 운영 `max_connections` 61 기준([성능 측정](../performance/이지은-인증회원.md) §10)

**단일 오리진으로 묶은 이유**

- Netlify가 `/api/*`를 백엔드로 프록시(`netlify.toml` rewrite) → 브라우저엔 주소가 하나 → 세션 쿠키가 퍼스트파티. **아이폰 Safari의 서드파티 쿠키 차단을 피하려는 선택**이고, 결과적으로 도메인·인증서도 불필요
- 카카오 `redirect-uri`는 netlify 주소로 명시 → 프록시 Host 처리와 무관하게 콜백이 같은 오리진으로 복귀. 2차 배포 전 아이폰 포함 로그인 E2E로 확인

- 작업일(월·화·수·목·토) 기준. 11.09 이후 코드 고정 — 운영 중 수정은 장애 대응과 2대 전환 설정(CD·Redis·관리 포트)만
- 10.12 구축부터 11.23 삭제까지 **계속 가동** — 중간 중단 없이 11.23 일괄 삭제
- **1차 측정 범위 축소** — 1차 측정 시점에 대여 요청·동네 인증이 미완성이라 핵심 흐름 재현 불가, 운영 DB에 데이터 없음. 부하·경합 측정은 2차 재측정으로 이관하고 1차는 **환경 기준선**(로컬 대비 운영 응답시간 배수)만 기록. [측정 양식](../performance/성능%20측정%20양식.md)
- **2차 재측정** — 운영 영향이 없도록 RDS 스냅샷 복제 환경에서 측정. 1차와 비교하는 값은 **같은 단일 인스턴스 경로**(ALB 거치지 않고 인스턴스 직접 호출), 2대 효과는 ALB 경유로 별도 측정. 환경·공통 조건·시간대 배정은 인프라 담당, 시나리오 실행·기록은 각 도메인 담당

Netlify 경로는 일반 HTTP API 전용. `/ws/chat`의 실시간 연결은 별도 WSS 진입점과 일회용 연결권으로 연결하도록 코드 준비. 운영 WSS 진입점 적용 전까지 3초 REST 재조회로 메시지 갱신. [채팅 WebSocket 배포](채팅%20WebSocket%20배포.md)의 적용 순서·검증·복구 절차 참조.

**채팅 전달 구성**

- 로컬에서는 `CHAT_REDIS_ENABLED=false`(기본값)로 같은 서버의 WebSocket에 직접 전달한다. 운영 `prod` 프로필은 Redis 컨테이너를 먼저 준비한 뒤 기본적으로 `true`로 기동한다. 운영에서도 `CHAT_REDIS_ENABLED=false`로 되돌릴 수 있다.
- 여러 백엔드로 확장할 때는 모든 백엔드에 `CHAT_REDIS_ENABLED=true`와 동일한 비공개 `REDIS_URL`을 설정한다. Redis는 메시지 본문이 아닌 커밋 신호를 전파하며 MySQL이 메시지 원본이다.
- GitHub Actions 배포는 `backend/compose.redis.prod.yaml`을 EC2에 복사하고 Redis가 정상 기동한 뒤 JAR을 교체한다. EC2에 Docker Compose가 없거나 Redis가 준비되지 않으면 JAR 교체 전에 배포가 실패해 기존 백엔드가 유지된다. 여러 서버에서 Redis를 끄면 교차 서버 전달은 DB 재확인 주기에 의존한다.

**기존 EC2에서 Redis 컨테이너 사용**

1. 배포 전에 EC2의 사용 가능 메모리와 Docker Compose 설치 여부를 확인한다. 현재 t3.small에는 백엔드도 함께 실행되므로 Redis 기동 전후 메모리를 비교한다.
2. 배포 후 `/home/ubuntu/BILLIM/backend/compose.redis.prod.yaml`이 있는지 확인한다. 현재 파일은 Redis 신호만 처리하므로 영속화를 끄고, 호스트의 `127.0.0.1:6379`에만 연결한다. 외부 보안 그룹에 6379를 열지 않는다.
3. 배포가 Redis를 자동으로 시작한다. EC2에서 `docker compose -f /home/ubuntu/BILLIM/backend/compose.redis.prod.yaml exec -T redis redis-cli ping`의 `PONG`을 확인한다.
4. `systemctl cat billim`으로 실제 운영 환경 변수 공급 방식을 확인한다. `prod` 프로필에서는 `CHAT_REDIS_ENABLED`가 없으면 `true`, `REDIS_URL`이 없으면 `redis://127.0.0.1:6379`를 사용한다. 기존 운영 환경에 `CHAT_REDIS_ENABLED=false`가 지정돼 있다면 제거하거나 `true`로 바꿔야 한다.
5. 재부팅 시에도 Docker와 Redis가 백엔드보다 먼저 준비되도록 `billim` 서비스의 시작 순서를 점검한다. 채팅 전송·다른 브라우저 수신·재연결을 확인한다. 문제가 있으면 `CHAT_REDIS_ENABLED=false`로 되돌려 백엔드를 재시작한다. Redis가 없는 상태에서 `true`로 기동하면 애플리케이션은 시작하지 못한다.

백엔드를 ECS 등으로 옮길 때는 Redis를 백엔드 복제본마다 만들지 않고 공유 서비스로 분리한다. 모든 백엔드의 `REDIS_URL`을 같은 사설 주소로 바꾸며, 현재 Compose 파일의 로컬 호스트 바인딩을 다중 서버 설정으로 그대로 사용하지 않는다.

**2대 전환 시 Redis — 1번 서버 Redis 공유**

Redis는 서버 간 "새 메시지" 신호 전달용. 메시지 원본은 MySQL. 상대가 다른 서버에 연결돼 있으면 Redis 없이는 DB 재확인 주기(2초)만큼 늦게 도착한다.

| | A. 1번 서버 Redis 공유 ⭐ | B. ElastiCache |
| --- | --- | --- |
| 추가 비용 | 없음 | ~$8 (`cache.t4g.micro`, 13일) |
| 작업량 | 바인딩·보안 그룹·`REDIS_URL` 변경 | 클러스터 생성·서브넷 그룹·연결 |
| 1번 서버 장애 시 | 채팅은 2초 재확인으로 계속 동작 | 영향 없음 |

- A 선택 — 신호만 다뤄 유실돼도 DB 재확인으로 복구된다. 운영 기간 2주에 관리형 서비스를 추가할 이득이 작다
- 1번 서버 Redis는 사설 IP에만 바인딩하고 6379는 2번 서버 보안 그룹만 허용. 외부 공개 금지
- 두 서버 `REDIS_URL`을 1번 서버 사설 주소로 통일
- 제약: Redis 활성 상태로는 Redis 없이 기동 불가. 1번 서버 장애 중 2번 서버를 재기동해야 하면 `CHAT_REDIS_ENABLED=false`로 기동

## 5. 미디어 공유 — 2차 배포 전 EFS 이전

사진이 EC2 루트 볼륨에 저장되고 있다. 루트 볼륨은 인스턴스 종료 시 함께 삭제되므로(실측: `DeleteOnTermination=true`) 인스턴스를 교체하면 DB 데이터는 남고 사진만 유실되고, 인스턴스를 늘리면 한쪽에 올린 사진을 다른 쪽이 못 찾는다. **확장 여부와 무관하게 2차 배포 전(11.05) EFS로 이전한다.**

| | EBS 데이터 볼륨 | S3 전환 | EFS ⭐ |
| --- | --- | --- | --- |
| 월 비용(20GB) | ~$1.8 | ~$0.5 + 요청 과금 | ~$6.6 (사용량 과금) |
| 코드 변경 | 없음 | 저장소 구현 교체 | 없음 |
| 다중 인스턴스 | 불가 | 가능 | 가능 |

- 모든 인스턴스가 같은 EFS를 `MEDIA_STORAGE_PATH`로 마운트 — **애플리케이션 코드 변경 없음**
- 전환 시 EFS는 기존 경로 위가 아닌 별도 경로에 마운트 — 기존 경로 위에 마운트하면 사진이 가려져 DB 기록만 남음. 사진 복사·검증 후 `MEDIA_STORAGE_PATH` 변경
- EBS 데이터 볼륨 분리는 검토 후 제외 — 수명 분리는 되지만 공유가 안 되고, EFS가 2차 배포 전 확정이라 중간에 거치면 마운트·복사·경로 변경을 두 번 하게 됨
- S3는 다중 인스턴스 공유가 가능하지만 도메인 제약(외부 스토리지 금지, 아래 검토 항목)에 걸리고 `LocalMediaStorage` 구현 교체도 필요 — 제외

**검토 항목**

- 저장 방식은 **Standard** — One Zone은 반값이지만 한 AZ 전용에 생성 후 변경 불가라, 2대를 AZ 분산하는 확장 계획과 충돌
- 사진 저장은 도메인 제약상 서버 영속 볼륨만 허용(`MediaStorage` — S3 등 외부 스토리지 금지). EFS는 마운트된 파일시스템이라 이 제약 안에서 유실 문제를 해결

**모니터링 서버**

- **모니터링 전용 EC2 분리** — 앱 서버 메모리 2GiB에 백엔드·Redis 적재 중. 같은 서버에 두면 메모리 부족 위험, 측정값에 수집 부하 혼입
- **t3.medium** — Prometheus·Grafana에 로그 수집(Loki) 추가 여지. 로그 수집은 앱 서버 여유 메모리 확인 후 결정
- 운영 앱 서버(1대 → 2대)와 2차 재측정 복제 환경을 같은 Grafana에서 관찰 — 11.05부터 두어 2대 전환 전후 비교
- 지표 보관은 삭제일(11.23)까지 전체
- 외부 공개 금지 — 지표에 요청 경로·DB 상태 포함 ([보안 점검](../security/인증%20검증%20및%20보안%20점검.md) §3). 모니터링 EC2 인바운드 없음
- CPU 크레딧 standard 모드 — 초과 사용 과금 차단. 수집·표시만 해 성능 저하 영향 없음
- 알림은 운영 환경만. 5xx·p95 알림은 5분간 요청 30건 이상일 때만 판정 — 저트래픽에서 1~2건으로 값이 튀는 오탐 방지

**측정 시 유의**

- 액추에이터 전체가 관리 포트로 옮겨감 — 헬스체크도 9090. ALB **헬스체크 대상은 9090**, 보안 그룹에서 ALB만 허용
- t3 계열은 CPU 크레딧이 떨어지면 성능이 깎여 측정값이 틀어짐 — 측정 전후로 CloudWatch `CPUCreditBalance` 함께 기록

## 7. 도입 검토

> EBS(Elastic Block Store, EC2용 디스크)는 이름이 비슷한 Elastic Beanstalk(배포 플랫폼)과 함께 검토했다. 
> EBS 데이터 볼륨 결론은 §5.

| 항목 | 결정 | 적용 시 비용(월) | 근거 |
| --- | --- | --- | --- |
| Elastic Beanstalk | 미적용 | ~$18 (ALB) | 배포 자동화·헬스체크·환경 변수 관리 모두 기존 구성(GitHub Actions CD + systemd)이 수행 중. 전환하면 고정 IP·Redis 컨테이너·systemd 재이식 비용만 발생 |
| Jenkins | 미적용 | ~$19 (전용 EC2) | GitHub Actions가 같은 역할을 무료 한도 내에서 수행 중. t3.small은 메모리 여유가 없어 동거 불가. 학습 목적은 로컬 Docker(`jenkins/jenkins:lts`)로 충분 |
| ECS (Fargate) | 미적용 | ~$51 (EC2 대체분 제외) | 컨테이너 자동 교체·확장은 서버 1대 규모에서 쓸 일 없음. 2차 배포(11.10) 직전 CD·진입점·Redis 동시 변경은 위험 |
| 분산 추적 (Tempo) | 미적용 | 모니터링 서버에 포함 | 병목 위치 확인에 가장 강력하나 앱 의존성·설정 추가 필요. 11.09 코드 고정 직전이라 위험 |

확장이 필요해지는 시점의 선택지도 Beanstalk이 아니라 ALB + EC2 증설 또는 ECS다.

**ECS 전환 시 변경점**

> ECS는 AWS의 컨테이너 실행·관리 서비스, Fargate는 서버 관리 없이 컨테이너만 실행하는 방식.

| 항목 | 현재 | ECS (Fargate) |
| --- | --- | --- |
| 실행 | EC2 jar + systemd | 컨테이너 (`Dockerfile` 있음) |
| 배포 | S3 jar + SSM 교체 | ECR 이미지 + 서비스 갱신 |
| 진입점 | CloudFront → EC2 | CloudFront → ALB → 컨테이너 |
| Redis | 같은 EC2 컨테이너 | 별도 컨테이너 |
| 사진 | EFS | EFS (그대로) |
| 비용(월) | ~$19 | ~$70 (컨테이너 41 + ALB 18 + Redis 10) |

- ALB는 컨테이너 IP가 교체 때마다 바뀌어 필요. 비용 증가의 주원인
- 서버 2대 이상 확장 시 재검토. 비용을 줄이려면 기존 EC2에서 컨테이너를 실행하는 ECS on EC2 — ALB 없이 현재 진입점 유지

## 8. 롤링 배포와 공존 불가 마이그레이션

배포는 한 대씩 교체하고 나머지가 요청을 처리한다(`deploy.yml`). Flyway는 앱 기동 때 돌기 때문에 **먼저 올라간 새 서버가 마이그레이션을 적용한 뒤에도 다른 서버는 구 코드로 돈다.** 그 사이 구 코드가 새 스키마에 쓰기를 시도한다.

- **조회만 바뀌는 마이그레이션은 안전하다** — 인덱스 추가, nullable 컬럼 추가, 생성 컬럼.
- **구 코드가 쓰는 값을 거부하는 제약은 안전하지 않다.** 그 구간에 해당 쓰기가 실패한다.

판단 기준: *구 코드가 이 테이블에 INSERT·UPDATE하는 값이 새 제약을 통과하는가.*

### V23 (저장 동네 2개) — 공존 불가

| 구 코드 동작 | V23 적용 후 |
| --- | --- |
| 위치 인증 (E_011) | **실패** — `active_slot` 없이 ACTIVE 삽입 → CHECK 위반 |
| 동네 변경 | **실패** — `status='LEFT'`로 바꾸며 슬롯을 비우지 않음 → CHECK 위반 |
| 조회 전부 | 정상 |

- 영향 범위는 **동네 인증·변경뿐**이다. 한 대 교체되는 수 분 동안만이고 나머지 기능은 멀쩡하다.
- 그래서 **한 번에 올린다**(팀 결정). 선택지는 둘이었다.
  1. 두 대를 같이 내리고 올려 공존 구간을 없앤다 — 수 분 전체 중단
  2. 롤링 그대로 두고 그 구간의 동네 인증 실패를 감수한다 — 다른 기능은 정상
- 쪼개는 방법도 있었다 — V23에서 컬럼·백필·UNIQUE만 올리고(구 코드와 공존 가능), 다음 배포에서 CHECK를 붙이는 2단계. 운영 기간이 2주라 배포 횟수를 늘리는 쪽을 택하지 않았다.
- 참고로 **V22는 운이 좋았다.** 유니크만 걸었고 구 코드가 어차피 ACTIVE를 하나만 만들어 위반할 일이 없었다. 제약을 추가할 때마다 위 기준으로 따로 판단해야 한다.

### 적용 전 확인 (V23 리허설 결과)

운영과 같은 구조·규모(회원 1,001 / 소속 1,004)의 복사본에 적용해 확인했다. 소요 1초 미만.

- ACTIVE 소속 1,001건 전부 `active_slot = 1`, LEFT 3건 전부 `NULL`
- 현재 동네가 빈 회원 3명 → 백필로 0명
- UNIQUE·CHECK 생성, 제약 위반 행 0

기존 데이터에는 영향이 없다. 제약을 추가하는 마이그레이션은 **적용 전에 같은 방식으로 리허설한다** — 운영 테이블을 다른 스키마로 복사해 돌려 보면 위반 행을 미리 찾을 수 있다.
