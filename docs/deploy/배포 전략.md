# 배포 전략

> 버전 : v0.1.2\
> 수정일 : 2026.10.26

AWS 배포 계획과 비용·일정.

## 1. 목표

- **최소 1주 서비스 운영** — 라이브 11.08~, 발표 11.21까지 유지
- **다중 인스턴스로 확장 가능한 구조** — 세션을 DB에 둬 인스턴스를 늘려도 로그인이 유지됨. 로컬 4대 교차 테스트로 검증 완료([보안 점검](../security/인증%20검증%20및%20보안%20점검.md) §2)

## 2. 구성

**구축 완료**

```
브라우저 → billim.netlify.app (Netlify: 프론트 + /api 프록시) → EC2 1대 → RDS
```

**확장 시 (미확정)**

```
브라우저 → billim.netlify.app → ALB → EC2 #1·#2 → RDS + EFS(사진 공유)
```

| 구성 | 선택 | 역할 | 상태 |
| --- | --- | --- | --- |
| 앱 | EC2 (t3.small) | 애플리케이션 | 1대 구축 |
| DB | RDS (MySQL) | 관리형 · 자동 백업 | 구축 |
| HTTPS·프록시 | Netlify | 공개 HTTPS 종단, `/api/*` 프록시 | 구축 |
| 로드밸런서 | ALB | 헬스체크 · 인스턴스 분산 | **확장 시** |
| 미디어 | EFS | 사진을 여러 인스턴스가 공유 | **확장 시** |

> 확장 판단은 1차 측정 결과와 남은 비용을 보고 결정. 1대로도 발표까지 운영 가능.

**단일 오리진으로 묶은 이유**

- Netlify가 `/api/*`를 백엔드로 프록시(`netlify.toml` rewrite) → 브라우저엔 주소가 하나 → 세션 쿠키가 퍼스트파티. **아이폰 Safari의 서드파티 쿠키 차단을 피하려는 선택**이고, 결과적으로 도메인·인증서도 불필요
- 카카오 `redirect-uri`는 netlify 주소로 명시 → 프록시 Host 처리와 무관하게 콜백이 같은 오리진으로 복귀. 라이브 전 아이폰 포함 로그인 E2E로 확인

- **1차 측정 범위 축소 (10.19 판단)** — 대여 요청·동네 인증 미완성으로 핵심 흐름 재현 불가, 운영 DB에 데이터 없음. 부하·경합 측정은 2차로 이관하고 1차는 **환경 기준선**(로컬 대비 운영 응답시간 배수)만 기록. [측정 양식](../performance/성능%20측정%20양식.md)

**채팅 전달 구성 (10.26)**

- 현재 EC2 한 대에서는 `CHAT_REDIS_ENABLED=false`(기본값). 같은 서버의 WebSocket으로 직접 전달하고 DB 재확인으로 전달 공백을 복구한다. Redis 서버와 `REDIS_URL` 설정은 필요 없다.
- 여러 백엔드로 확장할 때는 모든 백엔드에 `CHAT_REDIS_ENABLED=true`와 동일한 비공개 `REDIS_URL`을 설정한다. Redis는 메시지 본문이 아닌 커밋 신호를 전파하며 MySQL이 메시지 원본이다.
- GitHub Actions 배포는 JAR을 교체하고 `backend/compose.redis.prod.yaml`을 EC2에 복사한다. Redis 컨테이너 시작과 환경 변수 전환은 별도 운영 작업이다. 이 설정 없이 여러 서버를 운영하면 교차 서버 전달이 DB 재확인 주기에 의존한다.

**기존 EC2에서 Redis 컨테이너 사용**

1. EC2의 사용 가능 메모리와 Docker Compose 설치 여부를 확인한다. 현재 t3.small에는 백엔드도 함께 실행되므로 Redis 기동 전후 메모리를 비교한다.
2. 배포 후 `/home/ubuntu/BILLIM/backend/compose.redis.prod.yaml`이 있는지 확인한다. 현재 파일은 Redis 신호만 처리하므로 영속화를 끄고, 호스트의 `127.0.0.1:6379`에만 연결한다. 외부 보안 그룹에 6379를 열지 않는다.
3. EC2에서 `cd /home/ubuntu/BILLIM/backend` 후 `docker compose -f compose.redis.prod.yaml up -d --wait`를 실행한다. `docker compose -f compose.redis.prod.yaml exec -T redis redis-cli ping`의 `PONG`을 확인한다.
4. `systemctl cat billim`으로 실제 운영 환경 변수 공급 방식을 확인한 뒤 `CHAT_REDIS_ENABLED=true`, `REDIS_URL=redis://127.0.0.1:6379`을 설정한다. Redis가 준비된 뒤 백엔드를 재시작한다. Redis가 없는 상태에서 활성화하면 현재 애플리케이션은 기동하지 못한다.
5. 재부팅 시에도 Docker와 Redis가 백엔드보다 먼저 준비되도록 `billim` 서비스의 시작 순서를 점검한다. 채팅 전송·다른 브라우저 수신·재연결을 확인한다. 문제가 있으면 `CHAT_REDIS_ENABLED=false`로 되돌려 백엔드를 재시작한다.

백엔드를 ECS 등으로 옮길 때는 Redis를 백엔드 복제본마다 만들지 않고 공유 서비스로 분리한다. 모든 백엔드의 `REDIS_URL`을 같은 사설 주소로 바꾸며, 현재 Compose 파일의 로컬 호스트 바인딩을 다중 서버 설정으로 그대로 사용하지 않는다.

## 5. 미디어 공유

인스턴스를 늘리면 사진 공유가 필수 — 로컬 디스크면 한쪽에 올린 사진을 다른 쪽이 못 찾아 이미지가 깨짐.

- **EFS 우선** — 모든 인스턴스가 같은 EFS를 `MEDIA_STORAGE_PATH`로. **애플리케이션 코드 변경 없음**
- S3는 더 정석이지만 `LocalMediaStorage` 구현 변경 필요 — 트래픽 증가 시 2차 이후 검토

## 6. 관측·측정

| 구성 | 선택 | 도입 | 비고 |
| --- | --- | --- | --- |
| 지표 노출 | Actuator `/actuator/prometheus` | 1차 | 관리 포트 9090, `127.0.0.1` 바인딩 |
| 부하 생성 | k6 (외부 실행) | 1차 | [측정 양식](../performance/성능%20측정%20양식.md)·스크립트 |
| 지표 수집·저장 | Prometheus | **2차** | |
| 대시보드 | Grafana | **2차** | |

- **같은 EC2에 Prometheus·Grafana 적재 — 추가 과금 없음.** 별도 인스턴스는 월 ~2.6만이고 11.23 삭제 예정이라 제외
- t3.small 메모리 2GiB — 지표 보관은 7일만. 더 길게 두면 디스크·메모리가 부족
- 액추에이터 전체가 관리 포트로 옮겨감 — 헬스체크도 9090. ALB를 붙이면 **헬스체크 대상을 9090으로** 두고 보안 그룹에서 ALB만 허용
- 인스턴스를 늘리면 Prometheus가 각 서버의 9090을 수집 → **보안 그룹에서 인스턴스 간만 허용.** 외부 공개 금지 — 지표에 요청 경로·DB 상태 포함 ([보안 점검](../security/인증%20검증%20및%20보안%20점검.md) §3)
- t3 계열은 CPU 크레딧이 떨어지면 성능이 깎여 측정값이 틀어짐 — 측정 전후로 CloudWatch `CPUCreditBalance` 함께 기록
