# 시스템 구조

> 버전 : v0.1.0\
> 수정일 : 2026.11.11

서버 구성·상태 위치·장애 영향·사용 기술의 역할 정리. 배포 절차는 [배포 전략](배포%20전략.md), 리소스 값은 AWS 배포 가이드.

## 1. 전체 구성

2대 전환(11.12) 이후 기준.

```
브라우저 ─ https ─▶ Netlify (프론트 + /api 프록시, 요청 서명)
                      └─▶ CloudFront ─ VPC 원본 ─▶ 내부 ALB ─┬─▶ EC2 #1 (Spring Boot jar) + Redis 컨테이너
브라우저 ─ wss ──▶ CloudFront(채팅) ──────────────────────────┘    EC2 #2 (Spring Boot jar)
                                                                    │
                                                    RDS MySQL ◀─────┤ (공유 원본 데이터)
                                                    EFS ◀───────────┘ (공유 사진)
모니터링 EC2 (Prometheus · Grafana) ─ 관리 포트 9090 수집 ─▶ EC2 #1·#2
```

| 계층 | 구성 | 대수 | 비고 |
| --- | --- | --- | --- |
| 진입 | Netlify · CloudFront | 관리형 | 공개 HTTPS 종단. EC2는 외부 직접 접근 불가 |
| 분산 | 내부 ALB | 1 | 헬스체크 9090 `/actuator/health` |
| 애플리케이션 | EC2 t3.small | 2 | 같은 jar. 서버별 차이는 환경 변수뿐 |
| 데이터 | RDS db.t3.micro | 1 | 모든 업무 데이터의 원본 |
| 파일 | EFS | 관리형 | 2a·2c 마운트 대상 |
| 신호 | Redis 7.4 (1번 서버 컨테이너) | 1 | 채팅 신호·입장권 전용. 영속화 끔 |

## 2. 모놀리식 선택

**단일 Spring Boot 애플리케이션 + 도메인 패키지 분리** (모듈러 모놀리스).

| 도메인 패키지 | 담당 영역 |
| --- | --- |
| `member` | 인증·회원 |
| `community` | 동네·인증 |
| `item` | 물건·검색 |
| `rental` | 대여·약속 |
| `chat` · `notification` | 채팅·알림 |
| `safety` | 신고·차단·운영 |

**MSA를 택하지 않은 이유**

- **판정이 도메인을 가로지름** — 이웃 프로필 1건에 동네 소속·거래 이력·차단 여부 판정(쿼리 8건, [인증·회원 측정](../performance/이지은-인증회원.md) §2). 서비스로 나누면 요청당 서비스 간 호출 3회
- **트랜잭션 경계** — 대여 요청 저장과 사건(outbox) 기록이 한 커밋(`RentalRequestEffects`). 분리 시 분산 트랜잭션 또는 보상 처리 필요
- **운영 규모** — 서버 1~2대, 예산 20만 원. 서비스별 배포·진입점·관측 비용이 기능 개발 시간을 잠식
- **인증 비용** — 서비스 간 인증(JWT 등)이 추가로 필요. 현재는 세션 1회 조회로 끝남 ([인증 방식 결정](../security/인증%20방식%20결정.md))

**분리를 대비한 경계**

- 도메인 간 읽기는 **창구 인터페이스만** 사용 — `CommunityMembershipQuery` · `BlockQuery` · `RentalPartyQuery`. 다른 도메인 저장소 직접 참조 금지
- 도메인 간 후속 처리는 **사건 테이블(outbox)** 경유 — 알림이 대여·채팅 코드를 직접 호출하지 않음
- 분리 시 창구 인터페이스가 API 호출로, outbox가 메시지 큐로 바뀌는 지점

## 3. 상태 위치

서버가 요청 처리에 필요한 상태를 들고 있는지 여부. 2대 운영의 전제.

| 상태 | 저장 위치 | 2대 운영 시 | 서버 장애 시 |
| --- | --- | --- | --- |
| 로그인 세션 · CSRF 토큰 | MySQL `auth_sessions` | 어느 서버든 처리 | 유지 |
| OAuth state | MySQL `oauth_login_attempts` | 로그인 시작·콜백이 다른 서버여도 성공 | 유지 |
| 업무 데이터 · 채팅 메시지 원본 | MySQL | 공유 | 유지 |
| 사진 | EFS | 공유 | 유지 |
| 배치 실행 잠금 | MySQL `shedlock` | 한 서버만 실행 | 잠금 만료 후 다른 서버가 실행 |
| 채팅 실시간 신호 | Redis Pub/Sub | 서버 간 전파 | 신호 유실 — DB 재확인으로 복구 (§4) |
| 채팅 연결 입장권 | Redis (30초 내 1회 소비) | 공유 | 발급 불가 (§4) |
| WebSocket 연결 | 서버 메모리 | 연결된 서버에 고정 | 끊김 — 재접속 후 기록 조회 |
| 인증 요청 제한 계수 | 서버 메모리 | 서버별 계수 — 한도가 대수만큼 증가 | 초기화 |
| 관리자 로그인 실패 잠금 | 서버 메모리 | 서버별 계수 | 초기화 |

**결론: 요청 처리는 무상태.** 고정 세션(sticky) 불필요, 어느 서버가 내려가도 로그인 유지.

- 서버 메모리 상태는 **유실·서버별 계수를 허용하는 것만** — 요청 제한·잠금은 대입 공격 억제 목적이라 2배 한도도 충분. 공유가 필요해지면 Redis로 이전
- 세션을 Redis가 아닌 MySQL에 둔 결과 — Redis 장애가 로그인에 영향 없음. 대가는 요청당 세션 조회 1건, 갱신은 5분 주기로 묶어 쓰기 제거 ([측정](../performance/이지은-인증회원.md) §3)

## 4. Redis 장애 대응

**원칙: Redis에는 잃어도 되는 것만.** 메시지 원본은 MySQL, Redis는 "새 메시지 있음" 신호와 30초짜리 입장권뿐. 그래서 영속화(`--save ""`, `appendonly no`)를 끄고 단일 노드로 운영.

| 상황 | 영향 | 대응 | 근거 |
| --- | --- | --- | --- |
| Redis 중단 — 연결된 채팅 | 실시간 신호 끊김 | 서버별 DB 재확인(2초 주기)이 누락 메시지 전달 | 로컬 시험: 31.95초 중단, 4건 전부 수신·누락 0 ([장애 복구](../reliability/채팅%20멀티%20인스턴스%20장애%20복구.md)) |
| Redis 중단 — 새 채팅 연결 | 입장권 발급·소비 503 | 프론트 대체 경로 여부 미확인 | `ChatSocketTicketService` — 미시험 |
| Redis 중단 — 로그인·조회·대여 | 없음 | — | 세션·데이터 모두 MySQL |
| Redis 복구 | 구독 자동 재연결 | — | 시험: 복구 후 구독자 2개, 다음 전송 32ms |
| 1번 서버 중단 | Redis도 함께 중단 + ALB가 1번 제외 | 2번 서버가 위 "Redis 중단" 상태로 서비스 | 단일 장애점 — 아래 한계 |
| Redis 없이 앱 재기동 | `CHAT_REDIS_ENABLED=true`면 기동 실패 | `CHAT_REDIS_ENABLED=false`로 기동 — 교차 서버 전달은 2초 재확인에 의존 | [배포 전략](배포%20전략.md) §4 |

**ElastiCache 대신 1번 서버 컨테이너** — 비교는 [배포 전략](배포%20전략.md) §4. 원본 데이터가 아니라 신호뿐이라 관리형의 복제·자동 장애 조치가 지키는 가치가 작음.

**한계와 후속**

- **헬스체크가 Redis 상태를 포함** — Spring Boot 기본값으로 Redis 연결 실패 시 `/actuator/health`가 DOWN. ALB가 두 서버를 모두 비정상 판정할 수 있음(ALB는 전체 비정상 시 전체로 전달하는 fail-open이라 완전 차단은 아님). 같은 이유로 Redis 장애 중 CD 배포는 헬스체크 대기에서 실패. 채팅 신호 하나 때문에 서비스 전체 상태가 흔들리는 구조 — 헬스체크에서 Redis 제외 검토 필요
- **Redis 장애 알림 없음** — Prometheus 수집 대상에 Redis 없음. 위 헬스체크 영향 외에는 감지 수단 없음
- 1번 서버 장애 시 Redis 동반 중단 — 2대 운영 기간(11.12~11.21) 한정으로 허용. 운영 연장 시 Redis를 별도 노드 또는 ElastiCache로 분리

## 5. 사용 기술과 역할

인프라·인증·공통 영역. 도메인 전용 기술은 각 도메인 문서.

| 기술 | 사용처 | 해결한 문제 | 근거 |

| Spring Security · OAuth2 Client | 카카오·네이버 로그인, 세션 쿠키 | 서버 측 즉시 로그아웃·세션 폐기 | [인증 방식 결정](../security/인증%20방식%20결정.md) |

| ShedLock (JDBC) | 만료 세션 정리 배치 | 2대에서 같은 배치 중복 실행 방지. 잠금 시각은 DB 시계 기준 | [보안 점검](../security/인증%20검증%20및%20보안%20점검.md) §7 |

| Prometheus · Grafana | 모니터링 전용 EC2 | 수집·대시보드·알림 4종 → 디스코드 | 저장소 `monitoring/` |

| GitHub Actions · OIDC · SSM | CD | 액세스 키·SSH 없이 배포. 2대 순차 교체 | [배포 전략](배포%20전략.md) §2 |

## 6. 감지 체계

| 단계 | 수단 | 잡는 것 |
| --- | --- | --- |
| 개발 중 | 요청당 SQL 수 집계 | N+1·불필요 쓰기 — 환경 무관 지표 |
| 개발 중 | `EXPLAIN` | 색인 미사용 전체 탐색 |
| 개발 중 | k6 + 초 단위 지표 | 평균에 묻히는 순간 급증 (정리 배치 사례 — [측정](../performance/이지은-인증회원.md) §5) |
| 개발 중 | 포화 곡선 + Hikari 활성·대기 | 자원 병목 위치 (풀 사례 — §6) |
| 운영 | Grafana 알림 | 수집 실패 · 5xx 1% · p95 500ms · 힙 90% |
| 운영 | SLO 대시보드 | 가용성 99.5% · 500ms 이내 95% · 에러 버짓 잔량 |

**미적용**

- 로그 수집(Loki) — 앱 서버 여유 메모리 확인 후 결정. 현재는 서버별 `journalctl` 직접 조회 — 2대에서는 두 서버를 따로 봐야 함
- 분산 추적(Tempo) — 코드 고정 직전 의존성 추가 위험 ([배포 전략](배포%20전략.md) §7)

## 7. 확장 순서

| 순서 | 대상 | 시점 | 이유 |
| --- | --- | --- | --- |
| 1 | Redis 분리 (ElastiCache 또는 전용 노드) | 운영 연장 시 | 1번 서버와 장애 동반 해소 |
| 2 | 요청 제한 계수 Redis 이전 | 서버 3대 이상 | 서버별 한도 증가 폭 확대 |
| 3 | RDS 등급 상향 | 서버 증설 시 | `max_connections` 61이 대수×풀 크기 상한 ([측정](../performance/이지은-인증회원.md) §10) |
| 4 | 채팅·알림 서비스 분리 | 동시 접속 증가 시 | 상주 연결이라 자원 패턴이 API와 다름. 진입점·Redis·outbox 경계가 이미 분리돼 첫 후보 |

ECS 전환 검토는 [배포 전략](배포%20전략.md) §7.
