## 0. 개선 흐름 요약

각 개선의 감지 → 가설 → 예측 → 조치 → 검증 경로. 상세는 괄호 안 절.

| 문제 | 감지 | 가설 | 예측과 근거 | 조치 | 결과 |
| --- | --- | --- | --- | --- | --- |
| 검색·지도·홈 7개 CASE p95 500ms 초과 (§2) | k6 11개 CASE 3회 중위값. 대상이 좁은 `neighbor`·`mine`은 13~19ms인데 동네 전체 대상 CASE만 느림. `home` ≈ `search-latest` | 동네 전체 대상 쿼리 중 **공통 비용**이 있다 | CASE별 실행 쿼리를 나눈 대응표(§3)에서 Q1이 8개 CASE 공통. Q1을 없애면 **Q1을 쓰는 8개만 비슷한 폭으로 줄고, 안 쓰는 3개는 그대로**일 것 | — | EXPLAIN ANALYZE로 Q1 340ms·101,600행 확인 (§3) |
| 차단 판정용 소유자 전체 조회 Q1 (§6) | Q1이 최신 20건 조회(0.03ms)의 1만 배. 차단 0건이어도 매번 실행 | 물건 쪽에서 "주인 전부"를 묻는 방향이 문제. 차단 쪽에서 "내 관계"만 물으면 물건 수와 무관 | 대안 비교: owner 인덱스 27ms vs 조회 방향 반전 0.02ms (차단 2만 건에서도 0.035ms) → 방향 반전 채택 | `BlockQuery.findBlockRelatedMemberIds` 추가, 소유자 전체 조회 삭제 | 통과 4 → 8개. 8개 CASE p50이 **331~507ms씩 같은 폭으로** 감소, 대조군 3개 변화 없음 → 예측과 일치 (§7) |
| 지도 집계 Q7 (§13) | 개선 1 후에도 p95 516ms | 인덱스에 `place_id`가 없어 행 읽기 + 임시 테이블 | 쿼리 단위 93 → 30ms. 단, 측정 편차(3회 폭 98ms)보다 작아 **p95로는 구분 안 될 수 있음** (§13) | 예정 | — |

**가설 검증 방식** — 한 번에 하나만 바꾸고 같은 데이터·VU·시간·CASE로 재측정. 차이가 3회 측정 폭(§7 편차)보다 클 때만 효과로 인정. 바꾼 쿼리를 쓰지 않는 CASE를 대조군으로 둬 환경 변동과 구분.

**예측 기록에 대해** — 개선 1은 대응표(§3)와 우선순위(§5)에 근거는 남겼지만 **수치 예측은 측정 전에 적지 않았다**. 다음 개선부터는 측정 전에 예측·근거·반증 조건을 먼저 기록하고 결과와 대조한다 (§13).

## 3. 병목 근거: EXPLAIN ANALYZE

> 아래 실행 시간은 **같은 시드 데이터**(`tools/item/item_seed.py`, 물건 102,000 · 대여 200,000)를 다른 환경(Linux · MySQL 8.0)에 재현해 측정한 값이다.
> 맥 Docker 환경과 절대값은 다르므로 **쿼리 간 비율과 실행 계획(읽은 행 수·사용 인덱스)**을 근거로 사용한다. 맥 환경 원본은 `docs/performance/raw/item-baseline-69cec64/explain.txt`.

| # | 쿼리 | 실행 시간 | 읽은 행 | 실행 계획 요약 |
| --- | --- | ---: | ---: | --- |
| Q1 | 차단 판정용 소유자 목록 `SELECT DISTINCT owner_id` | **340ms** | 101,600 | `idx_items_community_visibility_created` 범위 조회 후 **테이블 행 전부 읽음** (인덱스에 `owner_id` 없음) + 임시 테이블 중복 제거 |
| Q2 | 전체 건수 `COUNT(*)` | 24ms | 101,600 | 같은 인덱스만 읽음 (커버링) |
| Q3 | 최신순 20건 | 0.03ms | 20 | 같은 인덱스 역순, 20건에서 멈춤 |
| Q4 | 깊은 페이지 `OFFSET 20000` | 6ms | 20,020 | 인덱스만 읽을 때 기준. 실제 조회는 전체 컬럼이라 행 읽기가 추가됨 (추가 확인 필요) |
| Q5 | 키워드 건수 `title LIKE '%드릴%'` | 102ms | 101,600 | 인덱스로 동네 범위만 좁히고 **행마다 LIKE 필터** |
| Q6 | 기간 건수 (점유 대여·연체 `NOT EXISTS` 2개) | **757ms** | 101,600 | 물건 10만 행마다 대여 하위 쿼리 2개 확인 (`Nested loop antijoin`) |
| Q7 | 지도 장소별 집계 `GROUP BY place_id` | 98ms | 101,600 | 인덱스에 `place_id` 없음 → 행 읽기 + 임시 테이블 집계 |
| Q8 | 가까운 순 20건 `ORDER BY CASE place_id …` | 95ms | 101,600 | 계산된 값으로 정렬하므로 **10만 행 정렬** 후 20건 |

## 5. 병목 우선순위와 2차 개선 계획

원칙: 근거가 큰 순서로 고치고, 하나씩 적용한 뒤 같은 조건으로 재측정해 효과를 분리한다.

| 순위 | 병목 | 개선 방향 (2차 개발에서 확정) | 영향 CASE | 확인 지표 |
| --- | --- | --- | --- | --- |
| 1 (**적용 완료**, 7번) | Q1 차단 판정용 소유자 전체 조회 | 조회 방향을 뒤집는다. 조회 회원과 차단 관계인 회원 ID(보통 0~수 명)만 먼저 조회해 그 소유자만 제외. 차단이 없으면 조건 생략 | search 6종 · map · home (8개) | 요청당 SQL에서 Q1 제거, p95 |
| 2 | Q6 기간 검색 `NOT EXISTS` | 실행 계획 상세 분석 후 인덱스·조건 순서 조정 | search-period (기간 지정 map 포함) | Q6 실행 시간, p95 |
| 3 | Q5 키워드 `LIKE` | FULLTEXT(ngram) 인덱스 검토 | search-keyword | Q5 실행 시간, p95 |
| 4 | Q7 지도 집계 | `(community_id, visibility, place_id)` 인덱스로 인덱스만 읽기 | map | Q7 실행 계획, p95 |
| 5 | Q8 가까운 순 정렬 | 1~4 적용 후 재측정 결과로 결정 | search-nearest | p95 |

- 목표: 모든 CASE **p95 < 500ms · 오류율 < 1%** (1번 성공 기준). 개선 전후는 같은 데이터·VU·시간·CASE로 비교한다.
- 인덱스를 바꾸면 `docs/erd/도메인 및 DB 설계.md`, API 계약이 바뀌면 `docs/api/API 명세서.md`를 같은 PR에서 갱신한다.
- 1순위는 차단 데이터를 읽는 방식이 바뀌므로 차단 담당(노현섭)과 조회 창구를 협의한다. 현재 `BlockQuery`에는 "후보 중 차단된 회원 찾기"만 있고 "회원의 차단 관계 전체 목록"이 없다.

## 6. 개선 1: 차단 판정 방식 변경

| 항목 | 내용 |
| --- | --- |
| 문제 | 검색·지도·홈 요청마다 동네 공개 물건의 소유자 전체를 조회(Q1, 10만 행)한 뒤 차단 관계를 확인 |

| 결과 일치 | 차단 관계 회원의 물건 제외라는 결과는 같음. 기존 검색·차단 테스트 통과, 양방향 조회 DB 테스트 추가 |

## 11. 구조와 데이터 위치 (물건 도메인)

전체 구조는 [시스템 구조](../deploy/시스템%20구조.md) — 모듈러 모놀리스(단일 Spring Boot + 도메인 패키지), EC2 2대 + RDS + EFS. 여기서는 물건 도메인만 적는다.

| 데이터 | 저장 위치 | 2대 운영 시 | 비고 |
| --- | --- | --- | --- |
| 물건·이미지 연결·사진 메타데이터 | MySQL `items` · `item_images` · `media_files` | 어느 서버든 같은 결과 | 검색은 매 요청 DB 직접 조회. 캐시 없음 |
| 사진 파일(원본·썸네일) | EFS (`MEDIA_STORAGE_PATH`) | 한 서버에 올린 사진을 다른 서버가 읽음 | 루트 볼륨 유실 문제로 11.05 이전 ([배포 전략](../deploy/배포%20전략.md) §5) |
| 사진 정리 실행 잠금 | MySQL `shedlock` (`media-cleanup`) | 하루 1회, 한 서버만 실행 | `MediaCleanupJob` 새벽 4:30(KST) |
| 서버 메모리 상태 | 없음 | — | 물건 요청 처리는 무상태 |

**검색 결과를 캐시하지 않는 이유** — 결과가 조회자마다 다르고(차단 관계 제외), 대여 승인·반납·숨김으로 자주 바뀐다. 공유 캐시는 무효화 조건이 복잡해지고, 개선 1로 최신순이 60ms대가 돼 캐시가 필요한 근거도 사라졌다.

**다른 도메인을 읽는 방법과 MSA 분리 시 바뀌는 지점**

| 읽는 것 | 방법 | 분리했을 때 |
| --- | --- | --- |
| 차단 관계 | 창구 `BlockQuery` | API 호출 1회. 개선 1 전 방식이었다면 **소유자 10만 명 목록을 서비스 간에 보내야** 했다 — 이번 개선이 분리 비용도 줄였다 |
| 동네 소속 | 창구 `CommunityMembershipQuery` | API 호출 1회 |
| 동네·공용 장소 | 저장소 직접 참조 (`CommunityRepository` · `CommunityPlaceRepository`) | 경계 위반. 창구로 옮겨야 분리 가능 |
| 기간 검색의 대여 점유 | 검색 쿼리 안에서 `rentals` 테이블 `NOT EXISTS` 하위 쿼리 | **가장 분리하기 어려움.** 서비스가 나뉘면 한 SQL로 못 묶음 → 대여 쪽이 "기간에 점유된 물건 ID"를 주거나, 물건 쪽이 점유 기간 사본을 사건(outbox)으로 받아 들고 있어야 함 |

현재 규모(서버 2대·동네 단위 데이터)에서는 기간 검색을 한 SQL로 처리하는 것이 가장 빠르고 단순해서 모놀리스를 유지한다. 다음 개선(§13 기간 검색)도 이 구조 안에서 인덱스·조건 순서로 해결한다.

### 예측 1 — 지도 `(community_id, visibility, place_id)` 인덱스

| 항목 | 내용 |
| --- | --- |
| 예측 | `map` p95 약 516ms → **450~500ms**. 쿼리 단위 개선은 확실하지만 API p95 개선은 작다 |
| 근거 | EXPLAIN에서 Q7이 인덱스만 읽게 바뀌어 93 → 30ms(−63ms). 지도 요청에서 Q7이 차지하는 몫은 일부 |

| 판별 지표 | `map` p95 5회 범위, Q7 실행 계획(`Using index` 여부·읽은 행 수) |

## 16. 한계

- **차단 0건 시드** — 개선 1의 API 측정은 조회자 차단 관계가 없는 상태. 차단 2만 건은 쿼리 단위(0.035ms)로만 확인했고, 제외 목록이 길 때의 검색 p95는 미측정
- **부하 생성기·DB·서버가 같은 맥** — 조건 간 비교는 유효하지만 절대 수치는 이 환경 한정. 운영(EC2 t3.small + RDS)에서는 미측정
- **EXPLAIN은 다른 환경(Linux · MySQL 8.0)** — 같은 시드로 재현해 비율·실행 계획만 근거로 사용 (§3)
- **동네 1곳·물건 10만 건 쏠림** — 실제 동네별 분포가 아닌 최악 조건
- **요청당 SQL·서버 지표(CPU·Hikari 대기) 미수집** — 응답 시간이 흔들릴 때 쓸 대체 근거가 아직 없음 (§15)
