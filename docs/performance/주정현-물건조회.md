## 3. 병목 근거: EXPLAIN ANALYZE

> 아래 실행 시간은 **같은 시드 데이터**(`tools/item/item_seed.py`, 물건 102,000 · 대여 200,000)를 다른 환경(Linux · MySQL 8.0)에 재현해 측정한 값이다.
> 맥 Docker 환경과 절대값은 다르므로 **쿼리 간 비율과 실행 계획(읽은 행 수·사용 인덱스)**을 근거로 사용한다. 맥 환경 원본은 `docs/performance/raw/item-baseline-69cec64/explain.txt`.

| # | 쿼리 | 실행 시간 | 읽은 행 | 실행 계획 요약 |
| --- | --- | ---: | ---: | --- |
| Q1 | 차단 판정용 소유자 목록 `SELECT DISTINCT owner_id` | **340ms** | 101,600 | `idx_items_community_visibility_created` 범위 조회 후 **테이블 행 전부 읽음** (인덱스에 `owner_id` 없음) + 임시 테이블 중복 제거 |
| Q2 | 전체 건수 `COUNT(*)` | 24ms | 101,600 | 같은 인덱스만 읽음 (커버링) |
| Q3 | 최신순 20건 | 0.03ms | 20 | 같은 인덱스 역순, 20건에서 멈춤 |
| Q4 | 깊은 페이지 `OFFSET 20000` | 6ms | 20,020 | 인덱스만 읽을 때 기준. 실제 조회는 전체 컬럼이라 행 읽기가 추가됨 (추가 확인 필요) |
| Q5 | 키워드 건수 `title LIKE '%드릴%'` | 102ms | 101,600 | 인덱스로 동네 범위만 좁히고 **행마다 LIKE 필터** |
| Q6 | 기간 건수 (점유 대여·연체 `NOT EXISTS` 2개) | **757ms** | 101,600 | 물건 10만 행마다 대여 하위 쿼리 2개 확인 (`Nested loop antijoin`) |
| Q7 | 지도 장소별 집계 `GROUP BY place_id` | 98ms | 101,600 | 인덱스에 `place_id` 없음 → 행 읽기 + 임시 테이블 집계 |
| Q8 | 가까운 순 20건 `ORDER BY CASE place_id …` | 95ms | 101,600 | 계산된 값으로 정렬하므로 **10만 행 정렬** 후 20건 |

### 측정값과의 대응

| CASE | 요청 한 번에 실행되는 주요 쿼리 | 근거 |
| --- | --- | --- |
| search-latest | Q1 + Q2 + Q3 | Q1이 대부분. Q3 자체는 0.03ms |
| search-category | Q1 + 카테고리 건수 + 목록 | latest와 비슷한 수준 → 공통 비용 Q1이 지배적 |
| search-keyword | Q1 + Q5(건수) + Q5(목록) | latest 대비 약 +420ms |
| search-period | Q1 + Q6(건수) + Q6(목록) | 가장 느림 |
| search-nearest | Q1 + Q2 + Q8 | latest 대비 약 +450ms |
| search-deep-page | Q1 + Q2 + Q4 | latest 대비 약 +110ms |
| map | Q1 + Q7 | 검색과 같은 필터 사용 |
| home | 검색 최신순(Q1 + Q2 + Q3) + 동네·대여·알림 조회 | search-latest와 거의 같은 시간 → 검색 부분이 지배적 |

## 5. 병목 우선순위와 2차 개선 계획

원칙: 근거가 큰 순서로 고치고, 하나씩 적용한 뒤 같은 조건으로 재측정해 효과를 분리한다.

| 순위 | 병목 | 개선 방향 (2차 개발에서 확정) | 영향 CASE | 확인 지표 |
| --- | --- | --- | --- | --- |
| 1 (**적용 완료**, 7번) | Q1 차단 판정용 소유자 전체 조회 | 조회 방향을 뒤집는다. 조회 회원과 차단 관계인 회원 ID(보통 0~수 명)만 먼저 조회해 그 소유자만 제외. 차단이 없으면 조건 생략 | search 6종 · map · home (8개) | 요청당 SQL에서 Q1 제거, p95 |
| 2 | Q6 기간 검색 `NOT EXISTS` | 실행 계획 상세 분석 후 인덱스·조건 순서 조정 | search-period (기간 지정 map 포함) | Q6 실행 시간, p95 |
| 3 | Q5 키워드 `LIKE` | FULLTEXT(ngram) 인덱스 검토 | search-keyword | Q5 실행 시간, p95 |
| 4 | Q7 지도 집계 | `(community_id, visibility, place_id)` 인덱스로 인덱스만 읽기 | map | Q7 실행 계획, p95 |
| 5 | Q8 가까운 순 정렬 | 1~4 적용 후 재측정 결과로 결정 | search-nearest | p95 |

- 목표: 모든 CASE **p95 < 500ms · 오류율 < 1%** (1번 성공 기준). 개선 전후는 같은 데이터·VU·시간·CASE로 비교한다.
- 인덱스를 바꾸면 `docs/erd/도메인 및 DB 설계.md`, API 계약이 바뀌면 `docs/api/API 명세서.md`를 같은 PR에서 갱신한다.
- 1순위는 차단 데이터를 읽는 방식이 바뀌므로 차단 담당(노현섭)과 조회 창구를 협의한다. 현재 `BlockQuery`에는 "후보 중 차단된 회원 찾기"만 있고 "회원의 차단 관계 전체 목록"이 없다.

## 6. 개선 1: 차단 판정 방식 변경

| 항목 | 내용 |
| --- | --- |
| 문제 | 검색·지도·홈 요청마다 동네 공개 물건의 소유자 전체를 조회(Q1, 10만 행)한 뒤 차단 관계를 확인 |
| 근거 | Q1 340ms (최신순 20건 조회는 0.03ms). 차단 관계가 0건이어도 매번 실행 |
| 변경 | 조회 회원과 차단 관계(양방향)인 회원 ID만 먼저 조회해 그 소유자의 물건을 제외. 차단 쪽 `BlockQuery`에 `findBlockRelatedMemberIds` 공개 (저장소의 기존 쿼리 사용), 물건 쪽 소유자 전체 조회 삭제 |
| 쿼리 비교 | 소유자 전체 99~502ms → 차단 관계 조회 0.02ms. 차단 2만 건에서도 `index_merge`(두 인덱스 합침)로 본인 관계만 읽어 0.035ms |
| 결과 일치 | 차단 관계 회원의 물건 제외라는 결과는 같음. 기존 검색·차단 테스트 통과, 양방향 조회 DB 테스트 추가 |
| 코드 | `80f105a` |


## 9. 실행

```bash
cd BILLIM

cd backend
./gradlew bootJar --no-daemon
cd ..

docker compose -f docs/performance/tools/item/compose.yaml up -d --build mysql backend

# 데이터 생성: MySQL·마이그레이션 준비를 기다린 뒤 실행 (seed.py 없이도 동작)
# 이미 데이터가 있으면 다시 넣지 않고 세션·결과 파일만 갱신
python3 docs/performance/tools/item/item_seed.py

# 연결 확인 → CASE마다 워밍업 후 3회 측정 → 중위값 표까지 한 번에
bash docs/performance/tools/item/item_bench.sh

# 일부 CASE만 / 조건 변경
CASES="search-period map" bash docs/performance/tools/item/item_bench.sh
VUS=20 DURATION=60s bash docs/performance/tools/item/item_bench.sh
```

결과는 `docs/performance/tools/item/local/results/<날짜-시각>-<커밋>/`에 CASE별 원본과 `report.md`(중위값 표)로 남는다. `report.md` 표를 2번 표에 붙여 넣는다.

CASE 하나만 직접 실행할 때:

```bash
docker compose -f docs/performance/tools/item/compose.yaml run --rm \
  -e CASE=search-latest -e VUS=10 -e DURATION=30s \
  k6 run /scripts/item-read.js
```

CASE: `search-latest`, `search-keyword`, `search-category`, `search-period`, `search-nearest`, `search-deep-page`, `item-detail`, `mine`, `neighbor`, `map`, `home`

## 10. 종료·초기화

```bash
docker compose -f docs/performance/tools/item/compose.yaml down -v
rm -rf docs/performance/tools/item/local
```

`down -v`는 `billim-perf` 격리 DB 볼륨만 삭제한다. 개발 DB에는 실행하지 않는다.
