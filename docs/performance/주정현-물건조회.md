## 1. 조건

| 항목 | 값 |
| --- | --- |
| 측정일 · 담당 | 2026.10.21 · 주정현 |
| 구분 | 로컬 · 개선 전 |
| 서버 | macOS + Docker, 백엔드 1개(메모리 1GiB), MySQL 8.4 |
| 코드 | `69cec64` (측정 결과 폴더 이름에 자동 기록) |
| 데이터 | 같은 동네 회원 1,000명 + 조회 회원 1명 · 공개 물건 100,000건 · 내 물건 2,000건 · 장소 10곳 · 대표 이미지 100,000건 · 대여 200,000건 (승인 40% · 요청 대기 40% · 거절 20%, 승인 겹침 0건) |
| 대상 API | `GET /api/v1/items` 외 B파트 조회 API |
| 기준 부하 | 10 VU · 30초 · CASE마다 워밍업 10초 후 3회, 중위값 기록 |
| 성공 기준 | p95 < 500ms · 오류율 < 1% |

### 측정 시나리오

| CASE | API · 조건 | 확인 목적 |
| --- | --- | --- |
| `search-latest` | `GET /api/v1/items?sort=LATEST` | 기본 목록·페이지 count 비용 |
| `search-keyword` | `keyword=드릴` | `%LIKE%` 검색 비용 |
| `search-category` | `categoryId=1` | 복합 인덱스 적용 후보 비교 |

| `search-nearest` | `sort=NEAREST` | 장소별 거리 `CASE` 정렬 비용 |
| `search-deep-page` | `page=1000` | 깊은 `OFFSET` 비용 |
| `item-detail` | `GET /api/v1/items/{itemId}` | 상세 조립 비용 |

| `map` | `GET /api/v1/items/map` | 장소별 집계 비용 |

## 3. 측정 전 코드 가설

- 검색마다 같은 동네의 공개 물건 소유자 전체를 먼저 조회하고 해당 ID 목록으로 차단 관계를 조회한다. 소유자 수가 커지면 전처리 쿼리와 `IN` 절 비용이 증가할 가능성이 있다.
- 키워드는 `LIKE '%검색어%'`이므로 일반 B-Tree 인덱스를 사용하기 어렵다. `EXPLAIN ANALYZE`로 전체 스캔 여부를 확인한다.
- 기간 검색은 물건마다 점유 대여와 연체 대여 `NOT EXISTS`를 확인한다. 기존 `rentals(item_id, status, start_date, end_date)` 인덱스의 실제 실행 계획을 확인한다.
- 목록 응답 조립은 카테고리·대표 이미지·회원·장소·커뮤니티를 배치 조회한다. N+1은 피했지만 고정 쿼리 수와 응답 조립 비용을 측정한다.
- 지도 API는 필터에 맞는 전체 장소 집계를 만든 뒤 애플리케이션에서 범위 필터링한다. 장소나 물건 수 증가 시 DB 집계량이 커질 가능성이 있다.

측정 결과와 `EXPLAIN ANALYZE`를 확인하기 전에는 개선안을 확정하지 않는다.

## 4. 실행

```bash
cd BILLIM

cd backend
./gradlew bootJar --no-daemon
cd ..

docker compose -f docs/performance/tools/item/compose.yaml up -d --build mysql backend

# 데이터 생성: MySQL·마이그레이션 준비를 기다린 뒤 실행 (seed.py 없이도 동작)
# 이미 데이터가 있으면 다시 넣지 않고 세션·결과 파일만 갱신
python3 docs/performance/tools/item/item_seed.py

# 연결 확인 → CASE마다 워밍업 후 3회 측정 → 중위값 표까지 한 번에
bash docs/performance/tools/item/item_bench.sh

# 일부 CASE만 / 조건 변경
CASES="search-period map" bash docs/performance/tools/item/item_bench.sh
VUS=20 DURATION=60s bash docs/performance/tools/item/item_bench.sh
```

결과는 `docs/performance/tools/item/local/results/<날짜-시각>-<커밋>/`에 CASE별 원본과 `report.md`(중위값 표)로 남는다. `report.md` 표를 2번 표에 붙여 넣는다.

CASE 하나만 직접 실행할 때:

```bash
docker compose -f docs/performance/tools/item/compose.yaml run --rm \
  -e CASE=search-latest -e VUS=10 -e DURATION=30s \
  k6 run /scripts/item-read.js
```

CASE: `search-latest`, `search-keyword`, `search-category`, `search-period`, `search-nearest`, `search-deep-page`, `item-detail`, `mine`, `neighbor`, `map`, `home`

## 5. 종료·초기화

```bash
docker compose -f docs/performance/tools/item/compose.yaml down -v
rm -rf docs/performance/tools/item/local
```

`down -v`는 `billim-perf` 격리 DB 볼륨만 삭제한다. 개발 DB에는 실행하지 않는다.
