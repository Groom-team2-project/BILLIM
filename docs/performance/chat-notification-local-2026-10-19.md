# 채팅·알림 로컬 성능 측정 (2026-10-19)

> 버전: v0.1.3 · 수정일: 2026.10.21

## 문제

채팅 전송·WebSocket 전달의 응답성과 알림 조회·읽음·outbox 처리 속도에 대한 실측 기준이 없었다.

## 근거 및 환경

- 초기 측정 소스: `origin/develop` 기준 `5f4345f`에서 백엔드 JAR 생성. 아래의 연결 공백 수정 후 재측정은 별도 코드 버전이며, 수정 커밋 `bb3c291`을 포함한다. 초기·후속 결과를 같은 빌드의 연속 실행으로 해석하지 않는다.
- Windows Docker Desktop 29.8.2 / Compose 5.6.0 / k6 0.54.0 / MySQL 8.4 / Java 21. 단일 백엔드 컨테이너(메모리 상한 1GiB), 독립 `billim_perf` DB. 테스트 PC 사양과 Docker 전체 자원 한도는 측정하지 않았다.
- 별도 테스트 계정 16명, 채팅방 8개, 각 방 참여자 2명, 초기 알림 800건. 실제 로그인 세션 및 CSRF 검증을 통과하는 요청. SQL 상세 로그를 끈 `perf` 프로필.
- HTTP 및 WebSocket 테스트는 outbox worker를 끄고 실행했다. worker는 별도로 켜서 합성 사건을 측정했다.
- k6의 각 VU는 서로 다른 방에 배치했다. 0.2초 휴지 간격을 둔 부하이며, 한 방에 동시 전송이 집중되는 최악의 경우를 재현하지 않는다.

## 변경

`docs/performance/tools/chat-notification/`에 독립 Compose, 테스트 데이터 생성기, k6 시나리오, outbox 측정기를 추가했다. 운영 서버와 기존 개발 DB 설정은 변경하지 않았다.

## 한계 및 다음 측정

- 이 수치는 단일 PC, 단일 인스턴스, 최대 8 VU의 로컬 기준값이다. 배포 용량이나 동시 사용자 한계로 해석할 수 없다.
- WebSocket은 매 메시지마다 새 연결을 열었다. 실제 사용처럼 장시간 연결 유지 시의 메모리·전달 품질을 별도로 측정해야 한다.
- 8개 방에 부하를 분산했다. 한 방의 순번 할당 잠금 경합, 2계정 간 실시간 전달, 다중 인스턴스 전달은 측정하지 않았다.
- 알림 outbox 측정은 합성 사건 투입부터 처리까지다. 실제 대여·신고 API의 사건 발행과 알림 수신 전체 경로는 포함하지 않는다.
- WebSocket 첫 4 VU 실행의 미수신 4건은 재현 조건과 서버 로그를 추가로 추적할 필요가 있다.
- 배포 모니터링을 하려면 Prometheus 수집 대상의 인증·네트워크 접근, 보존 기간, 자원 비용, 계측 항목을 팀과 합의한 뒤 적용한다. 현재 `/actuator/prometheus`는 인증이 필요한 경로이며, 이번 작업은 이를 변경하지 않았다.

재현 명령과 초기화 방법은 `docs/performance/tools/chat-notification/README.md`에 있다.

WebSocket의 모든 HTTP 전송은 201이었다. 별도 `chat_delivery_failures` 지표를 추가해 수신 실패를 직접 판정한다. 32 VU 즉시 전송은 28/2,332건(1.20%), 128 VU·50ms 대기는 7/6,634건(0.11%)이 5초 안에 수신되지 않았다. 대기 시간을 늘린 실행에서는 재현되지 않아 연결 등록과 전송 간 타이밍 경합을 의심하지만, 원인은 확정하지 않았다. HTTP 전송 성공을 실시간 수신 성공으로 간주하면 안 된다.

한 방 집중 128 VU에서 처리량은 분산 시의 약 1/3로 낮아지고 p95는 약 18배 높아졌다. 동일 방의 `next_sequence` 잠금 경합과 일치하는 양상이지만, DB 잠금 대기 시간을 직접 계측한 결과는 아니다. 부하 증가 시 관찰한 백엔드 메모리는 약 570~644MiB/1GiB였고, CPU는 순간 최대 약 289%였다. Docker 전체 CPU/메모리 사용량과 장기간 추이는 수집하지 않았다.

Outbox worker는 재기동 직후 합성 사건 50건으로 준비한 뒤 500건을 투입했다. 500/500건 알림 생성, 완료 16.14초, 약 31.0건/s, 사건 생성부터 완료까지 p95 15.79초였다. 큐 적체가 늘면 후반 사건의 대기 시간이 커진다. 알림 처리량에 대한 운영 목표가 정해지면 배치 크기·폴링 간격·사건당 DB 작업을 함께 검토해야 한다.

이 측정은 순차 실행하여 DB 메시지 수가 점점 늘었고, VU 수에 맞춰 서로 다른 회원 수를 늘리지는 않았다. 단계별 수치는 동일 조건의 엄밀한 용량 비교가 아니라 병목 징후를 찾는 탐색 결과다. 특히 0.2초 휴지가 전체 요청률을 제한하므로 593건/s를 시스템 최대 처리량으로 해석하지 않는다.

## 실시간 미수신 원인 진단

기존 시험은 메시지마다 WebSocket을 다시 연결했다. 실제 화면처럼 VU마다 소켓 한 개를 유지하며 각 10건을 200ms 간격으로 보내는 시나리오를 추가했다. 64 VU에서는 640건 모두 수신, 전달 p95 97.09ms였다. 128 VU에서는 HTTP 전송 1,280건 모두 성공했으나 WebSocket에서 **첫 메시지 6/128건 미수신**, 이후 메시지 **0/1,152건 미수신**이었다. 수신 성공분의 전달 p95는 2.61초였다. 같은 조건의 재측정도 첫 메시지 **4/128건 미수신**, 이후 **0/1,152건 미수신**, 전달 p95 2.84초로 재현됐다. 테스트 기준에 첫 메시지 미수신율 1% 미만을 별도로 추가했고 재측정은 실패 판정됐다.

이 결과는 연결 시작 구간의 공백을 강하게 시사한다. 현재 서버는 `afterConnectionEstablished`에서 DB 권한 확인을 마친 뒤 `sessionByRoom`에 세션을 넣고, 브로드캐스트는 그 맵에 들어 있는 세션에만 보낸다. 브라우저의 연결 열림 통지와 서버의 맵 등록 완료 사이에 메시지가 커밋되면 이벤트를 놓칠 수 있다. 50~100ms 대기 시 미수신이 줄어든 결과와도 일치한다. 다만 서버의 실제 등록 시각과 미수신 메시지 ID를 함께 기록한 것은 아니므로 확정 원인은 아니다.

**기본 로직 수정안:** 핸드셰이크 때 방의 마지막 커밋 순번을 기록한다. 수신 권한 확인과 세션 등록을 마친 뒤 그 순번 이후의 메시지를 DB에서 페이지별로 조회해 같은 WebSocket 응답 형식으로 재전송한다. 등록 이후의 일반 브로드캐스트는 그대로 유지한다. 두 경로가 겹치면 중복 수신될 수 있으므로 기존 클라이언트의 메시지 ID 병합을 유지한다. 연결 시작 중간에 메시지를 커밋하는 회귀 테스트를 먼저 추가한다. 이 방식은 외부 WebSocket 메시지 형식을 바꾸지 않는다. 기존 프론트의 `afterSequence` 재조회는 안전망으로 유지한다.

**성능 후속 과제:** 128개 유지 연결에서 전달 p95 2.61초가 관찰됐다. 브로드캐스트는 수신 소켓마다 DB로 `canReceive`를 확인하고 동기식으로 전송한다. 수신자 수에 따라 인증 조회와 전송 대기 시간이 증가할 가능성이 있다. 서버 처리 시간·DB 쿼리 수·부하 발생기 사용량을 분리 계측한 뒤 인증 확인 주기와 배치/비동기 전달 방식을 검토한다. 권한 철회 지연에 영향을 주는 캐시 적용은 별도 보안 협의가 필요하다.

## 연결 공백 수정 후 재측정

핸드셰이크 때 방의 마지막 저장 순번을 기록하고, 권한 확인 및 소켓 등록 이후 그 사이의 메시지를 DB에서 조회해 재전달하도록 수정했다. 연결 중 저장된 메시지 재전달과 권한 철회 시 종료를 단위 테스트로 확인했다. 기존 WebSocket 메시지 형식은 그대로다.
수정 전 실행은 재전달 코드가 없는 빌드, 수정 후 실행은 `bb3c291`의 재전달 코드를 포함한 빌드다. 유지 연결 실행은 VU당 소켓 1개·메시지 10건, `open` 직후 첫 전송·이후 200ms 간격, 수신 대기 최대 5초다. 재측정 당시 전체 빌드 해시는 기록되지 않았으므로 `bb3c291` 자체에서 실행했다고 단정하지 않는다.

| 유지 연결 128 VU, 각 10건 | 첫 메시지 6/128건·재측정 4/128건 미수신, 전달 p95 2.61~2.84초 | 두 차례 모두 0/128건 미수신, 전체 각 1,280/1,280 수신, 전달 p95 1.41초·752ms | 측정 시점마다 부하 변동 존재 |
| 매번 새 연결, 연결 직후 전송 32 VU·20초 | 28/2,332건 미수신 | 0/2,959건 미수신, 전달 p95 19ms | 약 146.5건/s |

중복 전송 가능 구간은 기존 프론트의 메시지 ID 병합으로 처리한다. 저장 실패·서버 중단·다중 인스턴스 전달은 이 수정의 대상이 아니다. 변경 후 DB에 메시지가 더 쌓인 상태였고 동시 실행 여부도 달라, p95 차이 전부를 코드 수정 효과로 해석할 수 없다. 수신 누락 0건은 이 조건에서의 관측 결과이며 영구적인 무손실 보장은 아니다.

## 남은 성능 병목

128 VU를 한 방에 집중해 20초 전송한 결과 4,137건, 약 199.0건/s, HTTP p95 607ms, 오류 0건이었다. 실행 중 MySQL `performance_schema.data_lock_waits` 표본에서 대기 36개와 `chat_rooms` 레코드의 배타 잠금을 확인했다. 여러 방에 분산한 앞선 측정은 약 593건/s, p95 28.5ms였다. 측정 시점·DB 데이터량이 달라 엄밀한 전후 비교는 아니지만, 한 방의 순번 할당을 직렬화하는 잠금이 실제 병목이라는 근거다.

현재 전송 서비스는 `chat_rooms` 행의 쓰기 잠금을 획득한 뒤 중복 요청 조회, 물건·동네·차단·제재 정책 조회, 메시지 저장을 수행한다. 잠금 보유 구간을 줄이려면 정책 판정을 잠금 전으로 옮기는 방안을 검토할 수 있으나 권한 변경과 경합 시의 정합성을 함께 설계해야 한다. 방별 순번을 다른 방식으로 할당하거나 비동기 전달을 도입하는 변경은 데이터 정합성·아키텍처에 영향을 주므로 별도 계획과 팀 합의가 필요하다.

## 성능 개선 후보와 적용 기준

이번 단계에서는 성능 개선 코드를 적용하지 않는다. 다음 변경은 동일한 데이터 규모와 부하 조건에서 잠금 대기 시간, 전송·전달 p95, 처리량, 오류율을 변경 전후로 비교한다.

| 후보 | 해결하는 문제 | 적용 조건과 주의점 |
| --- | --- | --- |
| 전송 트랜잭션의 잠금 보유 구간 축소 | 한 방에 전송이 몰릴 때의 `chat_rooms` 행 잠금 대기 | **우선 검토**. 중복 조회와 정책 판정의 실행 시점을 분석하고, 잠금 밖으로 옮기는 권한 검사는 상태 변경 경합 시 재검증 기준을 먼저 정한다. 같은 방 동시 전송·중복 키·차단·제재 변경 테스트 필요. 새 기술 스택 불필요. |
| 전달 경로의 권한 조회·동기식 fan-out 분석 | 여러 WebSocket 연결을 가진 방의 전달 지연, HTTP 응답 대기 | 소켓별 DB 조회 수와 브로드캐스트 소요 시간을 별도 계측한 뒤 검토. 권한 캐시는 철회 반영 지연을 만들 수 있으므로 보안 협의 전 적용하지 않는다. |
| Redis Pub/Sub | **다중 백엔드 인스턴스** 사이의 실시간 이벤트 전파 | 실제 다중 인스턴스 운영 때 권장. 각 인스턴스가 방 이벤트를 구독해 자신이 보유한 소켓에 전달한다. 메시지 원본은 MySQL에 보관하고 재연결·누락은 기존 `afterSequence` 조회로 복구한다. Pub/Sub 자체는 구독자가 없을 때 이벤트를 보관하지 않으므로 단독 무손실 수단으로 쓰지 않는다. 방 순번 잠금은 해결하지 못한다. |
| Redis Streams 또는 Kafka | 저장 후 이벤트 전달을 지속적으로 재시도할 별도 요구 | 단순 1:1 채팅의 현재 측정만으로는 도입 근거 부족. DB와 브로커의 이중 쓰기 문제를 막는 outbox 설계, 소비자 중복 처리, 운영 비용을 먼저 정해야 한다. Kafka의 파티션별 순서 보장도 현재 MySQL의 방별 순번 할당 잠금을 제거하지 않는다. |

Redis 공식 문서는 [Pub/Sub의 at-most-once 특성](https://redis.io/docs/latest/develop/use-cases/pub-sub/)과 [Streams의 소비자 그룹](https://redis.io/docs/latest/develop/data-types/compare-data-types/)을 구분한다. [Kafka 공식 문서](https://kafka.apache.org/documentation/)는 같은 키의 이벤트가 같은 파티션에서 순서대로 읽힌다고 설명한다. 따라서 현재 병목에 바로 Redis나 Kafka를 도입하지 않고, 다중 인스턴스 전달 또는 지속 가능한 이벤트 재처리 요구가 확인될 때 해당 기술을 선택한다.

다음 성능 개선의 착수 조건: 방별 부하 목표와 허용 p95 합의, 잠금·fan-out 단계별 계측, 권한 판정·API 계약·아키텍처 변경에 대한 저장소 규칙상 사전 승인. 배포 모니터링 도구 적용은 수집 범위·접근 권한·보존 기간을 팀과 합의한 뒤 별도 작업으로 진행한다.
