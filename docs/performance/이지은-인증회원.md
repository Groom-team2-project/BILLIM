## 2. 요청당 쿼리

환경과 무관하게 재현되는 값. SQL 로그에서 요청 스레드만 집계.

| API | 쿼리 수 |
| --- | --- |
| 내 프로필 | 5건 |
| 이웃 프로필 | **9건 → 8건** (회원 조회 병합 후. 8건 실측, 9건은 `findById` 2회→`findAllById` 1회 차이로 유도) |

**8건 구성**

- 조회 — `auth_sessions`+`members` 1(조인, 세션 복원) · `members` 1(조회자·대상 일괄)
- 권한 판정 — `community_memberships`+`communities` 2(대상 소속·동네 이름) · `community_memberships` 1(조회자 소속) · `rentals` 1(거래 당사자) · `blocks` 2(양방향·단방향)

### 인증 고정 비용 — 전 도메인 공통

인증은 모든 요청이 거치므로 세션 조회가 전 API의 바닥값. 도메인별 엔드포인트 11개를 같은 방식으로 집계 — 아래는 200을 받은 10개(대여 목록은 파라미터 누락으로 400, 인증 1건만 확인).

| 엔드포인트 | 전체 | 인증 | 세션 UPDATE |
| --- | --- | --- | --- |
| 알림 미읽음·목록 · 채팅 미읽음·방 목록 · 카테고리 | 2 | 1 | 0 |
| 동네 목록 | 3 | 1 | 0 |
| 내 프로필 | 5 | 1 | 0 |
| 이웃 프로필 | 8 | 1 | 0 |
| 물건 목록 | 10 | 1 | 0 |
| 홈 | 20 | 1 | 0 |

**세션 조회 1건은 11개 전부 동일.** 가벼운 엔드포인트에서는 전체 쿼리의 절반.

`session-touch-interval=0s`로 바꾸면 **11개 전부 인증 2건 · 세션 UPDATE 1건** — 제품의 모든 읽기 요청이 같은 행에 쓰기를 유발. 3절의 처리량 1.55배 차이가 회원 조회만의 문제가 아닌 이유.

## 3. 회원 조회 병합과 세션 갱신 주기

**회원 조회 병합** — 조회자와 대상을 각각 읽어 회원 테이블을 두 번 왕복. `findAllById`로 묶어 **9건 → 8건**(병합 전 9건은 유도값).

**세션 유휴 시각 갱신 주기** — 모든 인증 요청이 세션 행을 읽는데, 유휴 판정용 `last_seen_at`을 매번 쓰면 같은 행에 쓰기가 몰림. 현재 설정은 5분 주기로 묶어 쓰기를 건너뜀(`session-touch-interval`).

두 설정을 같은 회차에서 연속 측정. 3회 중위값, 괄호는 최소~최대.

| 설정 | 요청당 UPDATE | 처리량 | 평균 | 이웃 프로필 p95 |
| --- | --- | --- | --- | --- |
| 0s | 1건 (매 요청) | 455.1 /s (453~479) | 18.60 ms | 32.51 ms |
| **5m** | **없음** | **704.0 /s** (679~745) | **12.00 ms** | **20.73 ms** |

**처리량 1.55배, 평균 응답시간 1.55배.** 실패율은 양쪽 0% (누적 45.7만 요청).

설정 내 편차는 처리량 5.6~9.8%, p95 17.5~25.0%. 설정 간 차이 55%가 편차보다 커 노이즈로 설명되지 않음.

**재현과 p99** — `5m`을 별도 회차로 3회 더 측정. 처리량 659.8 /s · p95 21.60 ms · **p99 39.02 ms**(25.8~39.3). 회차 간 차이 6.7~13%로 회차 내 편차와 같은 수준.

대가는 유휴 만료 판정이 최대 5분 늦어지는 것.

## 4. 동시 수정 — 쓰기 경합

이름 수정의 충돌 방어는 두 겹. `expectedVersion` 선검사로 오래된 화면의 수정을 거르고, 엔티티 `@Version`으로 커밋 시점의 충돌을 차단. 같은 버전으로 20건 동시 전송 후 어느 경로를 타는지 확인.

| 실행 | 200 | 409 — `currentVersion` 포함(선검사) | 409 — **없음**(`@Version`) |
| --- | --- | --- | --- |
| 1차 (원자료 미보관) | 1 | 10 | 9 |
| **3차** | 1 | 0 | **19** |

**정합성 정상** — 실제 수정은 양쪽 모두 1건(`version` +1). 실패는 전부 409.

**두 경로의 비율은 타이밍에 따라 변함.** 20건이 동시 출발하면 대부분이 승자의 커밋 전에 행을 읽어 선검사를 통과하고 `@Version`에서 걸림. 3차에서는 실패 19건 전부가 그 경로. 고정 비율이 아니라 **그 경로가 존재한다는 사실**이 결과.

2차는 제외 — 보낸 이름이 저장된 값과 같은 VU가 생겨 변경 없음으로 200이 1건 섞임. 실행마다 다른 이름을 쓰도록 스크립트 수정.

두 트랜잭션이 같은 버전을 읽어 선검사를 함께 통과하면, 커밋에서 밀린 쪽은 `OptimisticLockingFailureException` 경로. 이 경로는 `currentVersion` 미포함.

**조치** — 프론트 분기가 `currentVersion` 존재 여부였던 탓에 그 경로의 응답은 "다시 불러오기"가 아닌 일반 오류 토스트. 두 경로가 공유하는 `code === "VERSION_CONFLICT"`로 변경.

다른 화면(`AdminReportsPage` · `AdminNoticesPage`)은 이미 `code` 기준 — 이 화면만 해당.

**범위는 전역** — 선검사 + `@Version` 패턴이 5개 도메인에 있고, `currentVersion` 없는 409는 `GlobalExceptionHandler` 한 곳에서 나옴.

| 도메인 | 위치 | 동시 요청 빈도 |
| --- | --- | --- |
| 대여 | `RentalService` 승인·취소 · `AppointmentCommandService` 약속 수락 | **높음** — 한 물건에 요청 여러 건 |
| 안전 | `AdminReportService` 신고 처리 · `NoticeService` 공지 수정 | 관리자 2명이면 발생 |
| 물건 | `ItemService` 수정·공개여부 | 낮음 |
| 회원 | `MemberService` 이름 수정 | 거의 없음 |

**후속** — 모든 화면이 `code`로 판정하므로 동작에는 문제 없음. 다만 응답 계약이 두 모양인 상태.

통일에는 밀린 쪽의 버전 재조회가 필요하고, 실패한 트랜잭션에서는 불가해 별도 트랜잭션 요구. 동시 요청이 몰리는 대여 승인에서 `currentVersion`을 쓰려 할 때 걸림.

## 5. 만료 세션 정리와 인증 경합

모든 인증 요청이 `auth_sessions`를 조회하고, 정리 배치는 같은 테이블을 하루 한 번 대량 삭제. 삭제 조건 컬럼에 색인 없음 — **대상 5천 건에도 10만 행 전부 읽음.**

EXPLAIN — 색인 없음 `type=ALL` 99,189행 → 색인 추가 `type=range` **5,000행** (`ix_auth_sessions_absolute_expires`).

부하 중 정리를 실행해 초 단위 관찰. 전체 10만 건·만료 5천 건, 조건별 3회.

| | 배경 p99 | 삭제 초 p99 | 삭제 초 처리량 |
| --- | --- | --- | --- |
| 색인 없음 | 22.1 ms | **98.3 ms** (78~106) | 615건 |
| **색인 추가** | 21.4 ms | **41.9 ms** (35~71) | 616건 |

배경값이 양쪽 같아 조건 차이로 판정 가능. **p99 급증 2.3배 완화.**

**처리량 저하는 남음** — 615 → 616건으로 변화 없고, 양쪽 모두 배경(약 810건)의 75%. 색인은 탐색 비용만 없애고 5천 행 삭제·커밋 비용은 그대로.

코드 주석은 동시 실행을 위험으로 봤으나(`분산 잠금 도입`), 실제 문제는 **단일 실행의 크기**. 다음 수는 배치 분할.

요약 지표로는 안 보임 — p99 22.75 → 25.56 ms, 처리량 748 → 725 /s. 초 단위 관찰이 필요한 이유.

## 6. 포화 곡선과 커넥션 풀

한 지점만으로는 서버 한계 판정 불가. VU를 올리며 자원 지표를 함께 관찰 — 관리 포트(`127.0.0.1:9090`)에서 2초 간격 표집.

| VU | 처리량 | p95 | p99 | 풀 활성/대기 |
| --- | --- | --- | --- | --- |
| 10 | 802.8 /s | 14.8 ms | 19.7 ms | 10/0 |
| 20 | 840.5 /s | 29.7 ms | 38.9 ms | 10/11 |
| 40 | 784.3 /s | 77.3 ms | 123.3 ms | 10/31 |
| 80 | 874.7 /s | 125.6 ms | 158.9 ms | 10/71 |
| 160 | 874.2 /s | 256.3 ms | 323.0 ms | 10/151 |

전 구간 실패율 0% · 앱 CPU 15~18% · 시스템 CPU 93~96%.

**VU 10에서 이미 포화**(풀 10 기준 800~875 /s). VU 16배에 응답시간만 17배 — 추가 동시성은 전부 대기. 단계별 1회라 단계 간 ±10%는 구분 불가, 곡선의 모양이 결과.

**대기 = VU − 10.** 커넥션 10개(Hikari 기본값)가 전부 점유되고 초과 요청은 모두 대기. 풀이 큐 역할.

### 풀 크기 변경 — VU 80 고정, 3회 중위값

| 풀 | 처리량 | 편차 | p95 | p99 |
| --- | --- | --- | --- | --- |
| 10 (기본값) | 804.6 /s | 2.7% | 137.7 ms | 175.4 ms |
| **30** | **1156.9 /s** | 2.2% | 114.3 ms | 152.7 ms |
| 60 | 1159.7 /s | 8.1% | 108.6 ms | 158.3 ms |

**풀 10 → 30에서 처리량 1.44배.** 30 → 60은 편차 내 변화 없음 — **적정값 30 근처, 그 이상은 무효.**

앱 CPU 15~18%·시스템 CPU 93~100%라 머신 한계로 보였으나, 풀을 늘려 처리량이 오른 것으로 **풀이 실제 병목.** 30 이상에서 멈추므로 그다음 천장은 풀이 아님.

1회 측정에서는 풀 30이 풀 10보다 나빴음(p99 503 ms). 3회 반복 후 편차 2.2% — **1회 결과로는 반대 조치로 이어질 값.**

### 적용 후 평상 부하 — 풀 30, VU 10, 3회 중위값

처리량 683.9 /s(606~711) · 평균 12.36 ms · p95 20.05 ms · p99 30.26 ms · 실패율 0%.

**VU 10에서는 풀 크기 무관** — 동시 10개면 풀 10으로도 대기 0. 회차별 중위값 659.8(풀 10) · 704.0(풀 10) · 683.9(풀 30) /s로 같은 범위. 풀 효과는 대기가 생기는 VU 80 이상에서만.

## 7. 한계

**측정 환경**
- 부하 생성기·MySQL·서버가 같은 머신이고 시스템 CPU 93~100% — **처리량 천장(약 1,160 /s)은 서버 한계가 아니라 이 머신의 한계.** 조건 간 비교는 유효하나 절대 수치는 이 환경 한정
- 운영은 낮은 사양에 원격 DB(RDS) — 쿼리 1건의 비용이 로컬보다 큼. 효과 판단은 운영 측정에서

**지표 신뢰도**
- 처리량·평균은 편차 10% 이내로 결론이 서지만, p95는 편차 25%로 여유가 작음
- **p99는 편차 52%** (25.8~39.3 ms) — 꼬리 지표라 이 규모·시간에서는 불안정. 중위값만 참고치로 기록

**각 측정의 범위**
- **회원 조회 병합(9→8)의 응답시간 효과는 미검증** — 쿼리 8건 중 1건 차이로 이 편차에서는 분간되지 않음. 확정된 건 쿼리 수
- 이웃 프로필 8건은 소속 데이터가 있는 상태 기준 — 시드로 구성. 소속이 없으면 권한 판정에서 404로 빠져 더 적음(미측정)
- 정리 경합은 세션 10만 건 기준 — 운영 세션 규모가 다르면 영향 폭도 다름. 색인 전후 범위가 78~106 ms와 35~71 ms로 거의 맞닿아 있음
- 시드가 전부 `RETURNED` — 요청 자동 만료 작업이 행을 잠그는 상황은 재현되지 않음

## 8. 후속

- **쿼리 8건 → 6건** — 소속 조회가 회원별·동네별로 나뉘어 3건. 일괄 조회로 1건 가능하나 커뮤니티 도메인 변경 필요
- **정리 배치 분할** — 색인으로 p99 급증은 줄었으나 처리량 저하는 남음. 한 번에 전부 지우지 않고 나누는 방식 검토
- **운영 풀 크기 확정** — 공통 설정 `${DB_POOL_SIZE:30}` 적용(완료). 운영값은 RDS `max_connections` 확인 후 환경변수로 지정 — db.t3.micro는 메모리 기준 상한이고 인스턴스 수를 곱해 계산
- **운영 환경 재측정** — 머신 한계에 막힌 구간은 EC2+RDS에서 다시 확인 필요
- **409 응답 형식 통일** — `@Version` 경로에 `currentVersion` 미포함 (4절)

## 9. 재현

환경 무관 근거(쿼리 수 · 인증 고정 비용 · 삭제 조건 색인)는 스크립트로 재확인. 통과 시 종료 코드 0.

```bash
# 앱을 SQL 로그 켠 상태로 기동한 뒤
set -a; . backend/.env; set +a
bash docs/performance/scripts/verify-counts.sh <앱 로그 경로>
```

응답시간·처리량은 머신에 좌우되므로 스크립트에 넣지 않음. 아래 절차로 직접 측정.

```bash
# 시드 — 회원·대여·차단. 세션은 토큰 원문을 쿠키로, SHA-256을 token_hash로 직접 삽입(로컬 전용)
docker exec -i billim-mysql-1 mysql -ubillim -p"$MYSQL_PASSWORD" billim \
  --default-character-set=utf8mb4 < docs/performance/scripts/seed-load.sql

# 기동 — 처리량 측정은 SQL 로그 off. 켜면 로그 비용이 수치를 가림
ARGS="--spring.profiles.active=local --logging.level.org.hibernate.SQL=info"
ARGS="$ARGS --logging.level.org.hibernate.orm.jdbc.bind=info"
ARGS="$ARGS --spring.jpa.properties.hibernate.format_sql=false"
(cd backend && ./gradlew bootRun --args="$ARGS")   # 래퍼는 backend 기준. 변경은 인자로 추가
#   --spring.datasource.hikari.maximum-pool-size=30
#   --billim.auth.session-touch-interval=0s

K="k6 run -e SESSION=<토큰> -e TARGET=4"     # 스크립트 경로는 항상 마지막 인자
JS="docs/performance/scripts/member-read.js"

# 처리량·응답시간 — 워밍업 1회 후 3회 반복
$K -e STEADY=30s $JS ; for i in 1 2 3; do $K -e STEADY=90s $JS; done

# 포화 곡선 — VU별 1회. 자원 지표는 관리 포트에서 2초 간격 표집
for vu in 10 20 40 80 160; do $K -e VUS=$vu -e RAMP=15s -e STEADY=60s $JS; done
curl -s 127.0.0.1:9090/actuator/prometheus \
  | grep -E 'hikaricp_connections_(active|pending)|(process|system)_cpu_usage'

# 동시 수정 — CSRF는 서버가 준 값 사용. 마스킹되어 DB의 csrf_token과 다름
CSRF=$(curl -s -H "X-Requested-With: XMLHttpRequest" -H "Cookie: BILLIM_SESSION=<토큰>" \
  localhost:8080/api/v1/auth/csrf | jq -r .csrfToken)
k6 run -e SESSION=<토큰> -e CSRF="$CSRF" -e VERSION=<현재 version> \
  docs/performance/scripts/member-rename-race.js

# 정리 경합 — 정리를 매분 실행. k6를 :40에 시작하고 다음 분 :05에 만료 5천 건 투입하면
#            그다음 :00 삭제가 유지 구간 중반
CLEANUP_CRON="0 * * * * *" sh -c 'cd backend && ./gradlew bootRun --args="$ARGS"'
$K -e STEADY=110s --out csv=out.csv $JS     # 초 단위 분석용

# 요청당 쿼리 수 — SQL 로그를 켜고, 요청 스레드만 집계
grep -c "nio-8080-exec.*org.hibernate.SQL" <로그>
```
