# 빌려준 대여 요청 목록의 정책 조회 일괄 처리

## 1. 문제

- 요청 20건의 승인 가능 여부를 조립하면서 유효 소속·양방향 차단·제재·공용 장소를 거래마다 반복 조회.
- 기존 목록 일괄 조회 이후에도 실제 HTTP 요청당 SQL 128회. 소속 40·차단 20·제재 40·장소 20회가 주요 잔여 비용.

## 2. 근거와 조건

- 측정일: 2026.11.07. 수정 전 기준은 이번 작업 시작 HEAD, 기준 커밋·전후 JAR·소스 SHA-256은 각 metadata.json 보존.
- 새 전용 프로젝트 `billim-rental-policy-20261107`. 개발 DB·기존 검증 DB 미사용.
- Docker MySQL 8.4·Java 21 백엔드 1대, 백엔드 메모리 상한 1GiB, 같은 macOS PC의 자원 공유.
- 합성 회원 42명·물건 2,000개·대여 2,000건. 소유자 계정의 요청 1,000건 중 최신 20건 조회. 각 물건·요청자 상이, 모두 승인 가능, 소속·장소 유효·차단·제재 없음.
- GET `/api/v1/rentals?role=OWNER&status=REQUESTED&page=0&size=20`. 10 VU, 요청 후 0.2초 대기, 워밍업 10초 제외·30초 × 3회.
- 전후 같은 DB·데이터·세션·컨테이너 설정 사용, 백엔드 JAR만 교체. 부하 측정과 빌드·테스트 동시 실행 없음.
- k6 HTTP 지연·MySQL 앱 계정 SELECT/INSERT/UPDATE/DELETE 계수, Actuator 3초 간격 수집. 요청마다 응답 전체·배열 순서·허용 행동 동일성 검사. 객체 키 순서만 비교 제외.
- 수정 전 측정 중 작업 트리 구현 편집, 서버에는 변경 전 JAR 유지. 수정 전 소스 지문은 `git show HEAD` 원본 기준으로 보정. 수정 후는 전체 빌드를 통과한 작업 트리 JAR.

## 3. 변경

- `RentalRequestPolicy.canApproveAll`에서 승인 후보의 회원 활성 상태·유효 소속·제재·공용 장소를 각각 일괄 조회. 차단은 기존 `BlockQuery.findBlockedAmong` 재사용, 물건 소유자별 후보만 조회.
- 소속은 기존 CommunityMembershipQuery에 후보 회원의 유효 동네 일괄 조회 추가. ACTIVE·인증 만료 전 기준 및 DB의 회원당 활성 소속 유일성 유지.
- 제재는 기존 SanctionService를 통해 일괄 조회. 미해제·시작 시각 이하·종료 없음 또는 종료 전 조건 유지.
- 단건과 목록의 최종 정책 조건을 같은 함수로 공유. 장소 활성 여부뿐 아니라 대여의 동네와 장소 소속 일치 검사 유지.
- `RentalQueryService`의 목록 읽기 문맥에 판정 결과 저장. 요청 밖 캐시 없음. 공유 일괄 요약 경로도 같은 읽기 문맥 사용.
- 실제 승인 명령의 개별 재검사·잠금·트랜잭션 경계 유지. DB 구조·인덱스·인증 정책·외부 API 형식 변경 없음.

- SQL **128→13회, 89.8% 감소**. 단일 HTTP 진단도 128→13회. INSERT/UPDATE/DELETE 0.
- HTTP p95 회차별 중위값 **116.492→44.093ms, 62.1% 감소**. 전체 요청을 합친 p95와 구분.
- 모든 정식 실행 HTTP 오류 0·응답 전체 및 허용 행동 일치 100%·k6 종료 코드 0. 총 7,463개 정식 요청.
- Actuator 수집의 outbox 상태 COUNT 4회/수집을 계측 SQL에서 분리. 보정 SQL=(앱 계정 SQL 합계−수집 횟수×4)/요청 수. 단일 요청 진단과 일치. 지연은 계측 비용을 포함한 원본값.

### 회귀 검증

- 실제 MySQL·실제 소속/차단/제재 서비스 적용 통합 테스트 추가. 승인 가능한 요청 20건의 SQL 상한 13회, 단건 상세의 요약 응답 전체 동일성 확인.
- 소속 만료 시각 일치·이탈·다른 동네·소유자 소속 만료, 양방향 차단, 요청자/소유자 탈퇴, 비활성/다른 동네/없는 장소, 비공개/삭제 물건 검증.
- 제재 시작 시각 일치·종료 시각 일치·미래 시작·해제·소유자 제재에서 목록과 단건 판정 일치 확인. 소유자 탈퇴는 목록 인증 거부 확인.
- 기존 점유·연체·요청 만료·동시 승인·멱등·약속 경합 등 포함 `backend/./gradlew build` 통과. 테스트 1,005건, 실패·오류·건너뜀 0.

## 5. 한계

- 로컬 합성 데이터·단일 백엔드·10 VU·30초×3회 기준. 운영망·최대 처리량·장시간 안정성으로 일반화 불가.
- 전후 시간 차·JVM/DB 예열·같은 PC 자원 공유 영향 포함. 큰 상대 지연 개선율을 모든 환경에 적용하지 않으며 SQL 감소를 주요 근거로 사용.
- 모두 승인 가능한 요청 분포. 거부가 일찍 결정되거나 페이지가 작은 경우 기존 단락 평가보다 일괄 조회 비용이 높을 수 있음. 혼합 정책 분포는 회귀 검증 대상이며 별도 부하 미측정.
- 요청별 소속·제재 일괄 판정은 한 번의 현재 시각을 사용. 실제 명령은 잠금 아래 실행 시점 기준 재검사 유지.
- 전체 내 대여 화면·개별 상세·약속 API의 체감 개선 수치로 해석 금지.
