# 대여 승인 멱등 재전송 측정

## 문제

- 같은 승인 요청의 동시 재전송·완료 후 재시도 시 응답 재사용과 중복 처리 방지 확인.
- 같은 키에 다른 본문을 보냈을 때 기존 요청을 다시 실행하지 않고 거부하는지 확인.

## 근거

- 최종 측정 완료: 2026-10-26 23:13 KST.
- 서버 커밋: `a4de1c8d39c2db983d365146be80ca962a16b108`.
- 기존 `billim-rental-perf` 환경 재사용: MySQL 8.4·Java 21·단일 백엔드, 메모리 상한 1GiB, `127.0.0.1:18081`.
- 서버·DB 구조·인증 로직 변경 없음. 실제 계정과 다른 전용 DB·임시 세션 사용.
- 측정마다 물건 20개·대기 요청 200개 추가. 각 물건의 첫 요청 1개만 재전송 대상으로 선택, 나머지 9개는 DB 정합성 확인용으로 유지.
- 승인 작업 20개를 순차 실행. 각 작업의 요청은 다음 순서.
  1. 같은 거래·같은 키·`expectedVersion=0`으로 10개 HTTP 요청 동시 전송.
  2. 같은 키·같은 본문으로 완료 후 1개 추가 전송.
  3. 같은 키·`expectedVersion=1`로 본문을 바꾸어 1개 전송.
- 총 240건. 동시 배치 200건·완료 후 재전송 20건·본문 변경 20건.
- k6 VU 1·iteration 1·HTTP batch 동시 연결 상한 10. 같은 소유자 계정 사용.
- JSON 객체 필드 순서 정렬 후 전체 응답 값 비교. 배열 순서·모든 필드 값은 그대로 비교.

## 변경

- `performance/rental/idempotency.js`에 요청 배치·응답 일치·키 재사용 거부 검증 추가.
- 기존 실행 도구에 `--idempotency` 모드 추가. 기본 동시 승인 모드는 유지.
- DB 후검증에 승인 버전 1·멱등 기록 수 추가.
- 임시 세션 2시간 제한, 실행 후 폐기 및 인증 fixture 삭제.

| 관측 요청률 | 179.01req/s |

- 같은 작업의 성공 응답 11개씩 값 일치 확인. 최초 처리와 재전송이 섞인 동시 배치는 별도 순수 재전송 성능으로 해석하지 않음.
- 완료 후 재전송 20건은 이미 저장된 성공 응답 재사용 구간만 별도 측정.
- 다른 본문 20건 모두 HTTP 409 `IDEMPOTENCY_KEY_REUSED` 확인.
- 물건별 최종 DB: 승인 1건·대기 9건. 실제 승인은 전체 20건만 발생.
- 승인 버전 1인 거래 20건·승인 이력 20건·약속 슬롯 40건·승인 outbox 이벤트 20건·멱등 기록 20건 확인.
- HTTP 실패율에는 정상적인 409 20건이 포함되어 8.33% 표시. 서비스 오류율로 해석 금지. 예상 밖 응답률은 0%.
- 최초 실행은 JSON 객체 필드 순서를 포함한 문자열 비교로 응답 일치 검증 실패. DB 후검증은 통과. 필드 순서 정렬 비교로 변경 후 새 거래에서 최종 실행 통과. 서버 변경 없음.
- 초기 진단 실행 이후 JVM·DB가 준비된 상태에서 최종 실행. 최종 수치를 초기 실행과 성능 개선으로 비교하지 않음.

원본: [최종 k6](raw/idempotency.json), [최종 DB 검증](raw/idempotency-verification.json), [초기 진단 k6](raw/initial-idempotency.json), [초기 진단 DB 검증](raw/initial-idempotency-verification.json).

## 재현

최초 전용 계정·동네 준비는 [목록 측정](rental-list.md#재현) 참고. 기존 전용 데이터가 있다면 다음 명령으로 실행.

```bash
cd backend
./gradlew bootJar
cd ..
docker compose -f performance/rental/compose.yaml up -d --build --wait
python3 performance/rental/run_approval.py --idempotency
docker compose -f performance/rental/compose.yaml stop
```

## 한계

- 약 1.34초의 짧은 시험. 작업 20개·단일 계정·동시 연결 10개에 한정. 최대 처리량·장기 부하 시험 아님.
- 최초 승인과 재전송 응답 혼합 지표를 별도 승인 성공 처리량으로 해석 불가.
- 승인 명령의 멱등성만 검증. 대여 요청 생성·약속 명령의 멱등성과 24시간 만료 후 키 처리·실패 후 재시도는 별도 대상.

- 실행마다 데이터가 추가되어 DB 전체 규모 변화. 최적화 전후 비교 시 같은 초기 상태 필요.
