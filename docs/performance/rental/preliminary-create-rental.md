# 대여 요청 생성 부하·재전송 측정

## 문제

- 여러 회원이 서로 다른 물건에 대여를 요청할 때 생성 응답 시간·처리량·실패율 및 원자적 저장 검증.
- 생성 요청의 동시·완료 후 재전송이 같은 거래를 반환하는지 확인.

## 근거

- 전용 Compose `billim-rental-perf`, HTTP `127.0.0.1:18081`, MySQL 8.4·Java 21·단일 백엔드, 백엔드 메모리 상한 1GiB.
- 요청자 10명(981000~981009)·소유자 10명(981011~981020), 회원 쌍이 겹치지 않도록 배치.
- 모든 회원은 전용 동네의 유효 소속 보유. 기존 실제 계정·개발 DB와 분리.
- 실행마다 새 공개 물건 2,420개 준비. 신규 요청은 매번 새 물건·새 UUID 키 사용.
- 경로: `POST /api/v1/rentals`, 시작일 KST 오늘+2일·종료일 오늘+3일. 물건 가능 기간 안으로 설정.
- 모든 계정 사전 검사 10명·1초 → 준비 구간 10명·30초 → 본 부하 10명·3분. 신규 요청 뒤 VU별 1초 대기.
- 생성 재전송은 별도 10개 작업에서 동일 키 동시 10건·완료 후 1건·다른 본문 1건, 총 120건 전송.
- 재전송 JSON 객체는 필드 순서 정렬 후 전체 값 비교. 배열 순서 유지.
- 세션 쿠키·CSRF 검증 유지. 임시 세션 10개 생성·실행 후 폐기, 인증 fixture 삭제.

## 변경

- 서버·DB 구조·인증 로직 변경 없음.
- `performance/rental/create-rental.js`와 `run_create.py`에 고유 데이터·구간별 측정·생성 재전송·DB 후검증 추가.
- 실패 결과를 숨기지 않고 구간별 종료 코드·원본 JSON 보관. 후속 실행 도구는 결과가 생성된 실패 구간도 보존하고 다음 구간 측정 가능.

- 본 측정 전체 생성 건수와 이력·이벤트의 추가 DB 집계는 실행 승인 거절로 미진행. HTTP 검증 결과와 재전송 전용 DB 후검증 범위를 구분.

### 생성 재전송: 중복 저장 없음, 동시 응답 검증 실패

| 최종 재전송 전용 구간 | 결과 |
|---|---:|
| 총 요청 | 120건 |
| HTTP 201 성공 | 20건 |
| 예상 밖 404 | 90건 |
| 정상적인 다른 본문 거부 409 | 10건 |
| 동시 재전송 응답 일치 검증 | 0/10 작업 통과 |
| 완료 후 재전송 응답 일치 | 10/10 통과 |
| 다른 본문 키 재사용 거부 | 10/10 통과 |
| 완료 후 재전송 평균 / p95 | 3.14ms / 5.56ms |

- 같은 키 동시 요청 10개 중 최초 생성 1건만 201, 나머지 9건은 404 `RESOURCE_NOT_FOUND`. 10개 작업에서 반복 재현.
- 동시 배치가 끝난 후 같은 요청을 보내면 201·동일 응답 반환. 총 20개의 201은 실제 생성 10건·완료 후 재전송 10건.
- 원본 비교는 배치에서 찾은 첫 유효한 201 응답을 기준으로 수행. 배열 첫 원소가 실패 응답인 경우 비교 기준이 잘못되는 측정 코드 문제도 보완. 이 변경 후에도 404 90건 재현.
- 예상 밖 HTTP 오류율 75%(90/120). 기본 `http_req_failed`는 정상 409도 포함하여 83.33%(100/120).
- 최종 재전송 DB 후검증: 대여 10건·서로 다른 물건 10개·요청자 10명·모두 REQUESTED/version 0. 이력·RENTAL_REQUESTED 이벤트·멱등 기록 각각 10건, 중복 저장 없음.
- DB 정합성 검증은 통과했지만 응답 기준은 실패(k6 종료 코드 99). 생성 멱등성 전체 통과로 보고하지 않음.
- 코드상 유력 분석 후보: 소유자 조회로 만들어진 트랜잭션 스냅샷 이후 회원 잠금 대기 → 최신 멱등 기록 조회 성공 → 기존 스냅샷의 거래 조회에서 새 거래를 못 찾는 흐름. 격리 수준과 조회 방식을 분리한 추가 재현 필요. 원인 수정 미진행.

### 준비 과정에서 발견한 데드락

- 최초 준비 부하: 280건 중 27건 실패(9.64%). 다음 진단 준비 부하: 290건 중 1건 실패(0.34%).
- 서버 로그에서 MySQL 오류 1213·SQLState 40001, `idempotency_records` INSERT 중 데드락 확인.
- InnoDB 최근 데드락에서 `uk_idempotency_member_operation_request`의 gap lock과 insert intention 대기 충돌 및 트랜잭션 롤백 확인.
- `IdempotencyRecordRepository`의 미존재 키 잠금 조회와 후속 INSERT의 상호작용이 분석 후보. 모든 경우의 정확한 교착 조건을 확정한 것은 아님.
- 코드·인덱스·격리 수준 변경 없이 새 물건과 새 키로 진단 반복. 데이터가 누적되며 실패 빈도 변화 관측. 성능 개선으로 해석 금지.
- 실패 준비 구간의 수치를 삭제하거나 최종 성공 구간으로 대체하지 않음.
- 원본 데드락 근거는 합성 DB의 잠금 정보만 추려 보관. 인증값 미포함.
- 근거: [최초 실패 준비 구간](raw/initial-create-warmup.json), [두 번째 진단 준비 구간](raw/diagnostic2-create-warmup.json), [데드락 잠금 요약](raw/create-deadlock-summary.txt).

## 재현

전용 계정·동네 최초 준비는 [목록 측정](rental-list.md#재현) 참고. 기존 전용 데이터가 있는 경우 저장소 루트에서 실행.

```bash
cd backend
./gradlew bootJar
cd ..
docker compose -f performance/rental/compose.yaml up -d --build --wait
python3 performance/rental/run_create.py
docker compose -f performance/rental/compose.yaml stop
```

- 생성 재전송만 재현: `python3 performance/rental/run_create.py --replay-only`.
- 검증 실패 시에도 원본과 DB 후검증 보존 후 비정상 종료. 실패 임계값을 완화하거나 서버 재시도로 오류를 숨기지 않음.

## 한계

- 대기 시간을 포함한 관측 요청률이며 최대 생성 처리량 아님. 반복 실행마다 데이터 누적.
- 재현된 데드락은 미해결. 최종 구간에서 오류가 없어도 안정성 문제 해결로 판단 불가.
- 생성 동시 재전송 404 미해결. 승인 명령 재전송 시험의 통과 결과와 구분.
- 사진·카카오·실제 채팅방 연결 없음. outbox 저장까지 포함하며 후속 알림 소비는 비활성.
- 단일 PC·단일 백엔드, 다른 Docker 서비스와 자원 공유. 운영 성능으로 일반화 불가.
- 잠금 대기·CPU·메모리 시계열·요청별 SQL 수 미측정. 데드락 발생 근거와 일반적인 잠금 대기 지표는 구분 필요.
- 다음 개선 후보: 동일한 빈 키 구간에서의 교착 재현 테스트 → 트랜잭션 격리·멱등 잠금 설계 검토 → 승인된 개선 후 동일 DB 초기 상태 비교.
