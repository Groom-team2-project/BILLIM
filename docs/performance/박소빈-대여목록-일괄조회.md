# 박소빈-대여 목록 일괄 조회 개선

> 양식: [성능 측정 양식](성능%20측정%20양식.md). 실제 MySQL·HTTP·k6 전후 비교. [과거 목록 측정](박소빈-대여목록.md)과는 데이터·부하 조건이 다르므로 수치 직접 비교 제외.

## 1. 문제

- 대여 20건 응답 조립 중 거래마다 상대 회원 조회 반복.
- 소유자의 대기 요청은 물건·연체·점유 검사도 거래마다 조회하는 구조.
- 기존 트랜잭션의 1차 캐시가 같은 회원의 중복 조회는 줄여도 서로 다른 상대 회원·물건 조회는 줄이지 못하는 문제.

### SQL 진단

| 대상 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 빌린 목록 단일 HTTP 요청 | 24 | 5 |
| 빌려준 요청 단일 HTTP 요청 | 204 | 128 |

- 빌린 목록의 회원 조회 21회 → 유효 회원 확인 1회 + 회원 일괄 조회 1회.
- 빌려준 요청은 회원 21→2회, 물건 20→1회, 연체 20→1회, 기간 겹침 20→1회. 총 76회 감소.
- 빌려준 요청의 나머지 주요 SQL은 소속 40회·차단 20회·제재 40회·장소 20회. 해당 정책은 이번 범위에서 변경하지 않음.
- 단일 요청 진단은 계측·부하 실행과 분리. 정규화된 SQL digest에는 root 계측 연결의 `SELECT @@version_comment`가 섞이므로 업무 SQL 해석에서 제외. 계정 카운터는 앱 계정만 집계.

## 3. 변경

- 해당 페이지에 있는 회원을 `findAllById`로 한 번에 조회해 ID별 응답 조립.
- 유효한 소유자 요청의 물건을 일괄 조회. 요청당 지역 변수로만 보관.
- 승인·전달 판단에 필요한 ACTIVE 기한을 itemId 기준 일괄 조회. 여러 ACTIVE가 존재해도 가장 이른 dueAt으로 연체 판정, 존재 자체로 전달 제한.
- 요청 ID 목록에 대해 상관 EXISTS 조회로 점유 충돌 일괄 판정. APPROVED·ACTIVE·RETURNED 및 양끝 포함 날짜 경계 유지.
- 실제 소속·차단·제재·장소 판단은 기존 `RentalRequestPolicy.canApprove` 호출 그대로 유지.
- 단건 상세·상태 변경·홈 요약은 기존 조회 경로 유지. 실제 승인 명령의 잠금·재검사 변경 없음.
- DB·Flyway·인덱스·API 요청/응답·인증 설정·라이브러리 변경 없음.

- SQL 감소: 빌린 목록 약 79.2%, 빌려준 요청 약 37.3%.
- 이 조건의 p95 중위값 감소: 빌린 목록 약 14.1%, 빌려준 요청 약 21.8%. SQL 감소를 주 개선 근거로 사용.
- 모든 기록 구간 HTTP 오류 0·전체 응답 일치 100%. INSERT/UPDATE/DELETE 모두 0.
- 응답 시간의 각 회차 p95를 집계한 중위값이며, 모든 요청을 합친 p95와 구분.

### 계측 자체의 SQL 분리

- `/actuator/prometheus`를 한 번 수집하면 기존 OutboxMetrics의 상태별 건수 조회 4회 발생.
- 별도 [단독 수집 진단](rental/raw/list-compare-20261031/actuator-probe.json)으로 SELECT 4회·outbox COUNT 4회 확인.
- 원본 계정 카운터 보존. 보정 SQL = 원본 SQL 합계 − Actuator 수집 횟수 × 4.
- 보정 결과는 모든 회차에서 각각 24·5·204·128로 일정, 표준편차 0. 단일 HTTP 요청 진단과 일치.
- 계측의 실행 비용은 응답 시간에서 뺄 수 없으므로 지연은 수집을 포함한 원본 그대로 사용.

### 기능·품질 검증

- 개선 전 추가한 MySQL 테스트의 조회 수 제한 2건 실패 확인 후 개선 적용. 개선 후 통과.
- MySQL 통합 테스트: 서로 다른 회원 20건에서 조회 수 상한 확인, 목록과 단건 상세의 요약 응답 전체 동일성 검증.
- 경계: RETURNED의 종료일=요청 시작일 겹침, dueAt과 현재 시각 일치/1마이크로초 차이, ACTIVE 존재 시 전달 제한, 요청 만료·지난 시작일·기존 정책 거부 유지.
- 대여 테스트 145건 통과. `backend/./gradlew build` 전체 테스트 944건 통과, 실패·오류·건너뜀 0.
- 실 HTTP 비교는 기준 응답의 객체 키 순서를 제외하고 모든 값·배열 순서·허용 행동 비교.
- 최초 도구 워밍업의 JSON 키 순서 비교 실패는 [제외 원본](rental/raw/list-compare-20261031/before/borrowed/excluded-key-order-warmup/) 보존. 객체 키를 정렬하는 검증으로 수정한 뒤 워밍업·3회 측정 재실행. 성능 표본에서 제외.

## 5. 한계와 남은 비용

- 로컬 같은 PC·같은 DB의 읽기 부하. 운영망·장시간 부하·최대 처리량으로 일반화 불가. 0.2초 대기를 포함한 닫힌 부하의 처리량.
- 인접 비교 전후로 다른 컨테이너와 CPU 공유. SQL 횟수는 동일 재현됐지만 응답 지연은 환경 영향 포함.
- 빌려준 요청 20건은 서로 다른 물건·요청자이고 모두 승인 가능. 같은 물건·회원이 반복되거나 일찍 거부되는 목록은 기존 1차 캐시·단락 평가로 개선 폭이 다를 수 있음.
- 소속·차단·제재·장소의 반복 SQL 120회는 남아 있음. 이를 줄이려면 기존 도메인 판정 창구의 일괄 조회 설계를 별도로 검토할 대상.
- 목록 API만 측정. 프론트 최초 화면 전체·요약·상세 20건의 합산 지연 개선 수치는 아님.
- 데이터는 전용 DB에 직접 넣은 합성 데이터. 실제 운영 분포·인증 갱신·주기 작업을 모두 재현하지 않음. outbox 소비·인증 정리 비활성, 요청 만료 간격 24시간.
