# 성능 측정 양식

> 버전 : v0.1.0\
> 수정일 : 2026.10.19

> 이 양식을 복사해 `docs/performance/<담당>-<기능>.md`로 기록. 조건이 담당자마다 다르면 결과 비교가 불가.

- 부하는 k6(`brew install k6`), 서버 지표는 Actuator `/actuator/prometheus`
- 측정 경로는 ALB 없이 인스턴스 직접 호출 — 차수 간 비교 기준 통일
- **환경이 다르면 같은 표에 섞지 않음** — 로컬과 운영은 표를 분리. 머신·네트워크가 달라 수치 비교가 성립하지 않음
- 환경을 넘는 비교는 환경 무관 지표로만 — 요청당 쿼리 수, 쓰기 발생 여부, 동시 요청의 응답 분포
- 같은 데이터·같은 경로로 두 번 재지 않은 측정은 기록 제외
- **1회 측정은 근거로 쓰지 않음** — 워밍업 후 3회 이상 반복, 중위값과 편차를 함께 기록
- 부하 생성기와 서버가 같은 머신이면 편차가 2배까지 벌어짐 — 측정 중 빌드·테스트 정지
- 쿼리 수·쓰기 발생 여부는 환경과 무관하게 재현 — 응답시간이 흔들릴 때의 대체 근거
- k6 스크립트는 `scripts/<기능>.js`로 함께 커밋

# <담당>-<기능> 측정

> 양식 : [성능 측정 양식](성능%20측정%20양식.md)

## 1. 조건

| 항목 | 값 |
| --- | --- |
| 측정일 · 담당 | YYYY.MM.DD · 이름 |
| 구분 | 로컬 / 운영 · 1차 / 2차 |
| 서버 | 로컬 macOS + Docker MySQL · 또는 EC2 t3.small 1대 + RDS db.t3.micro |
| 코드 | 측정 시점 커밋 해시 |
| 데이터 | members 1,000 · rentals 20,000 (쏠림 여부도 적는다) |
| 대상 API | `GET /api/v1/items` |
| 부하 | 10 VU · ramp-up 30s → 유지 3m |
| 성공 기준 | p95 < 500ms · 오류율 < 1% |

## 2. 결과

### 로컬

| 지표 | 개선 전 | 개선 후 |
| --- | --- | --- |
| 처리량 (req/s) · 3회 중위값 | | |
| p50 / p95 · 편차 | | |
| 오류율 · 실패 유형 | | |
| 요청당 SQL | | |

응답시간 편차가 크면 시간 지표는 비우고 환경 무관 지표만 채운다 — 빈 칸이 흔들리는 숫자보다 낫다.

### 운영

같은 표를 반복한다. 측정하지 않은 환경은 섹션을 두지 않는다.

쓰기 경합이 있는 기능은 동시 요청 결과도 적는다 — 예) 10 VU 동시 승인 → 1건 성공, 9건 409. 이 분포는 환경과 무관.

## 3. 해석과 한계

- 숫자가 뜻하는 것 — 기준을 넘겼는지, 어디가 걸렸는지
- 조치 — 막힌 곳이 있었다면 인덱스·쿼리·캐시 중 무엇을 골랐고 왜
- 한계 — 이번 측정으로 알 수 없는 것, 다음 차수로 넘길 것

## 4. 재현

```bash
k6 run -e SESSION=<토큰> docs/performance/scripts/<기능>.js
```
