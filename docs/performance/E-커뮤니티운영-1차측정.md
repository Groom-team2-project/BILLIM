## 4. 병목 근거

[raw/explain-result.txt](raw/explain-result.txt) 원본.

### 4.1 신고 목록에 정렬 인덱스가 없다 — 가장 큰 비용

`findAllByOrderByCreatedAtDescIdDesc`가 쓰는 `(created_at DESC, id DESC)` 인덱스가 없다.
기존 인덱스는 `(reporter_id, created_at, id)`와 `(community_id, status, created_at, id)`뿐이라
전체 목록 정렬에 쓸 수 없다.

```
-> Limit: 20 row(s)  (actual time=10.3..10.3 rows=20)
   -> Sort: r.created_at DESC, r.id DESC, limit input to 20 row(s) per chunk
       -> Table scan on r  (actual time=0.0104..7.44 rows=20000 loops=1)
```

**첫 페이지도 2만 행을 전부 읽고 정렬한다.** offset 10000은 13.6 ms, offset 0은 10.3 ms로
차이가 작다. 즉 깊은 페이지가 아니라 정렬 인덱스 부재가 원인이다.

### 4.2 주변 동네 좌표 사각형이 인덱스를 타지 못한다

```
-> Filter: (status='ACTIVE' and center_latitude between .. and center_longitude between ..)
     (actual time=0.0874..1.86 rows=81 loops=1)
   -> Table scan on c  (cost=362 rows=3547) (actual time=0.0723..1.3 rows=3500 loops=1)
```

좌표 컬럼에 인덱스가 없어 3,500행을 전부 읽은 뒤 걸러낸다. 전체 조회(1b)는 1.14 ms,
사각형 필터는 1.86 ms로 **DB 시간은 오히려 조금 늘었다.**

사각형 선필터의 이득은 DB가 아니라 그 뒤였다. 애플리케이션으로 넘어가는 행이 3,500 → 81로 줄어
거리 계산·정렬·응답 조립 비용이 줄었다. 이 선필터가 의도한 효과를 내려면
`(status, center_latitude, center_longitude)` 인덱스가 필요하다.

### 4.3 동네 검색 LIKE는 선두 와일드카드라 인덱스를 못 쓴다

```
-> Filter: ((name like '%역삼%') or (display_address like '%역삼%')) (actual time=2.97..2.98 rows=20)
   -> Index range scan on c using idx_communities_status_name over (status='ACTIVE')
        (actual time=0.115..2.63 rows=2470 loops=1)
```

인덱스는 `status='ACTIVE'` 범위를 좁히는 데만 쓰이고 2,470행을 훑는다.
동반 COUNT 쿼리는 3,500행 전체 스캔(1.02 ms)이다.

### 4.4 유효 소속 수 집계는 문제가 없다

```
-> Group aggregate: count(0) (actual time=0.0179..0.0379 rows=19)
   -> Covering index range scan on cm using idx_community_memberships_community_status_expires
```

동네 목록마다 20개를 한 번에 묻는 방식이고 커버링 인덱스로 0.04 ms에 끝난다. 손댈 곳이 아니다.

### 4.5 목록마다 COUNT가 함께 나간다

`Page` 반환이라 매 요청에 건수 세기가 붙는다. 신고 2만 건 1.18 ms, 검색 COUNT는 전체 스캔 1.02 ms.
개별로는 작지만 모든 목록 요청의 고정 비용이다.

## 5. 지도 연동을 켠 경우

카카오맵 로컬 API 권한은 최초 활성화 앱 하나에만 자동 부여된다. 로그인 앱에는 권한이 없어
403이 왔고, 테스트 앱의 REST API 키를 `KAKAO_REST_API_KEY`로 분리해 해결했다.
카카오 로그인은 기존 `KAKAO_CLIENT_ID`를 그대로 쓴다.

### 5.1 외부 호출 비용

주변 동네(E_071) 기준, VU 1 · 30회 순차 호출.

| 상태 | 평균 | 중위 | p95 | 최대 | 추가 지연 |
|---|---|---|---|---|---|
| 지도 OFF (DB만) | 18.8 ms | — | 22.9 ms | 28.6 ms | 기준 |
| 카카오 · 호출 성공 | 69.6 ms | 67.0 ms | 88.6 ms | 102.2 ms | +50.8 ms |
| 카카오 · 호출 403 실패 | 44.5 ms | 43.9 ms | 53.5 ms | 73.6 ms | +25.7 ms |
| **VWorld · 호출 성공** | **109.6 ms** | 104.4 ms | 176.2 ms | — | **+90.8 ms** |

운영 제공자는 VWorld다(카카오맵은 원격 탑재가 유료). **VWorld가 카카오보다 약 40 ms 느리다.**
호출이 두 번 나가기 때문이다 — `getAddress`로 코드를 얻고, 그 읍면동의 대표 좌표를 행정구역
검색으로 다시 받는다. 측정은 ±0.1도 범위의 무작위 좌표라 매번 다른 읍면동을 때려 지명 캐시를
거의 타지 못했다. 같은 동네 요청이 반복되는 실사용에서는 이보다 낮다.

**성공 호출 한 번이 카카오 51 ms, VWorld 91 ms다.** 지도를 켜면 주변 동네의 실비용이
10.7 ms에서 60~100 ms로 뛰고, 그동안 가장 비쌌던 관리자 신고 목록(20.3 ms)을 크게 넘어선다.
**지도 연동이 E 파트 최대 병목이다.** 운영 제공자가 더 느린 쪽이라 호출을 줄이는 일이
6.1의 제안대로 더 중요해졌다.

호출이 실패해도 25.7 ms가 든다. 장애 시에도 이 비용은 그대로 치른다.

### 5.2 폴백과 판정 경로 확인

| 확인 | 결과 |
|---|---|
| 지도 403일 때 응답 | 30회 전부 200. 503 없이 반경 판정으로 폴백 |
| 코드 일치 인증 | `판정=REGION`. 정확도 4,000 m(반경 3,000 m 초과)에도 통과 |
| 코드 불일치 인증 | `판정=RADIUS`로 떨어짐 |
| 주변 동네 자동 등록 | 역삼동(`11680101`)·양평읍(`41830250`)이 실제 코드로 등록됨 |
| 검색 후보 보충 | 카카오 "정자" → 2건. VWorld "서초" → 10건, "분당" → 5건(카카오는 0건) |
| 자동 등록 수렴 | 30회 호출로 동네 3,510 → 3,538 |

코드 경로가 정확도 상한을 보지 않는다는 설계가 실제로 확인됐다. 반경·정확도만으로는
막혔을 요청이 읍면동 일치로 통과한다.

농촌에서도 리가 아니라 읍 단위로 잡힌다(양평읍). 법정동 코드 앞 8자리만 쓰기 때문이다.

### 5.3 검색 보충의 한계

주소 검색은 검색어가 **구·시 이름과 같으면 그 지역 자체만** 돌려주고 읍면동을 주지 않는다.

| 검색어 | 카카오 응답 | 보충 결과 |
|---|---|---|
| 역삼 | 역삼동(법정동) · 역삼1·2동(행정동 행, `b_code` 빈 값) | 1건 등록 |
| 정자 | 성남 정자동 · 수원 정자동 | 2건 등록 |
| 서초 | 서울 서초구 (읍면동 이름 빈 값) | 0건 |
| 분당 | 성남시 분당구 | 0건 |

읍면동 이름이 빈 결과는 걸러내도록 구현돼 있어 구 단위 행은 동네로 등록되지 않는다.
의도한 동작이지만, 사용자가 "서초"나 "분당"만 입력하면 전국 후보가 보충되지 않는다.
이미 등록된 동네는 그대로 검색되므로 결과가 비는 것은 아니다.

| 3 | 커넥션 풀 | VU 20 > 풀 10, 전 구간 포화 대기 | 풀 크기 상향 후 동일 조건 재측정 | p95 70.8 ms 개선 |

### 6.1 1순위를 반경 우선으로 바꾸는 근거

현재 인증은 읍면동 코드를 먼저 묻고 실패하면 반경으로 내려간다. 두 기준은 OR이므로
**순서를 바꿔도 결과가 같다.** 반경을 먼저 보면 반경 안에 있는 요청은 지도를 부르지 않아
+51 ms를 치르지 않는다. 지도는 반경 밖 요청에서만 필요하다.

구현 당시에는 결정 문서의 '코드 우선'을 그대로 따랐고 호출 비용을 몰랐다. 측정값이 나왔으므로
순서를 재검토할 근거가 생겼다. 검색 보충은 캐시가 더 맞아 500건·30분 캐시를 적용했다. 읍면동 경계는 거의 변하지 않는다.

변경 전에 담당자 합의가 필요하다. 반경 우선으로 바꾸면 반경 안에 있으면서 코드가 다른
요청이 `판정=RADIUS`로 기록되어 운영 로그의 의미가 달라진다.

## 7. 측정의 한계

- **하한 8.1 ms가 모든 수치에 섞여 있다.** k6가 컨테이너에서 호스트를 호출하므로 NAT 왕복이
  포함된다. 절대값은 이만큼 부풀려져 있고, 엔드포인트 간 비교는 유효하다.
- **VU 20은 커넥션 풀 10을 넘는다.** 포화 상태의 수치이며 쿼리별 비용은 VU 1 열로 봐야 한다.
- buffer pool이 기본 128 MB다. 데이터가 작아 전부 캐시되므로 디스크 I/O는 측정되지 않았다.
- 쓰기 경로(위치 인증, 신고 접수, 차단 등록)는 측정하지 않았다. 읽기 병목을 먼저 잡는다.
- 팀 공통값의 VU·지속시간·환경이 아직 비어 있다. 정해지면 같은 조건으로 다시 돌려야 하며,
  지금 수치는 다른 담당자 결과와 직접 비교하지 않는다.
- **제공자를 VWorld로 바꾼 뒤 3장을 다시 재지 않았다.** 3장은 지도 OFF 기준이라 제공자와 무관하다.
- **판정 단위를 법정동(읍면동)으로 바꾼 뒤 3장을 다시 재지 않았다.** 코드 길이만 10→8자리로 줄었고 쿼리·인덱스는 그대로라 DB 비용은 같다. 외부 호출 비용(5.1)도 같은 엔드포인트다.
- **3장의 부하 측정은 지도 OFF 기준이다.** VU 20·60초를 지도 ON으로 돌리면 한 회차에
  카카오 호출이 2만 건을 넘어 무료 쿼터를 소진하고 종량제로 청구된다. 외부 호출 비용은
  5.1의 +51 ms를 주변 동네·위치 인증·동네 검색 요청에 더해서 봐야 한다.
- 외부 호출 측정은 30회 표본이다. 카카오 쪽 지연 변동은 더 넓은 표본이 필요하다.
