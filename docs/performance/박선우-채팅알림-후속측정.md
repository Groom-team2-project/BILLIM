# 박선우 채팅·알림 후속 성능 측정

> 버전: v0.4.0
> 수정일: 2026.10.31

## 조건

- 기준 코드: `origin/develop` `93004f1` (병합된 PR #74까지 반영). 성능 변경은 `perf/chat-notification-followup` 작업 트리에서 단계별로 빌드했다.
- 환경: Windows Docker Desktop, 백엔드 Java 21 컨테이너 1개(메모리 제한 1GiB), MySQL 8.4. `billim-perf-followup` 독립 Compose 프로젝트. 운영 DB와 기존 `billim-perf` 볼륨은 사용하지 않았다.
- 목록 데이터: 회원 한 명이 소유한 채팅방 50개, 각 방의 문의 회원은 서로 다름. 목록 시험 시 메시지·연결 대여·알림은 없다.
- 목록 부하: k6 4 VU, 각 15초, 단계별·페이지 크기별 3회. 요청 사이 사용자당 0.4초 대기. 준비 호출 후 측정했다.
- DB 조회 수: 다른 부하를 멈춘 상태에서 요청 1건 전후 MySQL `Com_select` 차이를 3회 확인했다. 서버 전체 계수이며 이 시점에는 활성 WebSocket과 outbox worker가 없었다.
- 원본 k6 요약은 `docs/performance/tools/chat-notification/local/`의 `baseline-20261031-*`, `rental-once-20261031-*`, `batch-base-20261031-*`에 보관했다. 이 디렉터리는 Git 제외이며 세션 fixture도 포함하므로 공유하지 않는다.

## 채팅방 목록: 단계별 비교

1. **기준:** 방별 기본 정보·대여·접근 판정 조회를 그대로 수행.
2. **중복 대여 조회 제거:** 응답의 연결 대여를 조회한 결과를 전송 가능 거래 판정에도 재사용.
3. **기본 정보 일괄 조회:** 목록 페이지의 참여자·물건·상대 회원·마지막 메시지·미열람 수를 묶어 조회. 상세 조회의 기존 경로는 유지.

## 유휴 WebSocket의 DB 재확인

- 20개 방에 각 2명씩 WebSocket 연결(40개), 메시지 전송 없이 20초 유지. 연결이 안정된 뒤 10초 동안의 MySQL `Com_select` 차이를 3회 측정했다.
- 변경: 한 방의 재확인에서 마지막 순번을 연결마다 읽던 것을 방당 한 번만 읽는다. 연결별 세션·참여 권한 검사는 유지한다.

| 단계 | 10초 `SELECT` 증가 3회 | 중앙값 | 변화 |
| --- | --- | ---: | ---: |
| 변경 전 | 801 · 802 · 801 | 801 | — |
| 변경 후 | 701 · 701 · 702 | 701 | 12.5% 감소 |

각 회차의 40개 연결은 모두 성공했다. 이 시험은 단일 백엔드의 DB 재확인 경로를 측정했다. Redis 장애 시 누락 복구 시간이나 교차 서버 수신 p95의 개선을 입증하는 수치는 아니다.

## 메시지 전송: 부하별 잠금 병목 확인

- `chat-send`, 방 분산과 한 방 집중을 번갈아 실행. 16 VU는 15초, 64 VU는 10초, 각각 3회. 사용자당 요청 사이 0.2초 대기.
- 측정 중 Compose 설정 변경으로 백엔드가 재생성된 **초기 실행의 마지막 회차는 무효**로 제외했다. 설정을 고정한 `send-stable-20261031-*`와 `send-64-20261031-*`만 사용한다.

| 동시 사용자 | 분산 방 p95 중앙값 | 한 방 p95 중앙값 | 분산 방 요청률 중앙값 | 한 방 요청률 중앙값 |
| ---: | ---: | ---: | ---: | ---: |
| 16 | 19.49ms | 17.48ms | 73.99/s | 74.47/s |
| 64 | 31.63ms | 240.33ms | 290.56/s | 181.86/s |

모든 유효 회차의 전송 실패는 0건. 16 VU에서는 방 행 잠금 문제가 나타나지 않았지만, 64 VU가 한 방에 몰리면 p95가 분산 대비 약 7.6배이고 처리량이 약 37% 낮았다. 이 결과는 코드의 `findLockedById` 직렬화와 일치하지만, 방 행별 잠금 대기 시간을 직접 잰 것은 아니다. 순번·차단·제재 동시성 규칙을 보존할 설계 없이 잠금 위치나 저장소를 변경하지 않았다.

## 알림 outbox: 묶음 크기 비교

- Docker 컨테이너 `billim-perf-followup-benchmark`에서 같은 백엔드 이미지와 MySQL DB를 사용해 worker의 `OUTBOX_BATCH_SIZE`를 50과 100으로 차례로 적용했다. 각 설정에서 합성 `REPORT_RESOLVED` 사건 500건을 3회 적재했다. 모든 회차에서 알림 500건이 생성됐고, 컨테이너 종료 코드는 0이었다.
- `lag_p95_ms`는 사건 생성부터 처리 완료까지다. 사건 단위 처리량은 적체 500건이 소진될 때까지의 값이며, 일반적인 실시간 알림 처리량이나 사용자 요청의 HTTP 지연이 아니다.

| 묶음 크기 | 지연 p95 3회 | p95 중앙값 | 처리량 3회 | 처리량 중앙값 |
| ---: | --- | ---: | --- | ---: |
| 50 | 17509.4 · 15775.8 · 14882.8ms | 15775.8ms | 28.0 · 32.4 · 32.6건/s | 32.4건/s |
| 100 | 12154.0 · 10137.0 · 9361.2ms | 10137.0ms | 39.2 · 49.7 · 49.2건/s | 49.2건/s |

100으로 올리면 이 조건에서 지연 p95 중앙값은 **35.7% 감소**, 처리량 중앙값은 **51.9% 증가**했다. 설정을 환경 변수로 바꿀 수 있도록 했고 실험 컨테이너에 100을 적용했다. 운영 기본값은 50으로 유지한다. 한 묶음의 처리 시간이 현재 점유 시간 1분을 넘는 데이터 분포에서는 만료 후 다른 worker가 다시 획득할 수 있으므로, 운영 적용 전에는 실제 사건 종류·수신자 수·다중 인스턴스에서 점유 시간과 실패율을 확인해야 한다. 현재 측정의 100건 묶음은 1분 안에 완료됐다.

## 해석과 다음 단계

- 이번에 적용한 변경은 목록 응답과 WebSocket 재확인의 DB 조회 비용을 줄였다. MySQL에 메시지를 원본으로 저장하고 Redis 신호 유실을 DB 재확인으로 복구하는 구조는 유지한다.
- 목록 데이터에 메시지·대여가 없으므로 실제 대화가 많이 쌓인 계정과 연결 대여가 있는 방의 응답시간은 별도 조건으로 검증해야 한다. DB 조회 수 감소는 확인됐지만 운영 응답시간은 네트워크·데이터 분포·서버 크기에 따라 달라진다.
- 64 VU 한 방 집중 병목은 별도 설계 대상이다. 잠금 밖으로 권한 검사를 옮기면 차단·제재·물건 비공개와 동시 전송이 경합할 수 있다. 잠금 대기와 보유 시간을 구간별로 계측하고 정책의 원자성을 정의한 뒤 독립 변경으로 비교한다.
- 알림 적체가 실제로 발생하면 `OUTBOX_BATCH_SIZE=100`을 후보로 적용하고, 사건당 수신자 수와 점유 시간·실패율을 함께 관찰한다. 이번 합성 사건 500건 결과만으로 운영 기본값을 바꾸지는 않는다.
- 고부하만으로 판단하지 않는다. 낮은 부하는 실제 사용자의 응답시간, 중간 부하는 방 수에 따른 조회 비용, 높은 부하는 잠금·풀 포화가 시작되는 지점을 보여준다. 서로 다른 부하 수치를 한 표의 전후 효과로 섞지 않는다.

## 멀티 인스턴스 동작 검증

- 별도 Compose 프로젝트 `billim-perf-multi-20261031`와 [`compose.multi.correctness.yaml`](tools/chat-notification/compose.multi.correctness.yaml)에서 같은 JAR의 Spring Boot 서버 2개, 공유 MySQL 1개, 공유 Redis 1개를 실행했다. 서버별 HTTP 진입점을 고정해 어느 인스턴스로 요청했는지 알 수 있게 했다. 8개 방·16개 테스트 계정의 세션은 공유 DB에 저장했다.
- Docker 측정 컨테이너 `billim-perf-multi-20261031-benchmark`가 종료 코드 0으로 끝났다. 원자료는 [`raw/chat-followup-20261031/multi-instance.json`](raw/chat-followup-20261031/multi-instance.json)에 저장했다.

| 검증 | 조건 | 결과 |
| --- | --- | --- |
| 서버 간 채팅 전달 | A에서 전송 → B의 WebSocket, B에서 전송 → A의 WebSocket을 8개 방에서 각각 확인 | 16/16 수신, 지연 p95 142.1ms·최대 163.5ms |
| 같은 방 동시 전송 | 두 서버에 64건 병렬 전송 | 64건 모두 성공, 순번 3~66 중복·누락 없음, DB 응답과 일치 |
| 동일 메시지 키 재시도 | 같은 사용자·키로 A와 B에 동시 전송 | 두 HTTP 응답이 같은 메시지·순번, DB 행 1개 |
| 알림 작업자 병렬 실행 | 두 서버의 outbox worker를 켜고 사건 300건 투입 | 300건 완료, 알림 300개·전달 기록 300개, 누락·중복 없음, 5.66초 |

이 검증에서 발견된 원자성·동시성 오류는 없다. 다만 outbox 기록에는 처리 인스턴스 식별자가 없어 **두 worker가 각각 몇 건을 처리했는지**까지 증명하지는 못한다. 점유 시간 만료 중 재처리와 운영 데이터 분포는 이번 결과의 범위 밖이다. 단일 인스턴스 응답시간 개선 비율이 두 서버에서도 그대로 유지된다는 결론 역시 이 동작 검증만으로 낼 수 없다.

## Redis 장애·서버 재시작·10분 지속 부하

위와 같은 두 서버·공유 MySQL·공유 Redis 환경에서 Docker 컨테이너 `billim-perf-multi-20261031-resilience`를 실행했다. 컨테이너는 종료 코드 0, 결과 상태 `passed`로 끝났다. 원자료는 [`raw/chat-followup-20261031/multi-instance-resilience.json`](raw/chat-followup-20261031/multi-instance-resilience.json)에 저장했다.

| 상황 | 검증 결과 |
| --- | --- |
| Redis 중단 | Redis를 멈춘 동안 A가 전송한 3건을 B의 유지 중인 WebSocket이 모두 수신했다. 지연은 1,383.9·2,011.0·2,009.6ms로 2초 DB 재확인 경로와 부합한다. Redis 재시작 후 구독자 2개가 복구됐고 새 메시지도 수신했다. |
| 서버 B 재시작 | B를 멈춘 동안 A의 전송 1건이 성공했다. B 재시작 후 기록 조회에서 해당 메시지를 확인했고, 새 WebSocket의 실시간 수신도 성공했다. Redis 구독자 수는 다시 2개였다. |
| 지속 부하 | 두 서버에 24개 작업자가 10분간 8개 방으로 전송했다. HTTP 86,441건 모두 성공했고, DB 메시지도 86,441건이었다. 방별 순번 중복·누락은 없었다. 전체 p95 31.5ms, p99 53.0ms, 평균 약 144건/초였다. 매분 투입한 outbox 사건 400건은 모두 처리됐고 알림·전달 기록이 각각 400개였다. |

지속 부하의 분당 요청률은 전반 5분 약 148~150건/초에서 후반 5분 약 138~140건/초로 낮아졌다. 분당 p95도 전반 14~23ms에서 후반 37~40ms로 높아졌다. 오류나 순번 손상은 없었지만, 이 변화의 원인은 CPU·GC·MySQL 대기 시간 계측 없이 특정할 수 없다. 장시간 안정성을 더 확신하려면 운영과 비슷한 데이터 규모·자원 제한에서 더 긴 시험과 자원 지표를 함께 봐야 한다.

이번 장애 시험은 Redis 1회 중단·복구, 서버 B 1회 중단·재시작이다. 장애 중 outbox 점유 만료·재시도, 두 서버 동시 장애, 로드밸런서를 통한 실제 브라우저 재접속은 별도로 검증해야 한다. 서버가 중단된 사이의 메시지는 재접속 WebSocket 자동 재생이 아니라 **기록 조회로 복구되는지** 확인했다.

요약 원자료는 [`raw/chat-followup-20261031/summary.json`](raw/chat-followup-20261031/summary.json)에 저장했다. 이 파일에는 세션 토큰이 없다. 전체 백엔드 `./gradlew build --no-daemon`은 2026.10.31에 성공했다.

## 재현

```powershell
$env:COMPOSE_PROJECT_NAME = 'billim-perf-followup'
$env:PERF_PAIRS = '50'
$env:PERF_NOTIFICATIONS_PER_MEMBER = '0'
$env:PERF_SHARED_OWNER = 'true'
$env:PERF_FIXTURE_NAME = 'fixtures-followup.json'
python docs/performance/tools/chat-notification/seed.py
python docs/performance/tools/chat-notification/measure-room-list.py baseline-20261031
python docs/performance/tools/chat-notification/count-room-list-sql.py
python docs/performance/tools/chat-notification/measure-idle-queries.py idle-before-20261031
python docs/performance/tools/chat-notification/measure-send.py send-stable-20261031 --vus 16
python docs/performance/tools/chat-notification/measure-send.py send-64-20261031 --vus 64 --duration 10s
docker build -f docs/performance/tools/chat-notification/Dockerfile.outbox-benchmark -t billim-perf-followup-outbox-benchmark docs/performance/tools/chat-notification
docker run --name billim-perf-followup-benchmark --mount 'type=bind,source=/var/run/docker.sock,target=/var/run/docker.sock' --mount "type=bind,source=$((Resolve-Path docs/performance/tools/chat-notification).Path),target=/scripts" billim-perf-followup-outbox-benchmark
python docs/performance/tools/chat-notification/export-followup-results.py
```

각 코드 단계마다 백엔드 JAR을 다시 빌드하고 `billim-perf-followup`의 `backend`만 재생성한다. 동일한 결과 이름은 기존 요약을 재사용하므로 재측정 시 새 이름을 지정한다.
