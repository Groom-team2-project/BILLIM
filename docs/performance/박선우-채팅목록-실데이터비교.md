# 채팅 목록 메시지·대여·알림 포함 비교

> 버전: v0.11.0
> 수정일: 2026.11.04

## 문제

기존 목록 측정은 메시지·연결 대여·알림이 없는 방 기준. 실제 데이터가 있는 상태에서 권한 판정 및 대여 요약 일괄 조회의 효과 확인 필요.

## 조건

- 기준 백엔드: `8b11869`, 추가 최적화 미적용.
- 격리 프로젝트: `billim-perf-rich`. 기존 개발·운영 DB와 별도 MySQL 볼륨.
- 환경: MySQL 8.4, Java 21, 백엔드 메모리 제한 1GiB, outbox worker 비활성.
- 동일 소유자 방 50개, 방마다 메시지 200건·미열람 50건·대여 5건. 대여 상태 REQUESTED·APPROVED·ACTIVE·RETURNED·CANCELED 각 1건.
- 문의 회원별 알림 100건, 총 5,000건. 알림은 데이터 공존 조건이며 채팅 목록 요청에서 알림 API 동시 부하는 미적용.
- 페이지 크기 1·20·50, 4 VU, 사용자당 대기 0.4초, 30초씩 각 3회.
- 같은 DB를 재사용하고 테스트 중 메시지 전송·읽음 변경 미수행. 요청 전 준비 호출 및 요청당 SELECT 증가량 3회 수집.
- 버전별 응답 JSON 저장. 개선 후 기준 응답과 비교하여 대여·권한·미열람·목록 순서 보존 확인.
- 원본 결과와 세션 fixture는 Git 제외된 `tools/chat-notification/local/`에 저장. 세션 포함 fixture 공유 금지.

## 변경

- 목록 요청의 활성 동네·본인 제재 1회 조회, 상대방 차단 관계 일괄 판정. 같은 결과로 목록 접근과 썸네일 노출 판정.
- 페이지 전체 연결 대여 일괄 조회. 물건·소유자·요청자와 채팅방의 연결 조건 및 참여자 검증 유지.
- 대여 도메인의 기존 목록 사전 조회를 재사용하는 내부 일괄 요약 창구 추가. 회원·물건·점유·겹침 사전 조회. 요청별 승인 정책 검증은 기존 정책 호출 유지.
- HTTP API·DB 스키마 변경 없음. 상세 조회 및 전송 경로 변경 없음.

## 지연 증가 원인 조사 및 쿼리 수정 검증

- 기준·직전·현재 이미지의 Java 버전은 모두 `21.0.13+9`. 이미지 ID는 각 실행 원자료에 기록.
- 마지막 메시지 일괄 조회의 상관 서브쿼리에서 `max(sequence)` 집계를 메시지 행마다 반복하는 실행 계획 확인. 50개 방·10,000개 메시지에서 서브쿼리 실행 10,000회, 각 집계에서 해당 방의 200개 행 탐색.
- 같은 DB의 ID만 조회하는 진단 쿼리에서 기존 약 319ms, 방별 최대 순번을 먼저 집계하고 결합하는 쿼리 약 0.24ms 관측. 단일 SQL·단일 실행으로 API 개선율이나 확정 성능 수치로 사용 금지.
- 전체 엔티티 컬럼을 조회하는 두 쿼리의 추가 실행 계획과 SQL을 [진단 원자료](raw/chat-rich-query-diagnosis-20261103/explain.txt) 및 [SQL](raw/chat-rich-query-diagnosis-20261103/explain.sql)에 보존.
- `findLatestMessagesInRooms`를 방별 최대 순번 집계 결과와 메시지를 결합하는 네이티브 조회로 변경. 기존 `(room_id, sequence)` 유일 인덱스 활용. 스키마·API 계약 변경 없음.
- MySQL 회귀 테스트 추가: 여러 방에서 각 최신 메시지 한 건 반환, 빈 방·대상 외 방 제외, 메시지 본문 및 순번 보존.
- 진단 비교 순서: 과거 `original93004f1` → 직전 `baseline` → 현재 `optimized` → 쿼리 수정 `fixed` → `fixed` → `optimized` → `baseline` → `original93004f1`. 버전별 2회. 이번 실행은 병목 원인 확인용이며 기존 버전별 4회 측정과 분리.
- 기존 DB·동일 워밍업·DB/JVM 재시작·30초 측정 유지. 측정 구간별 performance_schema 쿼리 누적 시간·횟수·탐색 행 수 차이 및 DB/백엔드 cgroup CPU 카운터 수집. GC 프로파일 미수집.
- `fixed` 전체 `build` 성공, 테스트 986개·실패 0개·건너뜀 0개. 실행 컨테이너 `billim-perf-rich-diagnostic-benchmark` 종료 코드 0, 결과 `passed`, 8회 완료. 워밍업 제외 측정 요청 5,598건 실패 0건. 각 회차·크기별 준비 응답은 최초 기준 응답과 일치. [원자료](raw/chat-rich-diagnostic-20261103/result.json) 보존. 최신 메시지 쿼리 수정·측정 도구·원자료를 같은 개선 브랜치에 포함.

각 버전 2회 p95의 중앙값(두 값의 산술평균). 평균 응답시간도 20개에서 과거 119.79ms → 수정 53.49ms, 50개에서 279.58ms → 112.36ms로 감소. 이번 개선 이미지와 쿼리 수정 이미지는 최신 메시지 조회 변경으로 비교되며, 20개 p95 63.9%, 50개 66.1% 감소 관측.

SQL 수는 과거·직전·이번 개선·쿼리 수정 순으로 1개 26·25·26·26회, 20개 387·272·140·140회, 50개 957·662·320·320회. 쿼리 수정 전후 SQL 횟수는 동일하며 한 쿼리의 작업량 감소가 API 지연 감소와 함께 나타남.

50개 방 부하 중 performance_schema 누적 비용 차이:

- 기존 최신 메시지 쿼리: 실행당 평균 248.88·254.14ms, 실행당 탐색 행 수 약 2,010,000회.
- 수정 최신 메시지 쿼리: 실행당 평균 1.160·1.161ms, 실행당 탐색 행 수 약 100회. 탐색 행 수는 중복 접근을 포함한 MySQL 계수이며 서로 다른 데이터 행 수 아님.
- 쿼리 호출 수·탐색 행 수는 구간 시작·종료의 전역 누적 계수 차이로 경계의 진행 중 요청 영향 가능. 다른 부하 없이 격리 프로젝트에서 수집.

결론: 저번 기본 정보 일괄 조회에 들어간 최신 메시지 상관 서브쿼리가 메시지 누적 데이터에서 주요 병목으로 작동. 빈 방 측정에서는 드러나지 않았음. 방별 최대 순번을 먼저 집계한 뒤 기존 유일 인덱스로 메시지를 결합해 병목 축소. 권한·대여 요약 일괄 조회의 SQL 감소 효과 유지. 1개 방은 과거보다 소폭 느리므로 모든 크기에서 개선됐다고 주장하지 않음.

진단은 버전별 2회로 표본이 적고 호스트 OS 캐시는 유지. 앞선 4회 비교와 수치를 섞어 개선율 계산하지 않음. 운영 성능·통계적 유의성·최대 처리량으로 일반화 불가. CPU 카운터는 원자료에 보존했으며 GC 프로파일링은 미실행. 추가 테스트 미실행.
