# 채팅 목록 메시지·대여·알림 포함 비교

> 버전: v0.6.0
> 수정일: 2026.11.03

## 문제

기존 목록 측정은 메시지·연결 대여·알림이 없는 방 기준. 실제 데이터가 있는 상태에서 권한 판정 및 대여 요약 일괄 조회의 효과 확인 필요.

## 조건

- 기준 백엔드: `8b11869`, 추가 최적화 미적용.
- 격리 프로젝트: `billim-perf-rich`. 기존 개발·운영 DB와 별도 MySQL 볼륨.
- 환경: MySQL 8.4, Java 21, 백엔드 메모리 제한 1GiB, outbox worker 비활성.
- 동일 소유자 방 50개, 방마다 메시지 200건·미열람 50건·대여 5건. 대여 상태 REQUESTED·APPROVED·ACTIVE·RETURNED·CANCELED 각 1건.
- 문의 회원별 알림 100건, 총 5,000건. 알림은 데이터 공존 조건이며 채팅 목록 요청에서 알림 API 동시 부하는 미적용.
- 페이지 크기 1·20·50, 4 VU, 사용자당 대기 0.4초, 30초씩 각 3회.
- 같은 DB를 재사용하고 테스트 중 메시지 전송·읽음 변경 미수행. 요청 전 준비 호출 및 요청당 SELECT 증가량 3회 수집.
- 버전별 응답 JSON 저장. 개선 후 기준 응답과 비교하여 대여·권한·미열람·목록 순서 보존 확인.
- 원본 결과와 세션 fixture는 Git 제외된 `tools/chat-notification/local/`에 저장. 세션 포함 fixture 공유 금지.

## 변경

- 목록 요청의 활성 동네·본인 제재 1회 조회, 상대방 차단 관계 일괄 판정. 같은 결과로 목록 접근과 썸네일 노출 판정.
- 페이지 전체 연결 대여 일괄 조회. 물건·소유자·요청자와 채팅방의 연결 조건 및 참여자 검증 유지.
- 대여 도메인의 기존 목록 사전 조회를 재사용하는 내부 일괄 요약 창구 추가. 회원·물건·점유·겹침 사전 조회. 요청별 승인 정책 검증은 기존 정책 호출 유지.
- HTTP API·DB 스키마 변경 없음. 상세 조회 및 전송 경로 변경 없음.

## 한계

- 합성 데이터, 단일 PC·단일 백엔드 기준. 운영 지연 및 최대 처리량으로 일반화 불가.
- 사진 없는 fixture로 썸네일 권한 조회 개선 효과는 별도 확인 필요.
- 장시간 테스트는 Docker에서 실행 후 추적 중지. 후속 사용자 요청 시 종료 코드와 저장 결과 확인.

## 워밍업과 실행 순서 통제 재측정

- 기존 기준·개선 이미지 재사용. 실행 이미지 ID 결과에 기록. 측정 중 빌드 미수행.
- 순서: 기준 → 개선 → 개선 → 기준을 2회 반복. 버전별 4회, 총 8회.
- 매회 MySQL·백엔드 컨테이너 재생성. InnoDB 버퍼 풀 종료 시 저장 및 시작 시 복원 비활성. JVM은 새 프로세스로 시작.
- 매회 페이지 1·20·50개 각각 300건의 워밍업 요청을 4 VU로 수행. 총 900건, 워밍업 결과는 비교 지표에서 제외.
- 워밍업 완료 후 동일 순서로 크기별 30초·4 VU·대기 0.4초 측정. 요청당 SELECT 3회 및 응답 JSON 일치 확인.
- 업무 데이터는 기존 50개 방·메시지 10,000건·대여 250건·알림 5,000건 유지. 격리 fixture 세션만 회차별 만료 연장.
- 호스트 OS 파일 캐시는 초기화하지 않음. DB·JVM 재시작과 동일 워밍업 및 순서 교차로 영향을 줄이는 비교이며 완전히 동일한 CPU·캐시 상태를 보장하지 않음.
- 컨테이너: `billim-perf-rich-controlled-benchmark`. 실행 스크립트 `rich-controlled.py`, 측정 스크립트 `rich-controlled.js`. 최종 결과는 `local/rich-controlled-20261103-result.json`.
- 종료 코드 0, 결과 `passed`, 8회 모두 완료. 워밍업 제외 측정 요청 5,336건 실패 0건. 매회·크기별 준비 응답은 최초 기준 응답과 일치. [원자료](raw/chat-rich-controlled-20261103/result.json)에 이미지 ID·회차별 지연·요청 수·SQL 수 기록. 세션 토큰 미포함.

| 페이지 크기 | 평균 지연 중앙값 전 → 후 | p95 중앙값 전 → 후 | p95 변화 | SELECT/요청 전 → 후 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 15.83 → 16.79ms | 18.67 → 20.58ms | 10.2% 증가(+1.91ms) | 25 → 26 |
| 20 | 173.41 → 138.93ms | 216.88 → 169.19ms | 22.0% 감소 | 272 → 140 |
| 50 | 411.56 → 324.11ms | 498.03 → 398.61ms | 20.0% 감소 | 662 → 320 |

각 버전 4회 지표의 중앙값. 20개 방의 p95 범위는 기준 196.11~246.64ms, 개선 165.57~184.16ms. 50개는 기준 485.39~510.84ms, 개선 385.11~418.43ms. 두 크기에서 개선 버전의 모든 회차 p95가 기준 버전 모든 회차보다 낮음. SELECT 값은 같은 크기·버전의 모든 회차에서 동일.

워밍업을 맞추고 순서를 교차해도 20·50개 방의 지연 감소 유지. 목록의 반복 조회 감소에 따른 개선을 뒷받침하는 결과. 1개 방에서 초기에 관측한 66% 감소는 재현되지 않았으며 최종 개선 근거에서 제외. 1개 방은 일괄 조회 준비 비용으로 SQL 1회·p95 약 1.9ms 증가 관측. 이번 변경은 여러 방의 목록에 효과가 있으며 모든 크기를 빠르게 만드는 변경은 아님.

관측 요청률 중앙값은 1개 9.37 → 9.35/s, 20개 6.82 → 7.24/s, 50개 4.83 → 5.40/s. 사용자별 대기를 포함하므로 최대 처리량으로 해석하지 않음. 합성 데이터·단일 호스트 환경의 비교로 운영에서 동일 개선율이나 통계적 유의성 보장 불가.

## 재현 및 저장 범위

- 실행 준비와 재측정 절차: [도구 README](tools/chat-notification/README.md#워밍업-통제-목록-비교).
