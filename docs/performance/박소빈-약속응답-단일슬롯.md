# 박소빈-약속 변경 응답 단일 슬롯 조회 개선

## 1. 문제

- 약속 제안·수락·철회 성공 후 `getAppointments`로 전달·반납 두 슬롯 전체 조회.
- 응답에는 변경한 슬롯 하나만 포함하지만, 다른 슬롯의 확정·대기 제안과 장소까지 조회하는 비용.
- 회원·물건·대여 잠금 획득 후 응답 조립을 수행하므로 해당 조회도 명령 트랜잭션 안에서 실행.

## 2. 근거

| 항목 | 조건 |
| --- | --- |
| 측정일 | 2026.11.02 |
| 기준 코드 | `9751467`의 약속 서비스. 개선 전 계측 테스트 추가 후 실행 |
| 환경 | macOS arm64·Java 21.0.9·Testcontainers MySQL 8.4·단일 테스트 작업자 |
| 대상 | `AppointmentCommandService`의 정상 제안·수락·변경 제안·철회·재제안·확정 교체 |
| 데이터 | 소유자·요청자 각 1명, 동네 1개, 공용 장소 2개, 공개 물건·승인 거래 각 1건, 전달·반납 슬롯 각 1개 |
| 날짜 | 고정 현재 시각 `2026-10-09T15:00:00Z`, KST 시작일 10월 10일·종료일 10월 11일 |
| 시나리오 | PICKUP/RETURN × 다른 슬롯 비어 있음/확정·대기 제안 존재 = 4개. 각각 정상 명령 6개, 총 24개 구간 |
| 다른 슬롯의 제안 | 다른 공용 장소 사용. 실제 제안→수락→변경 제안으로 확정·대기 상태 구성 |
| 계측 | Hibernate `Statistics.getPrepareStatementCount()`. 명령 직전 초기화, 서비스 트랜잭션 커밋 직후 수집 |
| 제외 | 준비 데이터·사전 명령·별도 GET 비교·재전송·DB 후검증. HTTP·세션 인증·실제 채팅·알림 소비 미포함 |
| 성공 조건 | 전 구간 정상 성공, 변경 응답 전체와 별도 목록 조회의 해당 슬롯 일치, 버전·기존 확정·재전송·사건·멱등 기록 보존 |

- 개선 전후 같은 테스트 시나리오·고정 데이터·시각·DB 이미지 사용. 실행마다 새 MySQL 컨테이너, 각 시나리오 이후 데이터 정리.
- JDBC로 삽입한 준비 데이터와 검증 SQL은 Hibernate 계측 대상에서 제외.
- SQL은 Hibernate가 준비한 SELECT/INSERT/UPDATE/DELETE 문장 횟수. DB 서버 전체 실행 계수·HTTP 요청당 SQL과 구분.
- 전후 테스트 4개씩 성공. 정상 명령 24개씩 계측, 예상 충돌을 섞은 과거 [약속 동시 변경 측정](박소빈-약속동시변경.md)과 수치 직접 비교 제외.

## 3. 변경

- `AppointmentService.getAppointment`로 해당 대여의 지정 슬롯 하나만 조회·응답 조립.
- 전체 목록과 단일 슬롯의 응답 조립을 `toSlotResponse`로 공유. 활성 회원·거래 당사자 확인도 동일 메서드로 공유.
- 지정 슬롯이 해당 대여 소속인지 확인. 대기 제안 중복·확정 제안 참조 검증 유지.
- `AppointmentCommandService.complete`에서 전체 조회 후 필터링 대신 지정 슬롯 조회 호출.
- 명령에서 이미 읽은 슬롯·회원·대여는 같은 트랜잭션의 JPA 1차 캐시 활용. 변경 슬롯의 확정·대기 제안·장소 조회 방식 유지.
- 기존 전체 약속 GET은 두 슬롯 조회 유지. 새 HTTP API·DTO·DB·인덱스·인증 정책·잠금 순서·트랜잭션 경계 변경 없음.

## 4. 결과

### 정상 명령당 SQL

PICKUP과 RETURN에서 동일한 횟수 관측. 각 칸은 해당 조건의 단일 명령 계측값이며 평균·p95 아님.

| 명령 | 다른 슬롯 비어 있음: 전→후 | 다른 슬롯 확정·대기 존재: 전→후 |
| --- | ---: | ---: |
| 최초 제안 | 18 → 16 | 21 → 16 |
| 최초 수락 | 20 → 18 | 23 → 18 |
| 확정 후 변경 제안 | 20 → 18 | 23 → 18 |
| 변경 제안 철회 | 20 → 18 | 23 → 18 |
| 철회 후 재제안 | 20 → 18 | 23 → 18 |
| 기존 확정 교체 수락 | 22 → 20 | 25 → 20 |

- 다른 슬롯이 비어 있으면 2회, 확정·대기 제안이 있으면 5회 감소.
- 최초 제안 SQL 감소율: 11.1% / 23.8%. 최초 수락·철회: 10.0% / 21.7%.
- 다른 슬롯의 제안 유무로 발생하던 SQL 증가 제거. 변경 슬롯 자체의 상태에 따른 SQL 차이는 유지.
- 실행 시간은 계측하지 않음. 응답 지연·잠금 보유 시간·처리량 개선율 주장 제외.

### 검증

- 새 MySQL 통합 테스트: 전달·반납 × 다른 슬롯 2상태, 정상 명령 24개에서 별도 GET 응답 전체 동일성 확인.
- 변경 버전 증가·변경 제안 중 기존 확정 유지·철회 시 기존 확정 유지·재확정 시 이전 제안 SUPERSEDED 검증.
- 다른 슬롯 응답 불변·이후 상태 변경 후 최초 제안 멱등 재응답·사건 및 성공 기록 수 검증.
- 최종 회귀 테스트에 다른 슬롯 상태와 무관한 명령별 SQL 상한 16/18/20회 추가. 개선 전 기록은 상한 추가 전 수집.
- 단일 조회의 로그인·활성 회원·거래 당사자·슬롯 소속·제안 정합성 거부 테스트 추가.
- `backend/./gradlew build` 통과. 전체 테스트 971건, 실패·오류·건너뜀 0. 기존 동시 제안·멱등 재전송·롤백·권한 및 날짜 경계 검증 포함.

## 5. 한계

- 소규모 합성 데이터·서비스 통합 테스트 기준. 운영 부하·네트워크·프론트 체감 개선으로 일반화 불가.
- 명령마다 별도 트랜잭션 사용. 준비·조회에 사용한 영속성 컨텍스트를 명령에 재사용하지 않음.
- 잠금 범위·종류·순서 유지. SQL 감소만으로 경합 부하의 잠금 대기 감소를 입증하지 않음.
- 변경하지 않은 다른 슬롯의 제안 정합성 검사는 전체 약속 조회에서 수행. 명령 응답은 대상 슬롯만 검사.
- 슬롯별 제안·장소 조회 일괄 처리, 캐시, 인덱스 추가는 이번 범위에서 제외.
