# 채팅·알림 성능 지표와 병목 분석

> 버전: v0.1.6 · 수정일: 2026.10.21

## 범위와 완료 기준

- 범위: 박선우 담당 채팅·알림의 로컬 단일 인스턴스 성능. 채팅방 응답 변환 이슈 [#28](https://github.com/Groom-team2-project/BILLIM/issues/28)의 통합 테스트 보강 포함.
- 성능 개선 코드는 이번 측정에 포함하지 않음. 새 기술 도입은 팀의 아키텍처·보안 협의 후 별도 작업.
- 측정 시점: `test/chat-notification-performance` 브랜치 `3376b37`의 백엔드 코드. PR #48 반영, PR #49 미반영. PR #49는 채팅·알림 코드를 변경하지 않음. 이 문서와 신규 테스트는 측정 이후 추가.

## 기능 검증

- `ChatRoomViewFlowDbTest`에서 실제 MySQL로 채팅방 생성·상세·빈 목록·결과가 있는 목록, 연결 대여 요약, 제한 사유·기존 대여 예외, 응답 변환 실패 시 롤백을 검증했다. 단독 실행 3/3 통과, 전체 테스트 실행에서도 3/3 통과.
- `./gradlew build` 전체 실행은 740개 중 1개 실패했다. 실패는 이 변경과 별개인 `ItemRepositoryTest`의 테스트 회원 저장에서 `members.created_at`이 `NULL`이 된 데이터 제약 오류다. 전체 빌드 통과를 확인했다고 볼 수 없으며, 이 오류의 담당 도메인 수정 또는 확인이 필요하다.

## 환경과 방법

- Windows 11 Pro, Ryzen 5 5600X, RAM 32GB. Docker Desktop에 보이는 메모리 약 16GiB.
- `docs/performance/tools/chat-notification/compose.yaml`의 독립 `billim-perf` 프로젝트: 백엔드 1개(메모리 상한 1GiB), MySQL 8.4, k6 0.54.0. DB 볼륨 초기화 후 회원 16명·채팅방 8개·알림 800건 생성.
- HTTP 시나리오는 128 VU, 각 반복 뒤 0.2초 대기. 방 분산은 8개 방을 순환하고 집중은 1개 방을 공유. 같은 테스트 회원을 여러 VU가 재사용함.
- WebSocket은 VU마다 연결을 유지하며 메시지 10건을 전송. 알림 조회·채팅방 목록 시나리오는 반복마다 HTTP 요청 2개를 실행하므로 표의 처리 수는 요청 건수.
- WebSocket 행은 `3376b37` 백엔드 코드의 별도 실행 결과. 이 커밋에는 연결 공백 재전달 수정 `bb3c291`이 포함된다. `chat-websocket-stable`에서 128 VU가 소켓을 각각 1개 열고 `open` 직후 첫 메시지, 이후 200ms 간격으로 총 10건을 전송했다. 소켓 대기 한도는 5초, 별도 연결 완료 대기는 0ms. 10월 19일 문서의 수정 전 미수신 실행 및 수정 직후 재측정과 실행 시점·DB 상태가 달라 각각 별개 결과다.
- 처리량은 `성공 HTTP ÷ 설정 기간`이 아니라 k6 `http_reqs.rate`를 사용한다. 실제 요청 집계 구간에는 20초 부하 종료 뒤 진행 중인 요청의 완료 시간이 포함될 수 있다. 표의 `20초`는 설정 부하 기간이며 처리량 분모가 아니다.
- Prometheus는 관리 포트 `backend:9090`에서 5초 간격으로 수집. 관리 포트는 호스트에 공개하지 않음. MySQL `Innodb_row_lock_*`는 부하 전후의 전역 누적값 비교.
- 원본 k6 요약은 Git 제외 디렉터리 `docs/performance/tools/chat-notification/local/*2026-10-20.json`에 보관. DB·Prometheus 볼륨은 이후 초기화할 수 있으므로 이 표가 영속 측정 기록.

### 한 방 집중 p99 추가 측정

`billim-perf` MySQL 볼륨만 초기화하고 같은 16명·8개 방을 다시 생성했다. 128 VU·20초·한 방 집중 조건으로 연속 3회 실행했다. k6 `--summary-trend-stats`에 `p(99)`를 추가했으며 원본 요약은 Git 제외 `docs/performance/tools/chat-notification/local/chat-hot-room-p99-2026-10-20*.json`에 보관한다. 2·3회차는 DB를 다시 초기화하지 않았으므로 메시지 증가와 JVM 예열의 영향이 포함될 수 있다.

### 서로 다른 사용자·채팅방의 1:1 대화 측정 (2026.10.21)

- 같은 로컬 PC와 `billim-perf` 단일 백엔드에서 `3376b37`의 백엔드 JAR을 실행했다. 이 변경에 포함된 `chat-realistic` 측정 스크립트를 사용했다. 이전 성능 실행과 별도로 독립 MySQL 볼륨을 초기화하고 64개 방·128명·각각 다른 세션을 생성했다. 1개 방에서 5건을 보내는 사전 점검 후 64 VU 측정을 연속 3회 실행했으며 회차 사이 DB 초기화는 하지 않았다.
- VU 하나가 서로 겹치지 않는 방 하나를 담당한다. 각 방의 소유자는 HTTP로 메시지를 2초 간격으로 5건 전송하고 요청자는 WebSocket 연결을 유지하며 수신한다. 첫 전송은 소켓 연결 1초 뒤 시작한다. 총 64개 송신 세션과 64개 수신 세션, WebSocket 연결 64개, 회차당 메시지 320건이다. 전송 응답은 HTTP 201, 수신은 `clientMessageId` 일치로 검증한다. 수신 지연은 송신 직전부터 다른 계정의 소켓 수신까지 k6 내부 시계로 측정한다.
- 아래 처리량은 k6 `http_reqs.rate`의 실제 집계 구간 기준이다. 설정된 메시지 간격을 포함하므로 기존의 대기 0.2초 전송 집중 부하와 직접적인 처리 용량 비교값이 아니다. 원본 요약은 Git 제외 `docs/performance/tools/chat-notification/local/chat-realistic-64-2026-10-21-run*.json`에 보관한다.

### 방마다 두 참여자가 동시에 보내고 받는 측정 (2026.10.21)

- 사용자 피드백을 반영해 앞의 1방향 시나리오와 별도로 `chat-paired`를 만들었다. **방 1개에 2 VU**를 배정하고 두 회원이 각자 WebSocket을 유지하면서 HTTP로 2초 간격으로 5건씩 보낸다. 연결 3초 뒤부터 전송해 양쪽 소켓 준비 시간을 확보한다. 회차별 실행 식별자로 과거 메시지 재전달을 제외하고 `senderId`로 상대방 메시지를 구분한다.
- 64개 방·128명·128 VU, 총 전송 640건과 상대방 수신 640건을 회차마다 검증했다. 1개 방·2 VU 사전 점검 후, 같은 DB에서 3회 연속 실행했다. HTTP 실패, WebSocket 연결 실패, 전송 미완료 반복, 상대방 미수신이 모두 0이었다. `chat_delivery_ms`는 송신 직전부터 상대 계정의 소켓 수신까지 같은 k6 호스트 시계로 측정했다. k6 `http_reqs.rate`의 실제 집계 구간을 처리량 분모로 사용한다.

- **상대방 수신 p95 154.2~558.0ms, p99 208.2~782.2ms.** 128 VU보다 처리량은 약 두 배지만, 이는 활성 방과 2초 간격 송신 계정이 함께 두 배로 늘어난 결과다. 최대 처리 용량을 뜻하지 않는다. 256 VU 첫 회차의 긴 지연 원인도 분리되지 않았으므로 발표에는 3회 범위를 함께 제시한다.
- 전송 구간의 계획 속도는 `송신자 256명 ÷ 2초 = 128건/s`다. 실제 집계 처리량 102.4~110.0건/s에는 연결 뒤 3초 대기와 5건 전송 뒤 종료하는 시간이 포함된다. 따라서 이 차이를 서버 용량 부족으로 해석하지 않는다.
- 이 시나리오는 양쪽 사용자가 모두 동시에 보내고 받는 경우를 재현한다. 다만 2초마다 규칙적으로 보내는 합성 부하, 로컬 단일 인스턴스, 동일 PC의 부하 발생기이며 실제 이용자의 불규칙한 입력, 인터넷 지연, 브라우저 렌더링, 다중 인스턴스 전달은 포함하지 않는다.

| 10초간 MySQL `Innodb_row_lock_waits` 증가 | 2,062 | 2,403 | 집중 처리 건수가 훨씬 적어도 대기 횟수 증가 |
| 10초간 MySQL `Innodb_row_lock_time` 증가 | 5,513ms | 89,748ms | 동시 대기 시간의 합계가 집중 시 약 16배 |
| 20초 구간 Prometheus `hikaricp_connections_active` 최대 | 10 | 10 | 기본 풀 최대 10개 도달 |
| 20초 구간 Prometheus `hikaricp_connections_pending` 최대 | 18 | 71 | 잠금 대기가 커넥션 점유와 풀 대기로 전파된 정황 |

`ChatMessageSendService.send`는 `ChatRoomRepository.findLockedById`로 방 행에 배타 잠금을 건 뒤 중복 메시지 조회, 권한 판정, 순번 할당, 메시지 저장을 수행한다. 같은 방의 요청은 이 구간에서 직렬화된다. 낮은 CPU 사용률에도 한 방 집중의 응답 지연이 커진 점과 행 잠금·커넥션 대기가 이를 뒷받침한다.

단, `Innodb_row_lock_*`는 DB 전체의 누적 지표다. 이번 재측정에서 `chat_rooms` 행의 잠금 대기를 건별로 추적하지 않았으므로 **방 행 잠금이 주원인이라는 것은 코드와 집계 지표를 결합한 강한 추론**이다. Hikari 대기값은 Prometheus의 5초 표본 최대치이며 순간 피크를 놓칠 수 있다. 부하 발생기와 서버가 같은 PC를 공유하고 DB 메시지가 순차 테스트 중 쌓였으므로 배포 용량이나 엄밀한 전후 개선 효과로 해석하지 않는다.

채팅방 목록은 회원당 테스트 방이 1개뿐이어서 20~50개 방에서의 응답 변환 비용을 검증하지 못했다. `ChatRoomViewService.list`는 방마다 기본 정보, 연결 대여, 접근 제한, 허용 거래를 조회하므로 N+1 가능성을 별도 계측해야 한다. 알림 조회는 이번 조건에서 우선 병목이 아니며, outbox 적체 시 약 15초 지연은 사용자 알림 신선도 목표를 정한 뒤 평가할 문제다.

## 개선 방안과 선택 기준

| 우선순위 | 방안 | 적용 이유와 범위 | 해결하지 못하는 점·선행 조건 |
| --- | --- | --- | --- |
| 1, 다중 인스턴스 도입 시 | **Redis Pub/Sub**로 커밋된 채팅 이벤트를 모든 백엔드 인스턴스에 전파 | 현재 인스턴스 메모리의 소켓에만 브로드캐스트하는 구조의 다중 인스턴스 공백 해소. MySQL 메시지를 원본으로 유지하고 재연결 시 `afterSequence`로 복구 | Pub/Sub는 구독자가 없으면 이벤트를 보관하지 않음. [Redis 공식 문서](https://redis.io/docs/latest/develop/pubsub/)의 at-most-once 특성 고려. DB와 발행 사이 실패를 보완할 outbox/재조회 설계 및 인스턴스 간 중복 전달 처리 필요. **현재 방 행 잠금 병목은 해결하지 못함.** |
| 1, 현재 단일 인스턴스 병목 | **잠금 보유 구간 축소** 및 DB 연결 점유 분석 | 방별 순번은 유지하되 잠금 전 수행 가능한 조회와 잠금 후 반드시 재검증할 정책을 분리. 같은 방 128 VU에서 행 잠금 시간·Hikari 대기를 직접 낮출 후보 | 권한·차단·제재 변경과 전송의 경합, 중복 키 재시도, 방별 순서 정합성을 먼저 설계하고 회귀 테스트 필요. 새 스택 없이 현재 병목에 직접 대응 |
| 2, 알림 신선도 목표가 현재 15초보다 엄격할 때 | **Redis Streams**와 기존 MySQL outbox 연계 검토 | 소비자 그룹·재처리로 worker를 여러 개 운영할 수 있음. [Redis Streams 공식 문서](https://redis.io/docs/latest/develop/use-cases/streaming/)의 acknowledgment·pending 항목 활용 | MySQL 저장과 Stream 발행의 이중 쓰기, 중복 소비, 보존 기간, 운영 비용 설계 필요. 우선 현재 배치 크기·폴링·사건당 DB 쓰기 횟수를 계측·개선한 뒤 도입 판단 |
| 후순위, 여러 독립 소비자와 장기 보존 필요 시 | **Kafka** 검토 | 채팅·알림·분석 등 독립 소비자가 장기간 사건을 재처리해야 하는 요구에 적합 | 현재 1:1 채팅과 500건 outbox 측정만으로는 클러스터 운영 비용을 정당화하기 어려움. 방별 MySQL 잠금은 별도 해결 필요 |

기술 스택을 우선 검토하되 **관측된 단일 방 병목의 직접 해법과 다중 인스턴스 전달 해법을 분리**한다. Redis를 순번 원장으로 즉시 바꾸면 Redis와 MySQL의 이중 쓰기, 순번 누락, 커밋 순서 문제가 생긴다. 순번 저장소 변경은 API 커서 계약과 장애 복구 설계가 확정되기 전에는 적용하지 않는다.

## 다음 검증

1. 한 방 집중 128 VU와 8개 방 분산 128 VU를 동일 메시지 수·같은 초기 DB에서 각각 3회 측정. 처리량, HTTP p95, DB 행 잠금 대기, Hikari 대기를 함께 비교.
2. 잠금 구간별 실행 시간과 `chat_rooms` 대상 잠금 대기를 계측. 권한 판정을 잠금 밖으로 옮길 경우 상태 변경과 동시 전송 테스트 추가.
3. 회원당 채팅방 1개와 20·50개에서 방 목록 p95·SQL 수 비교. N+1이 확인되면 일괄 조회로 개선.
4. Redis Pub/Sub 채택 전 두 백엔드 인스턴스에 각 참여자를 연결해 전달·재연결·중복·인스턴스 종료를 검증. 접근 제한과 세션 철회 지연을 보안 담당자와 합의.
5. 알림 신선도 목표를 정하고 outbox 50·500·1,000건의 지연·실패·DB 쓰기 수를 같은 조건에서 반복 측정.
