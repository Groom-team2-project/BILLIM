# 채팅 멀티 인스턴스 로컬 비교

> 버전: v0.1.7\
> 측정일: 2026.10.26

## 목적과 구현

- DB 방식: `feat/chat-db-relay` (`d1ca768`). 각 서버가 자신에게 연결된 방을 250ms 간격으로 DB에서 확인.
- Redis 방식: `feat/chat-redis-relay` (`80836c6`). 커밋 뒤 Redis Pub/Sub으로 방 ID를 발행하고 각 서버가 DB에서 메시지를 확인. 동일한 250ms DB 재확인 경로 유지.
- 두 방식 모두 메시지 원본은 MySQL에 저장. 소켓별 마지막 전달 순번, 수신 권한 확인, 연결 직후 누락 복구는 동일.
- 공개 API와 DB 스키마 변경 없음. Redis 방식에만 Redis 의존성과 운영 연결 설정 추가.

## 측정 조건

- Windows 11 Pro, Ryzen 5 5600X, RAM 32GB. Docker Desktop 엔진 29.8.2, Docker에 12 논리 CPU와 약 15.58GiB 메모리 표시.
- 독립 Compose 프로젝트 `billim-perf-multi`: MySQL 8.4, Redis 7.4, 백엔드 2개(각 1GiB 제한), k6. DB 방식에서도 같은 Redis 컨테이너를 실행하되 사용하지 않음.
- 64개 채팅방, 128개 계정. 방별 2 VU. 소유자의 WebSocket은 A, 전송 HTTP는 B. 요청자의 WebSocket은 B, 전송 HTTP는 A.
- 각 VU는 연결 3초 후 2초 간격으로 5건 전송. 64 VU는 32개 방·320건, 128 VU는 64개 방·640건. 동일 PC에서 k6와 모든 서버 실행.
- **교차 서버 지연**: HTTP 전송 시작부터 해당 발신자의 반대 서버 WebSocket에 메시지가 도착할 때까지. HTTP 처리 시간 포함. `chat_cross_instance_delivery_ms`.
- `chat_delivery_ms`는 상대 사용자의 소켓까지의 시간이며 이 배치에서는 전송 HTTP와 같은 서버로 전달된다. 교차 서버 비교 지표로 사용하지 않음.
- HTTP 처리량은 k6의 실제 실행 시간 기준 `http_reqs/s`. 약 12초간의 짧은 부하이며 지속 처리량 아님.

## 후속 측정: 256 VU · 128개 방

각 방식마다 독립 DB 볼륨을 새로 만들고 128개 방·256개 세션을 시드했다. 2 VU 접속 확인 뒤 256 VU를 5회 실행했다. 첫 2회 값이 이후 회차와 크게 달라 준비 실행으로 구분하고, 3~5회를 비교한다. JVM·캐시 영향은 가능한 원인이지만 따로 분리 측정하지 않았다. 실행마다 각 VU가 5건을 보내므로 HTTP 전송 1,280건, 교차 서버 수신 1,280건이다. 모든 실행에서 HTTP 실패, WebSocket 연결 실패, 미완료 반복, 상대 미수신은 0건이었다.

준비 실행의 교차 서버 p95도 보존한다: DB 1회차 1.95초, 2회차 1.61초; Redis 1회차 964ms, 2회차 1.69초. **준비 실행 구분은 결과를 본 뒤 정했다.** 따라서 아래 3회 비교는 탐색적 결과이며, 사전에 정한 준비 기준으로 독립 재실행해야 한다.

| DB | 4 | 732.19ms | 857.47ms | 89.21ms | 106.43 | 41,619 | 41,196 |

교차 서버 p95의 실행별 중앙값은 DB 753ms, Redis 419ms로 Redis가 약 44% 낮았다. HTTP p95의 실행별 중앙값은 DB 89ms, Redis 315ms로 Redis가 높았다. `http_reqs/s`는 2초 간격으로 전송하는 이 시나리오의 관측 속도이며 최대 처리 가능 TPS가 아니다.

MySQL 조회 수는 DB 방식 4.2만, Redis 방식 5.4만 수준으로 Redis가 약 28% 많다. 모든 메시지를 DB에서 다시 확인하는 공통 경로에 Redis 신호가 추가 조회를 일으키는 구조와 일치한다. `Com_select`는 서버 전체 계수이므로 정확히 어느 코드 경로가 몇 회 실행됐는지는 별도 계측이 필요하다. `Innodb_row_lock_waits`도 실행별 변동이 커 병목을 단정하지 않는다.

측정 중 호스트 CPU 최고 표본은 DB 60.1%, Redis 62.0%, 호스트 RAM 사용률 최고 표본은 DB 74.8%, Redis 75.6%였다. 백엔드 컨테이너 메모리 최고 표본은 DB 645MiB, Redis 690MiB로 각 1GiB 제한에 도달하지 않았다. 표본 간격과 `docker stats` 호출 시간 때문에 짧은 CPU 피크는 놓칠 수 있다. 이번 조건에서 PC의 지속적인 CPU·메모리 포화는 관찰되지 않았다.

## 후속 측정: Redis 전달 경로 조정

기존 Redis 이미지 `billim-perf-redis`를 보존하고 별도 이미지 `billim-perf-redis-optimized`를 만들었다. 새 독립 DB에 같은 128개 방·256개 세션을 시드했다. 이전과 동일하게 2 VU 접속 확인, 준비 실행 2회, 비교 실행 3회를 진행했다.

- 커밋 후 로컬 WebSocket 전달과 Redis 신호 발행을 크기가 제한된 실행기로 예약해 HTTP 요청 흐름에서 분리.
- 로컬 커밋 메시지는 기존 응답을 사용해 직접 전달. 연결별 권한·순번 확인은 유지하고, 순번이 비면 DB 재조회.
- Redis 발신 서버가 자기 신호를 다시 처리하지 않도록 서버 식별자 추가.
- Redis 신호 누락 복구용 DB 확인 간격 250ms → 2초. 신호 유실 시 최악 복구 지연 증가 가능.

| 방식 | 비교 실행 | 교차 서버 p95 | HTTP p95 | HTTP 요청/s | MySQL `Com_select` 증가 | 전송/미완료 실패 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 기존 Redis | 3 | 419.09ms | 315.26ms | 107.44 | 53,684 | 0/0 |
| 조정 Redis | 3 | 1.00초 | 307.40ms | 92.54 | 32,867 | 0/0 |
| 기존 Redis | 4 | 401.04ms | 271.00ms | 109.00 | 53,551 | 0/0 |
| 조정 Redis | 4 | 364.00ms | 161.20ms | 109.79 | 32,566 | 0/0 |
| 기존 Redis | 5 | 504.29ms | 323.95ms | 91.93 | 54,129 | 0/0 |
| 조정 Redis | 5 | 468.09ms | 224.42ms | 103.71 | 32,828 | 0/0 |

실행별 중앙값은 HTTP p95 **315ms → 224ms(약 29% 감소)**, MySQL 조회 증가 **53,684 → 32,828(약 39% 감소)**. 교차 서버 p95는 **419ms → 468ms(약 12% 증가)**했다. 비교용 DB 방식의 중앙값은 HTTP p95 89ms, 교차 서버 p95 753ms다. 따라서 요청 응답은 개선됐지만 DB 방식 수준에는 도달하지 않았고, 교차 서버 지연의 이점은 남았으나 기존 Redis 방식보다 일관되게 좋아지지는 않았다.

조정 버전의 5회 모두 HTTP 1,280건 성공, 교차 서버 수신 1,280건 성공, WebSocket 연결 실패 0건. Redis 구독자 2개 확인. 예약 거부·신호 발행 실패 로그 없음. 비교 실행의 호스트 CPU 최고 표본은 59.3%, RAM 사용률 최고 표본은 72.8%, 백엔드 컨테이너 메모리 최고 표본은 680MiB다. PC의 지속적인 자원 포화는 관찰되지 않았다.

조정 요소 네 가지를 동시에 바꿨으므로 HTTP 개선과 교차 서버 지연 변동의 원인을 각각 확정할 수 없다. 2초 복구 간격은 Redis 장애 시 전달 지연을 늘리므로 별도 장애 시험이 필요하다. 이 결과만으로 운영 Redis 채택을 결정하지 않는다.

관련 단위 테스트 15개 통과, 수정 버전 JAR 빌드 통과. 전체 `./gradlew build`는 통합 테스트가 15분 이상 진행되어 중단했으며 통과 여부는 확인되지 않았다. 중단 전 변경 코드와 관련한 실패 출력은 없었다.

## 교차 서버 지연 구간 계측: 16 VU

2026.10.24 조정 Redis 코드에 진단 로그를 추가해 8개 방·16 VU·회차당 80건을 측정했다. 기존 128개 방 시드를 유지하고 앞의 8개 방만 사용했다. 두 백엔드와 k6는 같은 PC의 Docker에서 실행했다. 백엔드가 완전히 기동하기 전에 시작해 연결이 실패한 회차는 제외했다. 이후 첫 성공 회차를 결과 확인 후 준비 실행으로, 다음 두 회차를 비교 실행으로 분류했다. 부하가 작고 짧으므로 앞의 256 VU 결과를 대체하지 않는다.

- 발행 대기: DB 커밋 후 실행기 예약부터 작업 시작까지. 발행: Redis `convertAndSend` 호출 시간.
- 신호: 발행 호출 직전의 시각부터 다른 서버가 Pub/Sub 콜백을 시작할 때까지. 같은 호스트의 시스템 시계 사용. 발행 호출 시간도 포함.
- 재조회: 수신 서버에서 방 갱신 완료까지. 권한 검사, 마지막 순서 조회, 메시지 조회, WebSocket 전송으로 세분화.
- k6 교차 수신: HTTP 전송 시작부터 발신자의 반대 서버 소켓 수신 콜백까지. HTTP 처리 및 k6 콜백 지연 포함. **각 구간의 p95를 더해 전체 p95로 해석할 수 없음.**

| 회차 | 교차 수신 p95 | HTTP p95 | 발행 대기 p95 | 발행 p95 | Redis 신호 p95 | 수신 서버 재조회 p95 | HTTP/수신 실패 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 준비 | 832.1ms | 831.5ms | 49.7ms | 30.7ms | 40ms | 168.4ms | 각 0/80 |
| 비교 1 | 111.4ms | 82.1ms | 6.6ms | 5.6ms | 15ms | 31.1ms | 각 0/80 |
| 비교 2 | 134.2ms | 108.8ms | 7.1ms | 7.5ms | 21ms | 26.0ms | 각 0/80 |

수신 서버 재조회 중 실제 메시지를 1건 이상 전달한 호출만 집계했다. 비교 1·2의 재조회 내부 p95는 권한 검사 **18.5·17.0ms**, 마지막 순서 조회 **6.6·7.0ms**, 메시지 조회 **10.7·12.4ms**, 소켓 전송 **2.6·1.2ms**였다. Redis 발행 직전부터 구독 콜백 시작까지의 p95는 15·21ms로, 관측된 교차 수신 p95 전체를 설명하지 않는다. 이 값에는 Redis 호출과 구독 콜백 대기도 포함되므로 Redis 네트워크 시간만 나타내지는 않는다. 서버의 권한·DB 재조회와 HTTP 요청 처리 시간이 함께 기여한다.

준비 실행에서는 HTTP p95와 교차 수신 p95가 거의 같고, 다음 두 회차에서는 모두 크게 낮아졌다. 이 변화의 원인이 JVM 준비, DB 캐시, 동시 전송의 순간 집중 중 무엇인지는 이번 계측만으로 확정할 수 없다. 특히 k6의 동기 HTTP 호출과 WebSocket 콜백 처리 순서가 종단 지연에 영향을 줄 가능성도 남는다. 각 구간은 개별 로그의 분포이므로 동일 메시지의 시점별 지연을 연결한 값은 아니다. Redis 자체에 수백 ms가 필연적으로 소요된다는 가설은 이 조건에서 지지되지 않았다.

원본 k6 로그와 백엔드 진단 로그는 Git 제외 `tools/chat-notification/local/redis-diag-*20261024*`에 보관했다. 진단용 Redis 신호에는 발행 시각을 추가했으며, `chat.relay.diagnostics=true`인 로컬 실험 컨테이너에서만 구간 로그를 출력했다. 관련 단위 테스트와 JAR 빌드 통과.

## 재측정: 저부하 가동 확인 후 256 VU

같은 독립 DB와 진단용 Redis 이미지를 재사용했다. 두 백엔드의 HTTP 응답을 확인한 뒤 **2 VU·1개 방·10건**을 가동 확인용으로 실행했다. 전송·수신 실패 0건. 이 결과는 성능 비교에서 제외했다. 서버를 재시작하지 않고 256 VU·128개 방·회차당 1,280건을 4회 연속 실행했다. 각 회차의 HTTP, 교차 수신, 상대방 수신, WebSocket 연결, 반복 완료 실패는 모두 0건이었다.

| 256 VU 회차 | 교차 수신 p95 | HTTP p95 | 발행 대기 p95 | Redis 발행 p95 | 발행 직전→상대 구독 p95 | 수신 서버 재조회 p95 | 호스트 CPU 최고 표본 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1.07초 | 716.7ms | 346ms | 19.7ms | 541ms | 112ms | 88.7% |
| 2 | 500ms | 176.4ms | 259ms | 14.0ms | 122ms | 83ms | 66.1% |
| 3 | 334ms | 167.5ms | 139ms | 6.6ms | 77ms | 76ms | 60.0% |
| 4 | 490ms | 254.6ms | 182ms | 7.2ms | 57ms | 107ms | 58.6% |

2 VU 가동 확인 후에도 첫 **고부하** 회차의 지연이 가장 컸다. 다만 이후 세 회차도 교차 수신 p95가 334~500ms로 변동했다. 저부하 가동 확인만으로 256 VU 조건의 준비 상태를 보장할 수 없고, 이 결과에서 첫 고부하 회차를 사후적으로 제외해서는 안 된다. 4회 모두 기록하며 높은 지연의 원인을 추가 분석해야 한다.

첫 고부하 회차에는 발행 작업 대기 p95 346ms, Redis 발행 직전부터 구독 콜백 시작까지 p95 541ms가 관측됐다. 따라서 고부하 지연을 HTTP 저장 경로만으로 설명할 수 없다. 실제 `convertAndSend` 호출 p95는 19.7ms였다. Redis 서버 네트워크 시간과 구독 콜백 작업 대기를 분리하지 않았으므로 541ms 전체를 Redis 서버 처리 시간으로 해석할 수 없다. 수신 서버 재조회 p95도 76~112ms로 무시할 수 없다. 각 p95는 다른 표본 분포라 서로 더할 수 없다.

현재 [`ChatRedisRelayConfig`](../../backend/src/main/java/com/billim/domain/chat/controller/ChatRedisRelayConfig.java)는 구독 콜백 실행기를 지정하지 않는다. Spring Data Redis 4.1.1의 [공식 API 문서](https://docs.spring.io/spring-data/redis/reference/api/java/org/springframework/data/redis/listener/RedisMessageListenerContainer.html)에 따르면 기본값은 `SimpleAsyncTaskExecutor`다. 로그의 구독 작업 스레드 번호는 두 백엔드에서 각각 5,100을 넘었다. 회차당 다량의 콜백 작업 생성과 수신 서버의 동기 DB 재조회가 순간 집중 시 대기 시간을 키웠을 가능성이 있다. 인과관계는 실행기 설정만 바꾼 대조 실험으로 확인해야 한다. 진단용 건별 `INFO` 로그 자체도 고부하 지연에 영향을 줄 수 있다.

원본은 Git 제외 `tools/chat-notification/local/redis-diag-warmup-2-20261024*`, `redis-diag-high-256-20261024-run*`, `redis-diag-high-backend-*-20261024.log`에 보관했다. 기존 DB 데이터가 누적된 상태에서 실행했으므로 새 DB를 사용한 이전 256 VU 측정과 직접 비교하지 않는다.

## 구독 콜백 실행기 대조

Redis 구독 콜백에 **16개 스레드·대기열 1,024개의 `ThreadPoolTaskExecutor`**를 지정하고, 장시간 유지되는 구독 연결에는 별도 2개 스레드 실행기를 지정했다. 발행 실행기와 메시지 조회 로직은 그대로 두었다. 같은 진단 로그 설정과 256 VU·128개 방·회차당 1,280건 조건을 사용했다.

첫 시도에서는 2 VU 가동 확인 뒤 첫 256 VU 회차의 교차 수신 p95가 2.11초로 기준 2초를 초과했다. HTTP p95도 985ms였다. 전송·수신 실패는 0건. 이어진 회차는 교차 수신 p95 512ms, HTTP p95 226ms였다. 그다음 Docker Desktop이 종료돼 연속 측정이 중단됐다. 종료 원인은 확인하지 못했으며 애플리케이션 오류로 단정하지 않는다.

Docker 복구와 격리된 테스트 계정 세션 갱신 후, 각 이미지에서 **2 VU 가동 확인 → 버리는 256 VU 준비 회차 → 256 VU 측정 3회**를 적용했다. 두 이미지가 기존 DB를 순차 사용해 메시지가 누적됐으므로 완전히 동일한 초기 DB의 무작위 순서 A/B 실험은 아니다.

| 이미지 | 256 VU 준비 회차 교차 p95 | 측정 1 교차 / HTTP p95 | 측정 2 교차 / HTTP p95 | 측정 3 교차 / HTTP p95 |
| --- | ---: | ---: | ---: | ---: |
| 기본 구독 실행기 | 539ms | 455 / 176ms | 367 / 162ms | 397 / 228ms |
| 구독 스레드 풀 | 911ms | 485 / 223ms | 323 / 161ms | 446 / 259ms |

모든 측정 회차에서 HTTP 1,280건 성공, 상대방 수신 1,280건 성공, WebSocket 연결 실패와 미완료 반복 0건. 구독 스레드 풀의 작업 거부와 Redis 신호 처리 실패 로그도 없었다. 세 측정 회차의 교차 p95 중앙값은 기본 실행기 **397ms**, 스레드 풀 **446ms**로, **지연 개선은 입증되지 않았다**. 실행별 변동과 DB 누적 때문에 49ms 차이를 성능 악화로 확정하지도 않는다.

스레드 풀은 두 백엔드에서 각각 구독 콜백 스레드 이름 **16개**를 재사용했다. 기본 실행기의 구독 콜백 로그에는 백엔드마다 서로 다른 스레드 이름 **2,565개**가 관측됐다. 따라서 자원 사용의 상한을 두려는 변경 목적은 달성했다. 반면 측정 3회에서 발행 직전부터 상대 구독 콜백까지의 p95 중앙값은 기본 실행기 **74ms**, 스레드 풀 **35ms**였어도, 발행 작업 대기 p95 중앙값은 각각 **161ms**, **246ms**였다. 서로 다른 구간의 p95는 더할 수 없으며, 콜백 구간 개선이 전체 사용자 지연 개선으로 이어지지 않았다.

2 VU만 실행한 뒤의 첫 고부하 회차가 두 버전 모두 뒤 회차보다 느린 경향을 보였다. 2 VU는 가동 확인이지 고부하 준비가 아니라는 해석과 일치한다. 그러나 JVM JIT, 연결 풀 확장, DB 캐시, OS·Docker 자원 및 동기 전송 집중을 분리 계측하지 않았으므로 **JVM 워밍업을 단독 원인으로 확정할 수 없다**. 첫 고부하 회차를 숨기지 않고 준비 회차로 별도 표시한다. 이 데이터에서는 스레드 풀의 지연 개선보다 스레드 생성 제한 효과가 명확하다.

원본 k6·호스트 자원 로그는 Git 제외 `tools/chat-notification/local/redis-listener-pool-*20261024*`와 `redis-control-resume-*20261024*`, 서버 로그는 같은 위치의 `*-backend-*-20261024.log`에 보관했다. 관련 단위 테스트와 JAR 빌드 통과. 전체 Gradle 빌드는 이번 대조 실험에서 실행하지 않았다.

## 전송 시점을 흩뜨린 256 VU 측정

구독 스레드 풀 이미지에서 256 VU·128개 방·회차당 1,280건을 유지했다. 기존 `chat-paired`는 연결 3초 후 전원이 2초 간격으로 전송한다. 새 `chat-paired-jitter`는 VU별 첫 전송을 연결 후 **2~4초**, 이후 전송을 **1.5~2.5초** 간격으로 무작위 배치한다. 두 시나리오 모두 사용자당 5건, 방당 양쪽 10건, HTTP 교차 서버 전송과 WebSocket 수신 조건은 동일하다. 2 VU 연결 확인과 256 VU 무작위 시나리오 준비 회차를 결과에서 제외했다. 이후 같은 서버에서 **고정→무작위→무작위→고정** 순서로 비교했다.

| 시나리오 | 회차 | 교차 수신 p95 | HTTP p95 | 실제 HTTP 요청/s | 발행 작업 대기 p95 | 수신 서버 재조회 p95 | MySQL 행 잠금 대기 누적 / 횟수 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 고정 2초 | 1 | 471ms | 300ms | 102.6 | 274ms | 87ms | 1,307ms / 54회 |
| 무작위 | 1 | 22ms | 13ms | 94.5 | 0.2ms | 8ms | 12ms / 3회 |
| 무작위 | 2 | 26ms | 16ms | 95.0 | 0.2ms | 9ms | 4ms / 3회 |
| 고정 2초 | 2 | 568ms | 325ms | 104.6 | 248ms | 124ms | 4,850ms / 156회 |

네 회차 모두 HTTP 1,280건과 상대방 수신 1,280건 성공, WebSocket 연결 실패·미완료 반복 0건. 고정 조건과 무작위 조건의 평균 요청 속도가 약 9% 달라지는 영향을 분리하려고, 전송 간격만 **2.2초**로 늘린 고정 시나리오도 두 번 실행했다. 이 경우 HTTP 요청/s는 **99.3·97.8**, 교차 수신 p95는 **570·488ms**, 발행 대기 p95는 **290·191ms**, MySQL 행 잠금 대기는 **1,339ms/38회·1,806ms/56회**였다. 무작위 조건과 평균 요청 속도를 가깝게 해도 고정 시점의 지연이 유지됐다.

이 결과는 기존 0.3~0.5초 p95의 상당 부분이 **256명이 2초마다 동시에 보내도록 만든 순간 집중**에서 나온다는 해석을 강하게 지지한다. 고정 조건에서는 같은 방의 두 회원 전송도 시간상 겹치고 MySQL 행 잠금 계수와 발행 작업 대기가 커졌다. 코드의 방 행 잠금이 그 원인일 가능성이 있지만 MySQL 전역 계수만으로 특정 테이블을 확정할 수는 없다. 무작위 조건에서는 그 대기가 크게 줄었다. 다만 무작위 시나리오는 동기 HTTP 호출 완료 뒤 다음 타이머를 예약하므로 전송 완료가 느릴 때 다음 요청도 밀린다. 또한 로컬의 짧은 2회 측정이며 다른 네트워크·트래픽 분포·장기 연결을 대표하지 않는다. **무작위 조건 p95 22~26ms를 운영 환경의 예상값으로 사용하지 않는다.**

재현: `python docs/performance/tools/chat-notification/measure-multi.py redis-listener-pool 256 <실행명> --case chat-paired-jitter`. 고정 간격 대조에는 기본 `--case chat-paired`, 평균 속도 비교에는 `--paired-interval-ms 2200` 사용. 원본 k6·호스트 자원 로그는 Git 제외 `tools/chat-notification/local/jitter-*20261024*`, `fixed-control-*20261024*`, `fixed-matched-*20261024*`, 서버 계측 로그는 `paired-jitter-backend-*-20261024.log`에 보관했다.

## 무작위 전송 시점의 DB 중계·Redis 중계 비교: 2026.10.26

앞 절에서 Redis 방식만 측정한 무작위 전송 시나리오를 DB 방식에도 동일하게 적용했다. 각 방식에서 백엔드 2개, 128개 방, 방당 양쪽 사용자 1명씩 256 VU, 사용자당 5건으로 회차당 HTTP 전송 1,280건을 수행했다. 발신자의 WebSocket은 HTTP 전송 서버와 다른 서버에 연결했다. 첫 전송은 연결 후 무작위 2~4초, 이후 전송은 이전 HTTP 완료 후 무작위 1.5~2.5초에 시작한다. 각 이미지에서 2 VU 가동 확인 1회, 256 VU 준비 1회를 먼저 실행하고 **사전에 정한 측정 3회**만 아래에 표시했다. 같은 PC와 Compose 프로젝트의 기존 DB·테스트 계정·부하 스크립트를 사용했다. 실행 순서는 **DB → 조정 Redis → 초기 Redis → DB 재측정**이다. 방식 전환 시 백엔드만 재생성하고 DB 볼륨은 유지했다.

| DB | 1 | 629ms | 705ms | 16.83ms | 93.77 | 43,589 | 각 0/1,280 |
| DB | 2 | 601ms | 660ms | 14.07ms | 95.27 | 44,754 | 각 0/1,280 |
| DB | 3 | 583ms | 636ms | 13.04ms | 95.44 | 44,849 | 각 0/1,280 |
| 조정 Redis | 1 | 45ms | 70ms | 27.29ms | 95.66 | 32,903 | 각 0/1,280 |
| 조정 Redis | 2 | 26ms | 49ms | 15.09ms | 96.30 | 32,957 | 각 0/1,280 |
| 조정 Redis | 3 | 20ms | 26ms | 12.39ms | 95.96 | 32,911 | 각 0/1,280 |

모든 측정에서 WebSocket 연결 실패 0/256, 미완료 반복 0/256. 실행별 교차 수신 p95의 중앙값은 **DB 601ms → 초기 Redis 30ms → 조정 Redis 26ms → DB 재측정 631ms**였다. 초기 Redis는 DB 폴링 250ms를 유지하고 Redis 신호를 추가한 버전이다. 따라서 순서를 뒤집어 DB를 다시 측정한 뒤에도 남는 약 0.6초와 0.03초의 차이는 **Redis 신호의 낮은 지연 효과**를 뒷받침한다. 한편 초기 Redis는 MySQL 조회 증가 중앙값이 **44,754건 → 56,736건(약 27% 증가)**, HTTP p95가 **14.07ms → 21.09ms**로 비용도 늘었다. 조정 Redis에서는 조회 증가 중앙값이 **32,911건**, HTTP p95가 **15.09ms**였다. 관측 HTTP 요청 속도 중앙값은 DB **95.27/s**, 초기 Redis **94.96/s**, 조정 Redis **95.96/s**로 가까웠다. 따라서 **멀티 인스턴스 실시간 전달을 위해 Redis 중계를 검토할 성능 근거는 확보했다.**

다만 **초기 Redis와 DB의 비교는 Redis 신호 추가 효과**, **조정 Redis와 초기 Redis의 비교는 여러 전달 로직 조정 효과**를 나타낸다. 조정 Redis에는 커밋 후 비동기 발행·로컬 직접 전달·자기 신호 무시·2초 DB 복구 폴링·구독 실행기 풀이 함께 들어 있다. 따라서 조정 Redis의 조회 감소나 HTTP p95 차이를 Redis 서버 자체만의 효과로 귀속할 수 없다. 동일 DB에 메시지가 누적됐고 각 이미지의 JVM 준비·캐시 효과도 완전히 분리하지 않았다. 매 회차 10여 초의 로컬 단기 부하이며, 송신 완료 후 다음 전송을 예약하는 사용자 시나리오다. 운영 네트워크, 장시간 연결, Redis 장애·재연결 시 전달 복구는 검증하지 않았다. 원본 k6·자원·MySQL 기록은 Git 제외 `tools/chat-notification/local/{db-jitter,redis-jitter,redis-baseline-jitter}-*20261026*`에 보관했다.

## 측정 중 확인한 문제와 한계

- 최초 k6 출력의 `chat_delivery_ms`는 교차 서버가 아닌 로컬 상대방 전달이었다. 교차 서버 누락은 확인했지만 지연은 확인하지 못했다. `chat_cross_instance_delivery_ms`를 추가한 뒤 재측정했고 위 표에는 수정 후 결과만 사용.
- Redis 서버의 Pub/Sub 구독자 2개 확인. Redis 메시지에는 방 ID만 포함하고 실제 내용은 DB에서 조회.
- Redis 실행 중 WebSocket 종료 직후 재확인 작업이 닫힌 소켓을 확인하며 경고를 남겼다. 이번 실행의 미완료 반복은 없었으나 로그 소음 개선 대상.
- 64 VU는 각 방식 1회, 128 VU는 각 방식 2회. 실행 순서와 이전 메시지 수가 완전히 같지 않다. 같은 방의 기존 메시지는 소켓 연결 시 현재 순번으로 건너뛰지만, DB 캐시·JVM 상태·PC 자원 편차는 남는다.
- 2초 간격의 동기화된 전송으로 실제 사용자 트래픽보다 순간 집중이 크다. 장기 연결, 장애 중 Redis 재연결, 프로세스 재시작 복구는 측정하지 않았다.
- HTTP 성공 메시지만 교차 지연에 포함. 미완료 반복과 HTTP 실패는 별도 지표로 확인.

저장소 루트에서 각 브랜치의 `backend/` JAR을 만든 뒤 해당 이미지 이름으로 `docker build -t billim-perf-db backend` 또는 `docker build -t billim-perf-redis backend`를 실행한다. 두 이미지를 모두 만든 뒤 각 방식마다 아래 순서로 진행한다. `local/fixtures.json`이 이미 있으면 먼저 별도 보관한다.

```powershell
$env:PERF_IMAGE = 'billim-perf-db' # Redis 측정에서는 billim-perf-redis
docker compose -f docs/performance/tools/chat-notification/compose.multi.yaml up -d mysql redis backend-a backend-b
$env:PERF_PAIRS = '128'
$env:PERF_NOTIFICATIONS_PER_MEMBER = '0'
python docs/performance/tools/chat-notification/seed-multi.py
python docs/performance/tools/chat-notification/measure-multi.py db 256 db-256-1
```

두 백엔드의 `/api/v1/auth/csrf`가 준비된 다음 시드한다. 시드 커밋 후 CSRF 확인만 실패하면 `seed-multi.py --refresh-csrf`로 복구한다. 방식 전환 전 `docker compose -f docs/performance/tools/chat-notification/compose.multi.yaml down -v`로 **독립 `billim-perf-multi` DB만** 초기화하고, `fixtures.json`을 보관한 뒤 다른 이미지로 다시 시작한다. Redis 측정은 `measure-multi.py redis 256 redis-256-1` 형식으로 실행한다.
조정 버전은 `billim-perf-redis-optimized` 이미지와 `measure-multi.py redis-optimized 256 redis-optimized-256-1`을 사용한다. 원본 로그·호스트 자원 표본·MySQL 계수는 모두 Git 제외 `local/`에 보관한다.
