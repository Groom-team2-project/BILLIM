- 편차는 3회 구간 지표의 모집단 표준편차와 최솟값~최댓값으로 표기. p95 중위값은 원본 요청 전체를 합친 p95와 다름.
- 응답 시간은 해당 구간 전체 HTTP 응답 기준. 승인 성공·예상 충돌·서버 오류가 섞인 경우 각각의 성공 지연과 동일하게 해석하지 않음.
- p50 또는 p95의 회차 최댓값/최솟값이 2배를 넘으면 공통 양식의 큰 편차 원칙에 따라 시간 기반 집계를 비움. 개별 원본은 유지.
- SQL은 드라이버·인증·권한 확인을 포함한 앱 계정의 DB 실행 횟수. 실패 시 롤백된 DML 실행도 포함하며 커밋 행 수와 다름.
- 시간 구간 양끝의 계정 누적 카운터 차이를 사용. SQL 준비·후검증은 별도 root 계정으로 실행, outbox 소비 비활성·요청 만료 주기 24시간·인증 정리 cron 비활성으로 주기 작업 혼입 억제.

동시 요청 분포: 각 회차 수락 성공 7, 15, 8건 / 철회 성공 13, 5, 12건. 약속별 성공 1건·VERSION_CONFLICT 1건 기대.

DB 후검증: 1회 통과, 2회 통과, 3회 통과.

Actuator 표본 수: 1회 1개, 2회 1개, 3회 1개. 구간별 원문 첫·마지막 표본 및 CPU·힙·연결 지표 시계열은 원본 관측 JSON에 보관. 짧은 경쟁 시험의 표본은 순간값으로만 해석.

## 3. 해석과 한계

- 현재 코드의 반복 관측 및 정합성 결과. 코드 최적화·개선 효과 판정은 수행하지 않음.
- 예상 409는 업무 충돌이므로 예상 밖 오류와 분리. 기본 http_req_failed는 예상 409도 포함.
- 부하 도구·서버·DB는 같은 PC, 다른 컨테이너와 자원 공유. 측정 중 추가 빌드·기능 테스트는 수행하지 않음. 운영 환경으로 일반화 불가.
- 짧은 경쟁·재전송 시험의 요청률은 최대 처리량이 아님. VU 수와 HTTP batch 동시 연결 수는 구분.
- 주기 작업을 억제한 전용 환경이므로 실제 주기 작업이 동작하는 운영 상황과 차이. 인증·API·DB 구조는 변경하지 않음.
