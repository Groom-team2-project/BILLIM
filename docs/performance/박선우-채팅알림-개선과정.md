# BILLIM 채팅·알림 성능 개선과 장애 대응

> 작성일: 2026.11.16 · 박선우 담당 사례

## 프로젝트 구조와 데이터의 위치

BILLIM 백엔드는 채팅·알림·대여 등 도메인을 한 Spring Boot 애플리케이션 안에서 나눈 모놀리스다. 멀티 인스턴스 검증은 같은 애플리케이션을 두 대에 띄운 것이다. 채팅과 알림을 독립 서비스로 배포하는 MSA와는 구조가 다르다.

| 구성 | 보관하거나 처리하는 것 |
| --- | --- |
| Spring Boot 백엔드 | HTTP 요청 처리, 자신에게 연결된 WebSocket과 연결별 전달 상태 관리 |
| MySQL | 메시지 본문·방별 순번, 알림 처리용 outbox 등 영속 데이터 |
| Redis Pub/Sub | 커밋된 메시지가 있다는 신호를 서버 간에 전달 |
| 브라우저 | WebSocket으로 새 메시지 수신, 재연결 시 마지막으로 받은 순번 이후 기록 조회 |

예를 들어 발신자가 A 서버로 메시지를 보내고 수신자가 B 서버에 연결돼 있으면, A가 MySQL에 저장한 뒤 Redis로 신호를 보낸다. B는 그 신호를 받고 MySQL에서 필요한 메시지를 읽어 자신의 WebSocket으로 전달한다. 서버가 재시작되면 연결은 끊기지만 DB에 커밋된 메시지 기록은 남는다. 열린 소켓은 서버가 보유하는 상태이므로 발표에서 서버를 완전히 무상태라고 표현하지 않는다.

## 채팅 목록 병목을 찾은 과정

1. **첫 가설.** 목록에 방이 많을수록 권한과 대여 정보의 반복 조회가 늘어났다. 여러 방의 데이터를 한 번에 가져오면 DB 왕복이 줄고, 방이 많은 페이지에서 효과가 클 것으로 예상했다.
2. **예상과 다른 결과.** 빈 채팅방에서는 병목이 잘 드러나지 않았다. 실제 사용을 흉내 내 메시지가 쌓인 데이터로 오래된 버전까지 복원해 비교하니, SQL 실행 횟수가 줄었는데도 과거 버전보다 목록 응답이 느린 구간이 있었다. HTTP p95로 회귀를 감지하고 SQL별 비용을 조사했다.
3. **원인과 다음 가설.** MySQL 실행 계획에서 최신 메시지 조회가 메시지 행마다 해당 방의 최대 순번을 다시 계산하는 것을 확인했다. 50개 방·메시지 1만 건에서 내부 집계가 1만 번 실행됐다. 방마다 최대 순번을 먼저 한 번 구하고 기존 `(room_id, sequence)` 인덱스로 메시지를 찾으면, 쿼리 호출 횟수가 같아도 반복 탐색 비용을 줄일 수 있다고 판단했다. 구현 전 가설은 작업량이 감소한다는 것이었고, API 개선율은 실험으로 확인했다.
4. **변경과 검증.** 최신 메시지 조회를 방별 집계 후 결합하는 방식으로 수정했다. 같은 DB에서 워밍업과 실행 시간을 맞추고, 버전 순서를 정방향·역방향으로 바꿔 측정했다. 회차별 HTTP 응답과 준비 호출의 응답 내용도 대조했다.

| 50개 방 기준 | 쿼리 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 채팅 목록 HTTP p95 | 425.17 ms | 144.34 ms |
| 최신 메시지 쿼리 실행당 평균 | 약 249~254 ms | 약 1.16 ms |
| 해당 쿼리 실행당 탐색 행 수 | 약 201만 회 | 약 100회 |
| 측정 구간 SQL 실행 수 | 320회 | 320회 |

쿼리 수정 직전 대비 50개 방 p95는 **66.1% 감소**했다. 더 오래된 버전의 314.77 ms를 기준으로 하면 **54.1% 감소**했다. 1개 방에서는 오래된 버전보다 1.75 ms 느렸다. 동일 진단 실험에서 버전별 두 회를 비교한 로컬 결과이며, 탐색 행 수는 중복 접근을 포함한 MySQL 계수다. 전체 5,598개 측정 요청에서 HTTP 실패는 없었다. 운영 성능과 최대 처리량은 별도 검증 대상이다. [비교 실험과 실행 계획](박선우-채팅목록-실데이터비교.md)

## Redis를 적용한 이유와 장애 대응

여러 서버에서 DB 재확인 주기만 기다리면, 저장이 끝난 뒤에도 상대 서버가 새 메시지를 알아차릴 때까지 대기가 생긴다. 커밋 직후 Redis 신호를 보내면 이 대기 구간을 줄일 수 있다고 예상했다. 로컬에서 전송 시점을 분산한 동일 시나리오의 교차 서버 수신 p95는 DB 방식 **601 ms**, 초기 Redis **30 ms**, 조정 Redis **26 ms**, DB 재측정 **631 ms**였다. 256명이 같은 주기로 몰려 보내는 실험에서는 더 긴 지연도 관측됐다. 발표에서는 HTTP 응답 시간과 WebSocket 수신 시간이 다른 지표라는 점, 수치가 전송 패턴에 따라 달라졌다는 점을 함께 설명한다. [멀티 인스턴스 비교](채팅%20멀티%20인스턴스%20비교.md)

| 검증 상황 | 복구 경로와 실제 결과 |
| --- | --- |
| 실행 중 Redis 약 32초 중단 | 신호는 재생되지 않는다. 수신 서버가 약 2초 간격으로 DB를 다시 확인했다. 전송 4건 모두 저장·교차 서버 수신 성공. 이번 실험의 HTTP 시작부터 수신까지 172~1,907 ms. DB 조회 시간이 더해지므로 2초를 복구 상한으로 보장할 수 없다. |
| 수신 서버 B 재시작 | 기존 소켓이 끊겼고, 재연결만으로 과거 메시지가 자동 재생되지 않았다. 마지막 순번 이후를 `afterSequence`로 조회해 중단 중 메시지 1건을 확인했다. |
| MySQL 중단 | 메시지 저장 실패, HTTP 500이 약 58초 뒤 반환됐다. Redis 신호와 별개로 저장소 장애의 실패 응답 시간은 개선 대상으로 남았다. |
| 별도 10분 지속 부하 | 두 서버에 24개 작업자가 8개 방으로 전송한 HTTP 86,441건과 DB 메시지 수가 일치했다. 방별 순번 중복·누락이 없었다. 별도로 투입한 outbox 400건도 모두 처리됐다. |

실행 중 Redis가 끊기는 경우와 Redis가 없는 상태에서 서버를 시작하는 경우는 구분한다. 배포 문서상 Redis 사용 설정이 켜져 있으면 Redis가 없는 상태에서 서버 기동이 막힐 수 있다. 이때 Redis를 끄고 기동하면 서버 간 전달이 DB 재확인에 의존한다. Redis를 사용하는 WebSocket 연결권 모드도 장애 시 발급 경로가 영향을 받으므로, 그 모드의 신규 연결과 기존 소켓의 복구는 따로 검증한다. ## 도구와 지표로 무엇을 설명할지

| 도구·모듈 | 사용한 목적 |
| --- | --- |
| k6, Docker Compose | 로컬 격리 환경에서 HTTP 전송과 WebSocket 수신을 관측하고, 동일 조건으로 버전 비교 또는 장애 재현 |
| MySQL 실행 계획, `performance_schema` | 느려진 SQL의 반복 집계 확인, 실행 시간·횟수·탐색 행 수 비교 |
| Spring WebSocket, Spring Data Redis | 브라우저 실시간 연결 유지, 서버 간 메시지 커밋 신호 전달 |
| Spring Boot Actuator, Micrometer, Prometheus, Grafana | 애플리케이션 지표 노출, 수집·저장 및 시각화. 코드에서 알림 outbox의 상태별 건수 지표 확인 |

여기서 **lag**는 구체적인 대기 구간으로 정의한다. 채팅은 시험 도구의 시계를 기준으로 **전송 요청 시작부터 상대 WebSocket 수신까지**, 알림은 **이벤트가 처리 대기 상태가 된 시점부터 처리 완료까지**다. 채팅 수신 지연은 기존 부하 시험에서 측정했다. 아래 운영 지표는 후속 제안이다.

- **채팅 전달 지연과 누락 복구** — 교차 서버 수신 p95·p99, DB 재확인으로 받은 메시지 수, 재연결 후 순번 조회로 복구한 건수. 지연이 올라갈 때 신호 발행·구독 대기와 DB 조회 시간을 나눠 본다.
- **알림 밀림** — 가장 오래 기다린 미처리 outbox의 대기 시간, 재시도·실패 건수. 대기 건수와 함께 봐야 한 건이 오래 남은 경우와 순간적으로 건수가 늘어난 경우를 구분할 수 있다.
- **DB 장애 응답** — Hikari 연결 획득 대기·시간 초과와 메시지 전송 실패율을 함께 확인한다. 재현 시 실패를 사용자에게 알리기까지의 시간과 복구 후 중복 저장 여부도 기록한다.

## 다음 발표와 문서에 남길 것

발표 첫 장에 브라우저 → 서버 A/B → Redis·MySQL 구조를 그리고, 각 화살표에 **메시지 원본, 커밋 신호, 재조회**를 표시한다. 사례 하나당 **감지한 현상 → 관측 근거 → 개선 가설 → 바꾼 코드 → 같은 조건에서 나온 결과 → 남은 한계** 순으로 설명한다. 채팅 목록은 쿼리 분석을, 장애 대응은 Redis·서버·DB가 각각 끊겼을 때 무엇이 남고 어떻게 복구되는지를 대표 사례로 사용한다.

다음 측정에서는 운영 배포 구성과 실제로 사용한 테스트 구성을 먼저 구분해 적는다. 그다음 운영과 유사한 환경에서 여러 방에 분산된 부하와 한 방에 집중되는 부하를 각각 재현하고, 부하 중 Redis 중단·수신 서버 재시작을 겹쳐 본다. 성공 조건은 커밋된 메시지의 누락·중복과 복구 지연으로 정한다. 동일 애플리케이션을 복제한 현재 구조로 원하는 지연과 장애 범위를 만족하는지 확인한 뒤, 독립 배포나 장애 격리가 필요한 경우에 서비스 분리의 비용과 이점을 논의한다.

성능 기록에는 비교 커밋, 데이터 크기·분포, 부하·워밍업·반복 횟수, p95·오류율·원본 결과를 남긴다. 설계 문서에는 원본 저장소, 인스턴스별 상태, 장애 시 복구 경로, 보장하는 범위를 적는다. API 명세에는 메시지 순번과 재연결 후 `afterSequence` 조회 계약을 연결한다. 같은 사실을 여러 문서에 복제하기보다 실행 값과 계약의 원문을 링크한다.
